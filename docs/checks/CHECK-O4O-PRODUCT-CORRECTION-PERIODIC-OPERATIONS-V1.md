## 한계·운영 경계

예약은 in-process worker가 실행 중일 때 처리한다. Cloud Run 휴면 중 정시 실행·상시 외부 cron 보장은 없다. 지연·누락 수·마지막 tick을 공개하고 부팅 후 처리한다. 한 실행 최대 50,000개, 한 tick 최대 4페이지이며 관리자가 범위를 나누고 진행을 확인한다.

설명서 갱신은 수동 검토 작업이다. 검토 종료를 설명서 게시·QR 변경으로 표시하지 않는다. 알림은 관리자 화면 내 보관·확인만 수행한다. 운영 로그인·실상품·운영 예약 생성은 수행하지 않았다. 테스트 계정 기준 파일은 이 worktree와 기준 checkout에 없으며 과거 계정으로 대체하지 않았다.

현재 단계는 push까지다. 향후 통합·배포는 별도 명시적 요청과 해당 HEAD의 기술 gate 확인 후 진행한다. 사용자 데이터 정기 보정의 실제 실행을 이번 개발 검증으로 대신하지 않는다.

### 발견·수정

1. **설정 키 길이**: settings.key의 varchar(100) 계약과 달리 신규 P2/정기 운영 fixture는 text였다. 예약 시작 실패 알림 key 102자가 실패해 오류 기록까지 rollback되는 사례를 실제 제한을 적용한 격리 DB에서 재현했다. 긴 알림·갱신 버전 키만 전체 논리 key의 SHA-256으로 제한 안에 저장한다. 기존 짧은 키와 논리 ID는 유지하고 긴 알림 확인도 같은 키로 동작한다. 16자 기존 언어 설명서의 갱신 이력 저장도 확인했다. migration은 없다.
2. **동시 설명서 승격**: 원본 점검 시 canonical이 없었으나 반영 직전 다른 관리자가 기존 candidate를 canonical로 승격하면 전체 조건 UPDATE가 새 설명서를 강등시킬 수 있었다. 재현 테스트가 수정 전 잘못 성공하는 것을 확인했다. 확인·잠금한 기존 ID만 강등하고 새 canonical은 unique 충돌로 차단해 상품 변경까지 rollback한다.
3. **저장 성공과 후속 조회 실패**: 대량 실행·예약·갱신·실행 제어·알림 확인이 저장된 뒤 현황 읽기만 실패한 경우를 분리했다. 확정된 실행·revision·확인 상태와 성공 안내를 유지하고 재생성 대신 새로고침을 안내한다.
4. **직접 링크의 미저장 검토 의견**: 과거 변경안 직접 링크를 열어 승인 선택·의견을 편집한 뒤 원본을 새로고침하면 링크의 저장본으로 입력이 초기화됐다. 링크 최초 진입 때만 저장본을 선택하고 이후 새로고침에서는 입력과 선택을 유지한다. 최근 30개 밖의 선택 변경안도 목록에서 유지한다.
5. **worker 선점 충돌**: REPEATABLE READ + SKIP LOCKED에서 snapshot 이후 갱신된 실행 행을 선점하려 할 때 40001이 발생해, 실제 페이지를 가져오기 전인데도 전체 tick이 실패하는 경우가 반복 검증에서 드러났다. 선점 전의 해당 충돌만 다음 tick으로 미루고 실제 처리 실패 횟수·실패 알림으로 계산하지 않는다. 다른 DB 오류와 이미 선점한 페이지의 실제 오류는 기존 실패 처리를 유지한다.

### 최종 검증

- API Jest **8개 suite / 171개 통과**. 신규 재현 2건은 수정 전 실패를 확인한 뒤 수정 후 통과했다. 실제 varchar(100)/varchar(50) 설정 계약에서 전체 회귀를 수행했다.
