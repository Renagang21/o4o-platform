## 실행 범위와 결과

계정 선정 SSOT는 기준 checkout의 로컬 전용 `docs/local/TEST-ACCOUNT.txt`다. 해당 안내의 연결 조사 결과와 운영 재연결 완료 기록은 이 작업의 승인된 테스트 계정을 canonical Store Owner Demo로 지정하고 공통 계정 코드 정본을 참조한다. 안내가 없는 상태에서 과거 seed/Demo 계정으로 대체한 것이 아니다. 검증은 사용자가 연결을 승인한 이 테스트 계정의 운영 API 흐름에 한정되며, 별도의 비공개 일반 사용자 계정 검증 완료를 뜻하지 않는다.

이 계정으로 이메일·비밀번호 인증을 실제 실행했다. credential은 `packages/auth-utils/src/demoAccounts.ts`에서 읽었으며 공개 기록에 세션·계정·조직 식별자·응답 원문을 넣지 않는다. 최초 검증 당시에는 브라우저 연결 도구가 없어 HTTP API 검증만 수행했다. 당시 결과를 화면 조작이나 실제 기기 검증으로 간주하지 않는다.

- 로그인: HTTP 200 / success=true.
- 접근 가능한 조직: 17개. 실제 개설 매장이 17개라는 뜻이 아니다. 기존 재연결과 삭제 미실행 상태가 남아 있다.
- 17개 조직을 선택해 서비스·자료·사본·자체 상품 목록을 읽었다. 제작 자료를 조회할 수 있는 매장은 1개이며, 이전 private before 기록의 유지 매장과 일치한다.
- 유지 매장 A: 제작 자료 15개, 자료함 첫 페이지 18개, 자산 첫 페이지 2개, 자체 상품 첫 페이지 8개. 전체 건수와 첫 페이지 항목 수를 혼동하지 않는다.
- 비교 조직 B: 제작 자료 HTTP 403/NO_ORG, 사본 HTTP 403/NO_ORGANIZATION, 자료함과 자산 목록은 HTTP 200/빈 목록. A의 자료를 대신 반환하지 않았다.
- 상품 목록 선택 불일치: A와 B에서 `/api/v1/kpa/store/local-products`가 HTTP 200으로 **동일한 상품 ID 집합 8개**를 반환했다. 응답에 조직 필드가 없어 헤더만으로 소유 조직을 확인했다고 주장하지 않는다. ID 집합의 일치를 실제 비교했다.

처음 자료함 mount root를 조회해 받은 404는 검증 URL 오류였다. 실제 `/kpa/store-library/contents`로 다시 확인했으며 제품 결함으로 기록하지 않는다.

## 선택 상품 목록 불일치 조사

`store-local-product.routes.ts`의 authorize는 요청 선택값을 `resolveStoreAccess()`에 전달한다. 공통 helper는 `isStoreOwner()`가 반환한 조직을 그대로 채택한다. 기존 resolver의 정책은 허용 후보 밖 선택값을 무시하고 기존 단일 후보로 돌아가는 것이다. 반면 PR #434의 자료 어댑터는 요청의 명시 선택값과 해석 결과가 다르면 차단한다.

읽기 재현은 선택 매장 화면과 실제 데이터 범위가 어긋나는 문제를 보여준다. 타 사용자 데이터 접근이나 운영 쓰기 성공으로 확대 해석하지 않는다. 상품 생성·수정도 같은 authorize를 쓴다. 후속 실행에서 유지 매장 A의 생성·수정은 성공했으며 새 상품의 다른 조직 선택 조회도 HTTP 200으로 반환돼 불일치를 다시 확인했다. 비교 조직에 상품을 쓰지는 않았다.

공통 resolver를 임의 변경하지 않는다. `O4O-STORE-ACCESS-AND-MEMBERSHIP-V1`의 선택 힌트 규칙과 모든 소비처 영향을 검토한 뒤 서비스 어댑터 또는 UI의 선택 확인 경계를 결정한다. 소비처에는 자체 상품, 취급 상품, playlist, event offer, Neture seller가 있다.

## 실제 작성·복사·게시 실행 결과

동시 변경 없음 확인 이후 canonical Store Owner Demo로 새로 로그인하고 유지 매장 A를 기존 private before 기록으로 확정했다. 비교 조직 B는 조직 선택 불일치의 읽기 검증에만 사용했다.

| 단계 | 결과 |
|---|---|
| 자체 상품 등록 → 상세 조회 → 수정 | 201 → 200 → 200 |
| 새 상품을 다른 조직 선택으로 조회 | 200 — 선택 불일치 FAIL 재현 |
| 직접 자료 작성 → 조회 → 수정 | 201 → 200 → 200 |
| 직접 자료를 다른 조직 선택으로 조회 | 403/NO_ORG |
| 직접 자료 삭제 → 삭제 확인 | 200 → 404/NOT_FOUND |
| 자체 상품 비활성화 → 상세 확인 | 200 → is_active=false |
| 기존 공개 CMS 원본을 A로 새 복사 | 201 |
| 새 사본 편집 → 편집 내용 재조회 | 200, 수정 제목 일치 |
| 사본을 다른 조직 선택으로 조회 | 403/NO_ORG |
| 사본 게시 → 게시 상태 재조회 | 200, publishStatus=published |
| 사본 수정·게시 후 CMS 원본 비교 | 원본 목록 항목 동일 |
| 검증 사본 숨김 | 200 |

원본은 변경하지 않았다. 따라서 원본을 나중에 변경해도 사본이 유지되는 방향의 독립성은 아직 미검증이다. 실제 약국 업무 자격이 확인된 매장은 A 하나이므로 B에서 작성·게시가 정상인 두 매장 시나리오도 완료했다고 주장하지 않는다. 브라우저 화면과 기기 출력은 별도다.

정리 범위의 한계: `asset-copy-core`의 `deleteById`는 snapshot 행만 삭제하며 편집 자료·게시 제어의 종속 정리를 하지 않는다. 기존 migration/entity에서도 해당 연결의 cascade를 확인하지 못했다. 불완전한 삭제로 orphan을 만들지 않고 새 검증 사본을 hidden으로 유지했다. 사본·편집 자료·게시 제어의 완전 정리는 미완료다. 검증 식별 정보는 작업 공간의 private 기록에만 보관하며 공개 문서에는 넣지 않는다. 상품은 표준 API 규칙에 따라 비활성 행으로 남는다.

[검증 사본 정리 WO](../work-orders/WO-O4O-STORE-VERIFICATION-COPY-CLEANUP-V1.md)에서 이번 사본만 대상으로 하는 CLI와 운영 연결 제안을 준비한다. 일반 삭제 API/Core 수정과 기존 자료 일괄 삭제는 범위 밖이다. 실제 운영 정리 결과가 확인되기 전에는 위 완전 정리 TODO를 완료 처리하지 않는다.
