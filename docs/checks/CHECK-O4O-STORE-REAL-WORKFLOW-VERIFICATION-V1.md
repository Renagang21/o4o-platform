## 실행 범위와 결과

운영 서비스의 canonical Store Owner Demo 계정으로 이메일·비밀번호 인증을 실제 실행했다. credential은 `packages/auth-utils/src/demoAccounts.ts`에서 읽었으며 공개 기록에 세션·계정·조직 식별자·응답 원문을 넣지 않는다. 브라우저 연결 도구가 없어 HTTP API 검증만 수행했다. 화면 조작이나 실제 기기 검증으로 간주하지 않는다.

- 로그인: HTTP 200 / success=true.
- 접근 가능한 조직: 17개. 실제 개설 매장이 17개라는 뜻이 아니다. 기존 재연결과 삭제 미실행 상태가 남아 있다.
- 17개 조직을 선택해 서비스·자료·사본·자체 상품 목록을 읽었다. 제작 자료를 조회할 수 있는 매장은 1개이며, 이전 private before 기록의 유지 매장과 일치한다.
- 유지 매장 A: 제작 자료 15개, 자료함 첫 페이지 18개, 자산 첫 페이지 2개, 자체 상품 첫 페이지 8개. 전체 건수와 첫 페이지 항목 수를 혼동하지 않는다.
- 비교 조직 B: 제작 자료 HTTP 403/NO_ORG, 사본 HTTP 403/NO_ORGANIZATION, 자료함과 자산 목록은 HTTP 200/빈 목록. A의 자료를 대신 반환하지 않았다.
- 상품 목록 선택 불일치: A와 B에서 `/api/v1/kpa/store/local-products`가 HTTP 200으로 **동일한 상품 ID 집합 8개**를 반환했다. 응답에 조직 필드가 없어 헤더만으로 소유 조직을 확인했다고 주장하지 않는다. ID 집합의 일치를 실제 비교했다.

처음 자료함 mount root를 조회해 받은 404는 검증 URL 오류였다. 실제 `/kpa/store-library/contents`로 다시 확인했으며 제품 결함으로 기록하지 않는다.

## 선택 상품 목록 불일치 조사

`store-local-product.routes.ts`의 authorize는 요청 선택값을 `resolveStoreAccess()`에 전달한다. 공통 helper는 `isStoreOwner()`가 반환한 조직을 그대로 채택한다. 기존 resolver의 정책은 허용 후보 밖 선택값을 무시하고 기존 단일 후보로 돌아가는 것이다. 반면 PR #434의 자료 어댑터는 요청의 명시 선택값과 해석 결과가 다르면 차단한다.

읽기 재현은 선택 매장 화면과 실제 데이터 범위가 어긋나는 문제를 보여준다. 타 사용자 데이터 접근이나 운영 쓰기 성공으로 확대 해석하지 않는다. 상품 생성·수정도 같은 authorize를 쓰지만 실제 쓰기를 수행하지 않아 쓰기 결과는 미검증이다.

공통 resolver를 임의 변경하지 않는다. `O4O-STORE-ACCESS-AND-MEMBERSHIP-V1`의 선택 힌트 규칙과 모든 소비처 영향을 검토한 뒤 서비스 어댑터 또는 UI의 선택 확인 경계를 결정한다. 소비처에는 자체 상품, 취급 상품, playlist, event offer, Neture seller가 있다.
