> **상태**: COMPLETED — 기존 업무 연결 단계의 개발·main 통합·배포 완료. 신규 원장 개발과 실계정 운영 검증은 별도

> **작업 지시**: 회원에게는 ‘내 상황’, 운영자에게는 ‘처리할 상황’. 개발 인계 후 사용자가 main 통합·배포를 추가 지시

## 1. 문제와 이번 정비

| 문제 | 이번 변경 | 유지하는 경계 |
|---|---|---|
| 운영 첫 화면이 심사 목록 또는 정적인 링크이며 실제 대기 상황을 모아보기 어려움 | 기존 문의함 `/manage` 집계로 운영 홈 구성: 건수·최초 접수일·업무 진입, 1분 갱신·수동 재조회 | 조회 실패를 0건으로 표시하지 않음. 다른 계정·사업으로 바뀌면 이전 결과 제거 |
| 공지·자료·참여 사업·지원·운영 설정이 여러 화면에 분산 | 같은 업무 영역으로 묶되 기존 실행 화면으로 연결 | 별도 공지 확인·교육 진도·일반 캠페인 완료 건수를 만들지 않음 |
| 각 심사 탭마다 진열·약관 설정이 반복됨 | 약국 사업은 별도 사업 설정 탭, 개별 조합은 별도 자료 진열·사업 약관 업무 | 조합 가입 자격·운영자 설정은 기존 Admin 전용 개인 조합 설정으로 유지 |
| CarePharm 문의함의 기존 route가 전용 layout에서 차단되고 사업 한정 운영자 역할도 해당 경로에 적용되지 않음 | 정확한 `/operator/inbox/business/carepharm`만 전용 메뉴·layout·기존 역할 guard에 연결 | 다른 사업 문의함·대표 전체 회원 화면은 허용하지 않음. Neture 활성 자격 및 서버 담당 사업 검사를 유지 |
| 사업별 경로·가입 단위를 공통화하면 개인 조합원을 약국 회원으로 오인할 위험 | 공통 표시 모듈과 약국 사업/개인 조합 adapter 분리 | Pharmcoop은 개인 가입·탈퇴 집계와 개인 조합원 화면 사용 |

운영 홈은 기존 자료 등재·가입·공급 제안 등의 대기 기록과 문의 처리 대기를 연결한다. 일반 프랜차이즈 포털에서 볼 수 있는 교육 수료율·지점 평가·일반 캠페인 진행률을 현재 구현된 것으로 표시하지 않는다. 비교 조사 근거는 [회원 홈 WO](WO-O4O-COOPERATION-MEMBER-HOME-LAYOUT-V1.md)의 공개 제품 설명이며, 비공개 프랜차이즈 운영 화면을 실사했다는 뜻은 아니다.

## 2. Core와 서비스 adapter

- `CooperationOperationsOverview`: 인증 client·scope·endpoint와 실제 목적지/업무 영역을 받는 공통 표시 모듈. GET 집계만 사용하며 회원 자격 판정·업무 상태 변경을 소유하지 않는다. 알 수 없는 대기 업무도 숨기지 않으며 서버의 임의 href 대신 adapter가 정한 경로로 이동한다.
- `BusinessOperationsOverview`: Pharmacy·드럭스토어형 약국·CarePharm 등 약국 단위 사업의 연결. 담당 사업 목록으로 확인된 사업만 표시하며 기존 `?key=&tab=` 심사 직접 진입을 유지한다.
- Pharmcoop: 조합별 `/operator-inbox/cooperative/:slug/manage`와 개인 가입/탈퇴 업무를 사용한다. 조합 ID→businessKey의 명시적 연결과 `cooperativeAccess`를 유지한다. 일반 약국 사업의 membership API를 호출하지 않는다.
- 기존 공유 심사 화면의 새 운영 홈은 opt-in이다. 기존 소비자는 원래 심사 탭을 유지하고, 운영 홈/설정 탭에서 숨은 가입 심사 목록을 조회하지 않는다.
- 알림 전달 확인 건수는 문의의 업무 완료/담당자 배정과 다르다. 기존 문의함의 답변·상태 전이·동시 수정 방지 계약을 변경하지 않는다.

## 3. 후속 개발: 회원 상태와 운영 행위의 연결

이번 단계는 기존 API·화면의 재배치다. 아래 데이터·권한·API 설계와 구현은 완료 범위에 포함하지 않는다.

| 영역 | 현재 가능한 일 / 부족한 점 | 다음 설계·개발 / 완료 판정 |
|---|---|---|
| 공지 | 게시판 공지와 공개 홈 메시지가 별개. 공개 홈 draft/published·노출 기간은 있지만 회원별 필수 확인 기록은 없음 | 공지 대상·중요도·기한·필수 여부·게시 상태, 게시 시점 대상과 공지 버전별 확인 기록 설계. 회원의 ‘확인 필요’와 운영자의 ‘미확인 대상’을 같은 원장으로 조회. 법적 동의·알림 읽음을 확인 기록으로 대체하지 않음 |
| 자료 | 제목·본문·태그·첨부, 초안/대기/게시/보관/반려. 게시 본문 수정은 이전 본문을 보존하는 개정 이력이 아님 | 분류·버전별 본문/첨부·공개 범위·관련 교육 연결 설계. 개정 안내와 회원의 이용 버전 식별. 약국이 이미 만든 매장 사본은 자동 덮어쓰지 않음 |
| 참여 사업 | 공급 제안, 이벤트 상품, 모집 조건 심사는 각각 원장과 상태가 다름. 일반 교육/공동 사업의 모집→신청→승인→진행→종료 흐름과 다름 | 실제 협업체 사업 유형·참여 단위·운영 책임 확정 후 기존 모델과의 연결 설계. 개인 조합원/약국 단위를 유지. 모집 조건 노출 승인과 참여 승인 구분. UI 통일을 위해 공급 계약을 일반 Program 테이블로 대체하지 않음 |
| 지원 | 접수/확인 중/답변 완료/종료/스팸, 답변 발송과 내부 메모·처리 이력. 마지막 처리자는 배정 담당자가 아님 | 담당자·처리 기한·필요 시 분류 설계. 회원의 ‘내 문의’에는 검증된 소유권 연결 필요. 익명 문의 이메일 일치만으로 계정에 연결하지 않음. 알림 수신 담당 그룹과 문의 건별 담당자 구분 |
| 운영 홈 | 현재 실제로 존재하는 대기 건·최초 접수일·처리 화면 연결 | 위 원장 구현 후 필수 공지 미확인·자료 검토/개정·사업 승인/진행 지연·담당 문의별 후속 행동을 추가. 조회 권한·기간·미조회 상태를 명시하며 가짜 0건/완료율 금지 |

권장 순서: ① 공지 대상·확인 계약과 문의 소유권/담당 계약 확정 → ② 회원/운영자 양면 조회와 실제 처리 구현 → ③ 자료 개정·교육 연결 → ④ 실제 사업 유형별 참여 흐름 → ⑤ 해당 원장으로 운영 홈 확장. 새 DB schema·migration·권한 범위 확대는 별도 작업의 명시적 범위로 정한다. 이번 작업에서 운영 DB write나 migration을 하지 않는다.

CarePharm 사업자 정보·약관·개인정보처리방침의 실제 게시 준비는 별도다. 사업자 정보 빈칸 초안을 이번 화면 정비로 게시 완료로 취급하거나 신규 가입 차단을 해제하지 않는다.
