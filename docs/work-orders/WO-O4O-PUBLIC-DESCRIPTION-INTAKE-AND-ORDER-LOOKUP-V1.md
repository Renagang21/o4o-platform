## 현재 지시와 범위

정부 공개정보를 우선하고 제조사 공식 B2C 자료로 보완한다. 공개 근거가 없으면 자동으로 설명을 만들지 않는다. 실제 설명이 없는 상품 레코드는 저장하지 않는다. 사용자 작성 설명은 작성자·원출처를 유지한 검토 후보로 누적한다. 이미지 분석·저작은 사용자 ChatGPT 앱에서 수행하며 별도 내부 AI 기능을 추가하지 않는다.

바코드·상품명은 주문장 입력값이다. GTIN과 GS1 AI(01)를 정규화하고 정확한 바코드를 우선한다. 이름은 선택 후보이며 자동 연결 근거가 아니다. 포장 바코드별로 설명을 재저작하지 않고 하나의 원천 설명을 재사용한다.

현재 사용자 지시는 과거 설명서 정책의 일반 식품·의약외품 등 신규 제작 보류보다 우선한다. 이번 대상은 제품별 정부·제조사 공개 근거가 확보된 설명의 검토 유입이다. 기존 QR 자료의 공식 DB 채택 보류와 소비자 commerce 은퇴 판정은 변경하지 않는다.

## 조사 결과와 구현 결정

- `shared_product_descriptions`와 기존 canonical 승격·감사 서비스를 유지한다. 새 테이블·migration·ProductMaster의 역방향 FK 없음.
- 원천 설명과 출처는 기존 `ProductCandidate.raw_payload`에 보관한다. 본문이 있는 후보만 접수한다. 미연결 후보를 이유로 ProductMaster를 자동 생성하지 않는다.
- 기존 canonical을 포함해 미리 대조하고, 관리자가 상품·유형·언어를 선택한다. 교체 시 현재 canonical과 후보의 revision을 재검증한다.
- 하나의 원천을 복수 포장 master에 적용할 때에도 관리자 선택을 요구한다. 물리 canonical은 Frozen 계약의 `(master, type, language)`를 유지한다.
- 매장 기여는 선택 조직의 저장된 상담자료 사본만 접수한다. 다른 조직 열람·매장 사용자의 공통 설명 직접 수정·자동 공개 없음.
- 주문장의 조회는 설명 열람용이다. offer 선택·장바구니·가격·주문 생성의 권위와 결합하지 않는다.
- 운영 DB 변경·대량 반영은 실행하지 않는다. 개발·검증·commit/push까지 수행한다.

## 검증 경계

검증은 합성 fixture와 격리된 로컬 DB를 사용한다. 실제 자료와 자격정보는 public 저장소에 넣지 않는다. 운영 조회 인증 실패를 코드 검증 성공이나 실제 자료 반영 완료로 바꾸어 보고하지 않는다.

참조: [Product Resource Frozen 기준](../baseline/O4O-PRODUCT-RESOURCE-ARCHITECTURE-BASELINE-V1.md), [전문 활용 원칙](../guides/products/O4O-PRODUCT-DESCRIPTION-PROFESSIONAL-USE-POLICY-V1.md), [매장 소비자 commerce 경계](../baseline/O4O-STORE-COMMERCE-BOUNDARY-V1.md), [B2B 주문 계약](../baseline/O4O-B2B-SUPPLIER-TO-STORE-ORDER-CONTRACT-V1.md).


## 구현된 이용 경로

1. 관리자 `/admin/o4o-product-db/description-intake`에서 준비한 `descriptions.json`을 선택한다. 기본 목적은 전문인 상담용 `B2B`, 언어는 `ko`이며 가져오기 전에 변경할 수 있다.
2. 기존 상품·현재 설명 대조는 읽기 전용이다. 접수 버튼은 본문과 공개 근거가 있는 설명을 검토 대기로 저장한다. 같은 파일을 다시 접수해도 동일 자료는 재사용한다. 상품·식별자·가격·주문 데이터 생성은 없다.
3. 관리자만 본문을 수정하고 대상 상품을 선택해 승인한다. 보관자료는 현행성 미확인 표시·별도 확인이 필요하다. 다른 관리자의 후보/대표 설명 수정은 revision 충돌로 차단한다. 승인 전체와 기존 갱신 검토 기록은 한 트랜잭션에서 처리한다.
4. 매장 주문 작업대의 설명 조회는 정확한 바코드를 우선한다. 이름 결과는 사용자가 선택하며, 해당 목적·언어의 승인 설명이 없으면 다른 설명으로 자동 대체하지 않는다. 검색 결과가 없어도 빈 상품을 만들지 않는다.
5. 저장한 매장 상담자료 상세의 ‘관리자에게 제안’은 저장된 revision·실제 상품 연결·선택 조직을 서버에서 확인한다. 상품명과 바코드는 실제 연결 상품에서 읽는다. 사용자 입력 근거는 정부 확인 자료로 둔갑시키지 않고 작성 맥락으로 전달한다. 공통 설명은 관리자 승인 전까지 바뀌지 않는다.

API: 관리자 `/api/v1/admin/o4o-product-db/description-intake`, 인증된 공통 조회 `/api/v1/neture/products/library/description-lookup`, 매장 소유자 기여 `/api/v1/kpa/store-contents/direct/:id/product-contribution`.

## 검증 결과

- `pnpm install --frozen-lockfile` 및 `pnpm run build:packages` 완료. 의존 manifest·lockfile 변경 없음.
- API `tsc --noEmit`와 production build, 관리자 `tsc --noEmit`·Vite build, 매장 TypeScript·Vite build 통과.
- API 입력·권한·기존 설명 작성 회귀 15건, 관리자 변환/검토 화면 6건, 매장 조회/제안 화면 4건 통과.
- 별도 localhost PostgreSQL의 합성 schema 통합 테스트 7건에서 빈 본문 제외, 읽기 전용 preview, 동시 중복 접수, 보관자료 승인 확인, 목적·언어 격리, stale canonical 차단, 전체 rollback, 매장 조직·실제 연결 상품·revision 검증을 수행했다. 동시 승인 한 건만 반영되는 것도 확인했다. 테스트 schema는 종료 시 완전 삭제했고 잔존 schema 0개 확인 후 이 작업의 컨테이너·볼륨도 삭제했다.
- 실제 준비 자료의 offline 변환/서버 입력 검증: 1,205개 수용, 빈 설명 0개, 보관자료 15개, DB write 0회. 실제 자료·증빙·POS 원본은 저장소에 포함하지 않는다.

## 운영 반영·인계 경계

개발 브랜치 `wo/product-description-public-data-workflow`를 push하여 통합 담당에게 인계한다. 이번 작업에서 main 병합·배포·운영 자료 반영은 하지 않는다.

설정된 테스트 계정의 읽기 전용 로그인 점검은 각각 HTTP 401, 비밀번호 세션 비허용 HTTP 403으로 실패했다. 로컬 테스트 계정 SSOT도 이 checkout과 기준 checkout에 없다. 따라서 운영의 기존 상품과 1,205개 설명의 실제 대조·승인 건수는 확인하지 않았고, 운영 DB에 접수하지 않았다.

후속 운영 단계는 정상 인증 확보 후 관리자에서 파일 대조→접수→승인이다. 실제로 연결되지 않는 상품은 기존 기본 상품 관리 경로에서 확인하며 설명 유입을 이유로 자동 생성하지 않는다.

문서 정합: 과거 일반 식품·의약외품 신규 제작 보류와 현재의 공개 근거 기반 수용 범위 차이는 본 WO에 사용자 지시로 기록했다. Frozen 자산 소유 구조, 기존 QR 자료 공식 채택 보류, B2B 주문 권위는 유지했다. canonical 색인/정본의 범위 밖 본문은 수정하지 않았다.

## 통합 단계 보완 (2026-10-27)

후속 사용자 지시로 이 공간에서 main PR 통합과 배포까지 진행한다. 위의 개발 단계 ‘push까지’ 경계는 당시 범위 기록이며, 이번 통합 지시가 이를 대체한다. 운영 상품 설명 자료의 대량 접수·승인은 별도이며 이번 배포에 포함하지 않는다.

PR #861 Codex P1 검토에서, 기존 운영자 상품 후보 API가 `service_key IS NULL`인 설명 제안까지 읽거나 처리할 수 있는 경로를 확인했다. 공유 저장소 사용과 검토 권한은 별개이므로 설명 리소스 라벨을 예약하고 다음과 같이 격리했다.

- 일반 후보 목록은 명시적인 source label 필터와 cross-service 조회에서도 설명 리소스를 제외한다.
- 일반 후보 상세·충돌 정보·거절·보관·연결/승격·일괄 상태 변경에서는 해당 리소스를 읽거나 바꾸지 않는다.
- 일반 후보 생성 API로 예약 라벨 또는 설명 리소스 payload를 위조하지 못한다.
- 기존 라벨 없는 후보·다른 공개자료 후보는 조회·일괄 처리 동작을 유지한다.

격리된 PostgreSQL 통합 검증을 8건으로 확장하여 실제 DB에서 위의 목록·상세·일괄 변경·거절·보관·위조 생성 차단과 관리자 전용 검토 경로 유지를 확인했다. API production build와 관련 후보/공급자 API 회귀 테스트 39건도 다시 통과했다. 재검증 schema 잔존 0개 확인 후 일회용 컨테이너·볼륨을 삭제했다. 이 수정은 권한 확대가 아니라 승인된 관리자 전용 경계의 누출을 닫는 조치다.

CI의 관리자 정보구조 회귀 검사가 새 화면 탭과 사이드바 정본의 불일치를 발견했다. 관리자 메뉴 SSOT와 permission map에 같은 진입점을 추가하고, 직접 URL도 기존 백엔드와 같은 플랫폼 관리자 경계로 제한했다. 소비처는 관리자 `useAdminMenu`·`AdminSidebar`·메뉴 진단 화면과 메뉴/권한 계약 테스트이며, 다른 서비스의 메뉴·공용 패키지는 이 설정을 import하지 않는다. 기존 메뉴의 역할은 변경하지 않았다. 사이드바/탭 1:1, 신규 메뉴의 플랫폼 역할, 직접 URL 보호, 전체 클릭 수 증가를 계약 테스트에 반영했다.

메뉴 보완 후 관리자 전체 Vitest 42개 파일·517건, TypeScript 검사·production build를 통과했다. 실제 `AdminSidebar`와 메뉴 SSOT·permission map을 이용한 합성 세션에서 1440px·390px 사이드바→신규 화면 진입과 서비스 운영자에게 해당 메뉴가 표시되지 않는 것을 확인했다. page error는 없었다. 운영 로그인 검증으로 간주하지 않는다.
