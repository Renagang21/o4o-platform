### 유지할 구분

- 공통: 중앙 운영자 지정·회수, 현재 서비스 역할 재판정, 서비스 회원 조회·심사·제재, 목록/폼/오류 처리 등의 기술 기반.
- 서비스별: 실제 심사 대상·필수 정보·운영 절차·게시/공개 범위·처리 상태·사업 지표·감사 항목. 공통 화면 부품을 쓴다는 이유로 같은 운영 절차를 강제하지 않는다.
- 중앙 관리자와 서비스 admin은 서로 다르다. 플랫폼 계정·운영자 부여·전체 시스템 정책을 서비스 운영 화면에 확장하지 않는다.
- 개별 커뮤니티 admin/operator, 사업 담당자, 공급자/개설자/강사는 별도 관계·소유권으로 판정한다. 동일한 운영자 아이디여도 다른 서비스 역할을 자동 부여하지 않는다.
- 공통 회원 operator의 조회·승인·반려와 admin의 정지·해제·탈퇴 정책은 유지한다. 이 정책을 입금·수료증·회비·사업 담당 권한으로 자동 복사하지 않는다. 금융/사업 역할 변경은 기존 정책부터 조사한다.

### 정상 유지 / 결함 후보 / 레거시 후보 / 정책 미정

- 정상 유지: 기존 서비스별 guard와 업무 원장, 완료된 회원·커뮤니티·펀딩·약국 사업 정비. 기존 화면/API가 있는 기능은 재구현보다 업무 단위 확인을 우선한다.
- 결함 후보: 메뉴에서 실제 업무/API로 연결이 안 되는 경우, 실패를 빈 목록으로 숨기는 경우, 처리 후 지표/목록 불일치, 권한 회수·소유권 변경 후 접근 잔존. 이번 1차 조사만으로 서비스 전체에 결함이 있다고 확정하지 않는다.
- 레거시 후보: 과거 플랫폼 admin 메뉴·다른 서비스 업무·이전 HUB/LMS 항목. route/capability/직접 URL/API/공유 소비처를 확인한 뒤 유지·이동·제거를 판정한다.
- 정책 미정: 새 신고·제재·승계 규칙, 사업 담당 admin/operator 분리, 금융 업무의 역할 확대/축소, 이력 보존·자동 삭제, 신규 승인/알림 절차. 기존 사용자 결정이나 정본 근거가 없으면 개발 전에 결정한다.

## 4. 조사 후 수정 TODO — 실제 개발 관리 기준

각 항목은 상세 조사 → 수정 TODO → 필요한 구현 → 검증·push·main·배포 증거까지 완료해야 체크한다. 기능 존재만으로 완료 처리하지 않는다. 초기 조사 체크 완료는 아래 미완료 개발 항목을 대체하지 않는다.

- [ ] 개설 신청 → 심사/반려 → 승인 → 포럼 연결의 상태·권한·실패 복구를 다시 대조한다. 개설자의 단계별 운영과 운영자의 예외 처리 권한을 구분한다.
- [ ] 이미 있는 포럼 실패 탭·복구 API·상세 재시도를 실제 연결로 확인하고 누락된 오류/처리 결과만 정비한다.

### T02. 약국 협력사업별 운영

- [ ] 기존 [사업 운영 흐름 WO](WO-O4O-PHARMACY-BUSINESS-OPERATOR-FLOW-V1.md)를 재사용하며 두 사업 담당/한 사업만 담당/일반 회원·타 조직 경계를 확인한다.

### T03. 공급자 서비스 운영

- [ ] 공급자 입점 심사·기본 정보 보완·서류 확인·승인/반려와 활성/비활성 관리의 현행 admin/operator 구분을 대조한다.

## 5. 개발 순서와 완료 기준

기본 순서: **T00(전체 소유권 대조) → T01(진행 중 펀딩의 운영 흐름 마무리) → T02(약국 협력사업) → T03(공급자) → T04(커뮤니티) → T05(강의) → T06(분회) → T07(Neture/약국의 최종 잔여 정합)**. T07의 소유권 조사 부분은 T00에서 먼저 다루고 구현은 해당 담당 서비스 순서에 맞춰 수행한다. 조사로 심각한 권한/데이터 결함이 발견되면 해당 수정부터 우선한다. 다른 담당자가 진행 중인 트랙은 기존 WO에 연결하고 같은 경로를 동시에 수정하지 않는다.

서비스별 완료 기준:

1. 실제 운영 업무 목록과 책임자가 확정되고 필요한 기능이 메뉴·직접 URL·API에서 연결된다.
2. 허용된 현재 역할/담당 관계만 작업할 수 있고 회수·상태 변경 후 기존 세션에서도 차단된다.
3. 목록 → 상세 → 처리 → 사유/결과·이력 → 사용자 화면 반영까지 연결된다.
4. 조회 실패·저장 실패·중복 요청·늦은 응답과 모바일 업무 흐름을 검증한다.
5. 해당 서비스/사업/분회에서 한 작업이 다른 서비스·공통 계정·다른 조직의 상태를 의도치 않게 바꾸지 않는다.
6. 영향받은 API/웹의 필요한 회귀·빌드, 최신 HEAD CI·Sonar 적용 결과·리뷰·정상 병합·필요한 배포를 확인한다.
7. 자동 검증·운영 read-only·실계정 미실행을 구분하고 사용자 직접 테스트를 CHECK에 남긴다.
