## 1. 목표와 적용 범위

하나의 개발 묶음으로 운영자가 업무를 발견하고, 담당 범위에서 처리·답변하고, 결과와 이력을 확인하며, 실패한 알림을 복구할 수 있게 한다. 메뉴나 API의 존재만으로 완료 판정하지 않는다. 아래 항목은 별도 소규모 개발 요청으로 나누기 위한 목록이 아니라 같은 묶음의 조사·구현·검증 기준이다.

대상은 Neture, Supplier, Funding, Community, Study(lecture), Store의 실제 서비스 운영 업무와 Pharmacy·CarePharm·드럭스토어형 약국 약국 협력사업, Pharmcoop 연합회 및 각 서브디렉토리 조합이다. 약사회 분회도 기존 지역 업무·권한·알림의 누락 확인에 포함한다. 독립 운영 workspace가 없는 서비스와 퇴역 서비스에 동일 메뉴를 복제하지 않는다.

operator는 가입 심사·이용 정지/해제·콘텐츠 숨김/복구·문의·일상 처리를 맡는다. admin은 영구 삭제와 서비스 영향 조치, 기존 계약상 운영자 지정 등을 맡는다. 같은 계정이어도 서비스·사업·조합 권한을 자동 전파하지 않는다. 전체 관리자 화면 개발은 다른 담당 트랙이다.

## 5. 범위 밖과 착수 경계

- 최초 승인은 TODO까지였으며 후속 `진행해` 지시로 개발을 착수했다. 개발 승인은 운영 write·migration·배포 승인이 아니다.
- 서비스 회원·활동·외부 첨부파일 완전 삭제는 admin 별도 묶음. 공유 참조·법정 보존·외부 삭제 재처리가 필요하며 일상 운영에 섞지 않는다.
- 전체 관리자 개발, 새로운 신고·소유자 승계 제도, 통합 운영 대시보드, 퇴역 서비스 복구 제외.
- 펀딩은 오프라인 계좌이체와 운영자 수기 기록을 유지. 은행 조회·PG·자동 송금/환급·자동 모집 결과/중지·개설자 승계 제외.
- schema·권한/API·공통 계약 변경 필요사항은 후속 설계에서 구체화한다. 현재 승인 밖 위험 변경은 저장소 절차에 따라 확인하고, 운영 migration·실계정 데이터 변경은 별도 명시 승인 없이 실행하지 않는다.
