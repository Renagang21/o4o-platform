> **상태**: ACTIVE
> **작성일**: 2026-11-14 · **최종 갱신**: 2026-11-14
> **근거**: 사용자 요청 — 사진 입력 우선, 관리자 정기 상품 정비, 주문 자동화 발견 자료도 활용

## 목적과 현황

거래명세서 사진 → ChatGPT 또는 O4O에서 정리 → 사용자 확인·수정 → 거래장 업무자료 보관 → 관리자의 정기 상품 DB 정비로 이어간다. QR은 이번 범위에서 제외한다. ChatGPT 경로에서 이미 읽은 사진을 O4O가 LLM API로 다시 판독하지 않는다. 비용 계산·요금제 연동·새 앱은 범위 밖이다.

3차를 A 공통 처리부, B 저장·인증 연결, C 화면·ChatGPT 연결로 나눈다. **A·B·C 구현과 격리 검증 완료, 통합·운영 적용 대기**다. B·C는 개발 branch `wo/photo-ledger-chat-integration`에서 함께 진행했다.

## 조사 근거

- `tools/o4o-local-agent/src/pharmacy-order-contract.mjs`: 기존 purchase는 상품·포장 연결과 프로그램 origin을 요구하며 명세서 단가·금액·제조번호·유효기한을 담지 못한다.
- `apps/api-server/src/services/work-data/work-data.service.ts` 및 local `pharmacy-data.mjs`: 사용자 lane의 purchase·usage·sale·balance 입력을 차단한다. 사진을 프로그램 원본으로 위장하지 않는다.
- `apps/api-server/src/modules/external-ai/adapters/store.adapter.ts`: 기존 save는 자료함 문서다. 거래장 입력 API로 오인하지 않는다.
- `apps/api-server/src/modules/neture/entities/ProductCandidate.entity.ts`: 관리자 상품 후보 큐가 존재한다. 거래 가격·매장 잔액까지 공용 상품 후보에 복사하지 않는다. 기존 후보 타입·소유권·중복·승격 경로의 정합 확인 후 B에서 연결한다.
- 구조 정본 Personal Assistant V2 §6-4: 기존 대화에서 확인·수정하고 업무 데이터와 Experience를 분리한다. 상품 매칭을 업무 시작 조건으로 강요하지 않는다.

## A. 구현한 공통 처리부

`apps/api-server/src/services/transaction-ledger/photo-invoice.ts`:

- 문서·행 스키마: 공급자·수취 사업자번호(알면), 명세서 번호(알면), 일자, 매입/반품, 원문 행, 상품명·업체코드·바코드·제조사·규격·수량·단위·단가·금액·제조번호·유효기한. 없는 값은 null, 세금 미상은 unknown.
- `inspectPhotoInvoice`: 미확정 경로·필수 누락·수량 0·행 금액·인쇄된 행 합계 불일치 검사. 소수점 6자리까지 BigInt 고정 소수점 계산. 불완전한 전체 합계를 추측하지 않는다. 일반 합계와 세금 포함 청구 총액을 혼동하지 않는다.
- 사진별 검증된 바이트 해시·페이지와 정리 내용을 revision에 반영한다. 수정 후 이전 revision의 확인 준비는 거절한다. 원문 상품명과 수량 단위는 바꾸지 않는다.
- `invoiceDuplicateHints`: 소유자별 사진 지문과 발행·수취 사업자번호+명세서번호+일자의 문서 지문. 식별정보가 없으면 문서 지문은 null. 지문은 중복 조회 힌트일 뿐 확정·자동 병합 근거가 아니다. 재촬영·페이지 일부 업로드·프로그램 수집본과의 중복은 B에서 별도 대조한다.
- `preparePhotoInvoiceConfirmation`: 문제가 없는 현재 revision의 확인 준비와 행별 관리자 정비 후보를 반환한다. 공통 상품 연결은 필수가 아니다. 후보는 원문 상품 정보와 출처 revision·행 ID만 포함하며 가격·거래처의 민감 거래정보는 포함하지 않는다. 상품 DB 쓰기나 후보 DB 저장은 하지 않는다.
- 함수들은 인증·사용자 승인·DB transaction을 대신하지 않는다. 실제 원본 업로드와 소유권을 검증한 어댑터가 사용해야 한다. 사진 메타데이터는 원본 보관 자체가 아니다.

검증: 합성 명세서 초기 Jest 20건과 처리부 strict TypeScript 검사 통과. 현재 검증은 아래 통합 기록을 따른다. 실제 사업자·상품·사진은 테스트에 넣지 않았다. 기존 프로그램 구매 형식에 금액을 넣거나 origin 없이 넣으면 거절되는 것도 조사 과정에서 확인했다. 초기 A에는 화면·route가 없었으며 B·C에서 확인 화면과 브라우저 검증을 추가했다.

## B. 저장·인증·원본 보관 — 구현

1. 기존 업무 데이터 영역을 재사용하는 저장 계약을 구체화한다. 사진 원본·추출 초안·사용자 교정 이력·확인된 업무 행의 연결을 보존하고, 업무 자료의 local/server 기준 저장소 정책을 따른다. 새 영구 스키마가 필요하면 migration·보존 규칙과 영향을 구체화해 통합 담당 검토 대상으로 인계한다.
2. 할인·세금·반올림·단위별 실제 명세서 차이를 명시적인 조정 근거로 표현한다. 원문 수량·단가·금액을 계산에 맞춰 덮어쓰지 않는다. 거래장 원장과 프로그램 원본의 동일 거래를 대조하고 이중 집계하지 않는다.
3. 서버에서 현재 초안을 다시 읽고, 연결된 작업공간·계정·쓰기 권한·revision·확인 요청을 검증한다. 호출자가 임의의 owner/actor를 모델 입력으로 지정하지 못하게 한다. 기존 자료함 쓰기 권한을 거래장 쓰기 권한으로 자동 확대하지 않는다.
4. 동일 명령 재시도 중복 방지와 별개의 실제 중복 거래 조회를 구현한다. 확인된 거래장 자료와 관리자 정비 후보 전달 기록을 같은 transaction 또는 재시도 가능한 outbox로 보장한다. 확인 준비 결과만으로 저장 완료라고 반환하지 않는다.
5. ProductCandidate 유입 규칙을 재사용하되 신규 상품 생성·바코드 확정·표준명 변경은 관리자의 정기 작업으로 남긴다. 주문 과정에서 발견한 상품 정보도 출처를 분리해 같은 후보 흐름에 연결한다. 매장별 거래 내역과 가격은 관리자 상품 정비 목록에 노출하지 않는다.

## C. O4O·ChatGPT 공통 이용 — 구현

- 기존 O4O 대화 안에서 확인·수정·실패 복구를 제공한다. 별도 데이터 정비 메뉴를 이용 전제로 추가하지 않는다.
- ChatGPT에는 초안 준비·조회·수정·확인 요청과 결과 조회 기능을 연결한다. O4O는 검증·저장만 실행한다. 기존 일반 문서 저장 도구와 구분한다.
- PC·모바일, 매장 간 격리, 권한 철회, 수정 후 오래된 확인, 같은 사진 재전송, 재촬영, 프로그램 수집본 중복, 부분 실패와 복구를 검증한다.
- 확정 저장은 실제 전체 명세서와 사용자 확인으로 검증한다. 이번에 제공된 부분 사진은 가림·잘림이 있어 확정 저장 근거가 아니다.

## 실행 결과와 인계

- **저장:** `PhotoLedgerService`와 `/api/ai/transaction-ledger`. 명세서·수정 이력·사진·명령 재시도 4개 테이블을 추가한다. 원본 byte hash는 서버가 계산하며 교체 전 사진도 보존한다. 매장별 서버 기준 저장소 동의와 기존 StoreAdapter 권한을 재검사한다.
- **확정:** 현재 version/revision, 필수 값·금액, 원본 미보관 확인, 프로그램 등록 상태를 검사한다. 매장별 잠금으로 동시 중복 확인을 직렬화한다. 명세서 상태와 상품 후보 전달은 한 transaction이다. 후보 실패 시 확정을 롤백한다. 동일 재시도와 다른 요청의 중복을 구분한다.
- **공통 상품:** 상품 ID가 없어도 반영 가능하다. 기존 `product_candidates`에 원문 상품 관찰 정보만 pending으로 전달한다. GTIN 형식·check digit이 확인되고 미확정이 아닌 값만 기존 identifier 후보 필드에 넣는다. 가격·사진은 전달하지 않는다. 도메인별 승격 제한을 유지하며 사진 후보를 자동으로 DRUG에 승격하지 않는다.
- **채널:** O4O `/api/ai/request`의 거래장 요청에서 기존 계측을 사용하는 사진 판독 후 초안을 만든다. ChatGPT에는 `prepare_transaction_invoice`, `get_transaction_invoice`, `list_transaction_invoices`를 추가한다. ChatGPT 경로에는 모델 호출이 없다. `o4o:ledger:read/write` 동의는 별도이며 일반 자료함 권한을 확장하지 않는다. 확인 API는 일반 O4O 로그인+정식 Origin에서만 이용하고 MCP에는 확정 도구를 노출하지 않는다.
- **화면:** `/work/ledger`·`/work/ledger/:id`. 매장 선택·서버 보관 선택, 최근 명세서 선택/상세/다음 목록, 필드 수정·원본 표시/추가·중복 사유·직접 반영. O4O 답변은 확인 주소를 실제 링크로 표시한다.
- **생명주기:** 서버 보관 중단 시 사진·이력·재시도와 관련 미처리 후보를 정리한다. 회원 탈퇴 시 개인 attribution만 분리하고 매장 업무 소유권을 유지한다. 폐업 재고 분류와 신규 org writer 차단 trigger를 등록했다.
- **Core 계약 변경:** 신규 영구 테이블 4개, additive REST·MCP API와 ledger scope 2개, 기존 multimodal 출력 한도 선택 인자(기존 기본값 유지). 기존 프로그램 원본 계약·Identity/Frozen·ProductMaster·결제 계약은 변경하지 않았다. dependency/lockfile/CI 변경 없음. `1794618000000-CreatePhotoTransactionLedger.ts`의 운영 적용은 통합 담당 검토 대상이다.
- **검증:** [통합 CHECK](../checks/CHECK-O4O-PHOTO-LEDGER-CHAT-INTEGRATION-V1.md). 운영 DB·외부 AI·실거래 자료에는 쓰지 않았다.

## 남은 범위

운영 적용·실제 앱 재연결·완전한 명세서의 실모델 판독 품질·실계정 사용은 별도로 확인한다. 프로그램 수집본과 사진의 상품별 자동 대조·집계 통합, 주문 과정 관찰 정보 연결, 관리자 후보의 범용 정비·승격 확장은 이번 변경에 포함하지 않는다. 현재 프로그램 등록 여부를 명시하고 기존 프로그램 집계와 사진 거래를 자동 합산하지 않는다. 이는 B 계획의 자동 대조 부분에 대한 보수적인 구현 결정이다.

개발 인계는 `wo/photo-ledger-chat-integration` 하나로 한다. A의 `b1082b6e7`을 cherry-pick한 커밋을 포함하므로 이전 `wo/photo-ledger-review-core`를 별도로 병합해 중복 작업하지 않는다. PR·병합·운영 migration·배포는 통합 담당이 진행한다.
