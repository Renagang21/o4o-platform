## 경계와 미정 정책

공급자 자격과 운영자 역할은 별개다. 개설자는 funding:operator를 받지 않으며 자기 펀딩에만 접근한다. 기존 market_trials/market_trial_participants/market_trial_forums와 Forum 원장을 사용하고 병렬 도메인 원장을 만들지 않는다. 주문·PG·배송·상품 전환을 연결하지 않는다. 오프라인 입금·처리 기록은 보존하고 현재 운영자 업무로 유지한다. 공급자 조직의 다른 구성원에 대한 자동 위임은 포함하지 않는다.

포럼 가입은 ACTIVE 초기 운영 모델 §3의 개설자 수동 승인·제거 정책을 유지한다. 자동 승인 여부에 대한 선택 질문은 답변이 없으므로 새로운 자동 승인 정책으로 간주하지 않는다. 입금 전 승인 이용을 허용하고, 입금 확인과 포럼 회원 원장은 분리한다. 운영 DB migration 적용은 코드 구현 승인과 구분하며, migration이 필요한 경우 정확한 변경·검증·복구 계획을 준비한 뒤 적용 권한을 확인한다.

## 조사 후 수정한 TODO와 구현 계약

1. 기존 공급자 identity resolver(organization owner + ACTIVE supplier + 정상 메인 가입)를 재사용한다. 신규 펀딩은 기존 supplierId(개설자 user ID)를 유지하고 공급자 계정·조직을 funding_created 이력에 기록한다. 다른 조직원에게 자동 위임하지 않는다.
2. 개설자 화면은 /market-trial/manage 아래에 배치한다. 기존 supplier/market-trial 주소는 직접 funding 주소로 연결하고 기존 메뉴·제품 후속 작업·알림을 모두 점검한다.
3. 상태 이력에 funding_submitted/funding_approved/funding_rejected 사유·처리자를 기록한다. 반려는 편집 가능한 draft로 복귀한다. 승인 사실은 저장하되 전용 포럼이 준비되기 전에는 submitted로 유지한다. 공개 DTO에서 심사 사유·처리자 정보는 제외한다.
4. forum_category_requests의 funding:<trial UUID> 코드와 funding-<trial UUID> 고유 slug를 전용 폐쇄형 포럼의 canonical 연결로 사용한다. market_trial_forums는 기존 공고 게시글 연결로 보존하며 게시판 ID와 혼용하지 않는다. 기존 slug unique 및 펀딩 행 lock으로 중복을 막고 schema/migration 없이 구현한다.
5. 포럼 공통 화면/API를 소비한다. 일반·다른 서비스 경로에서는 새 funding scope가 노출되지 않도록 공통 consumer 경계를 좁게 보완한다. generic write guard를 완화하지 않는다.
6. 개설자는 자기 펀딩의 진행 상태를 변경할 수 있다. 입금 확인·오프라인 처리 기록의 권한과 보존은 유지한다. 승인 후 주요 모집 조건 수정·운영자 추가 위임·강제 종료 확대는 이번에 임의 추가하지 않는다.
7. 참여 신청 및 포럼 회원 상태는 별도 원장으로 유지하며 기존 폐쇄형 Forum 원장·화면을 재사용한다. 펀딩 전용 회원 쓰기는 펀딩 행 잠금과 신청 상태 확인을 같은 트랜잭션에 묶어 승인·반려 경합 및 종료와의 경합을 차단한다. 자동 승인하지 않으며 초기 운영 모델 §3의 개설자 수동 심사를 유지한다.
8. 변경 API·Forum 공유 consumer·호스트 경계·역할·비동기 응답·동시성 테스트와 desktop/mobile mock browser를 검증한다. 실계정 검증은 후속 수동 항목으로 남긴다.

운영 schema/migration 변경이 필요하지 않으므로 별도 DDL 적용은 수행하지 않는다. 기존 종료 데이터 중 승인/진행 증거가 없는 행은 반려와 구별할 수 없으므로 공개하지 않고 개설자·운영자 조회에는 보존한다.
