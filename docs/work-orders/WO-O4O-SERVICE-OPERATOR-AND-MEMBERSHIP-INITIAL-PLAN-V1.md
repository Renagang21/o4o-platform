# 서비스 운영자 지정·서비스별 회원 관리 — 초기 정비계획 및 1차 조사 지시서

> **상태**: DRAFT
> **작성일**: 2026-10-09 · **최종 갱신**: 2026-10-09
> **근거 WO/IR**: 사용자 지시 — 서비스 운영자 지정과 서비스별 회원 관리 초기 계획·조사 지시서 작성
> **현재 단계**: 초기 정비계획 및 조사 지시서 작성. 1차 조사 결과와 구현 완료를 의미하지 않는다.

## 1. 목적과 진행 순서

중앙에서 지정한 운영자가 담당 서비스의 운영 화면에 접근하고, 해당 서비스 회원을 관리할 수 있는 기반을 정비한다.

진행 순서는 **초기 정비계획 → 1차 조사 → 조사 결과로 계획 수정 → 추가 조사 → 구현·검증**이다.
현재 문서는 조사를 위한 초안이다. 데이터 구조·API 통합 방식·migration·공통화 대상을 미리 고정하지 않는다.

## 2. 범위와 초기 방향

| 항목 | 사용자 지정 방향 |
|---|---|
| 운영자 지정 위치 | `admin.neture.co.kr`로 일원화 |
| 운영자 역할 | 각 서비스에 `admin`, `operator` 두 종류 |
| 권한 적용 단위 | 사용자 + 서비스 + 역할 |
| 지정·변경·해제 주체 | 중앙 관리자 |
| 서비스 회원 관리 주체 | 해당 서비스에 지정된 admin·operator |
| 공통 계정 관리 | 서비스 회원 관리와 구분 |
| 다른 서비스 접근 | 별도로 지정받은 권한이 있어야 가능 |
| 회원 자격과 운영자 권한 | 별도 관리; 한쪽 변경이 다른 쪽을 자동 변경한다고 가정하지 않음 |

`admin`·`operator`는 업무 역할 이름이다. 저장 문자열을 bare `admin`·`operator`로 바꾸라는 지시가 아니다.
현행 서비스 식별자·역할 접두어·권한 계약을 조사하고 대응표를 작성한다.

콘텐츠 관리, 서비스별 업무 관리, 공통 계정 관리 기능 개편은 범위 밖이다.
그 기능이 이번 두 기능의 권한 판정이나 데이터 변경을 소비하는 경우에는 영향 확인까지만 포함한다.

### 미확정 정책

- admin과 operator의 회원 관리 권한 차이.
- 승인·반려·이용 제한·해제·탈퇴 등 각 기능의 담당 역할과 의미.
- 장기 이용 제한 등 제한 종류·기간·해제 권한. 이전 제안을 확정 정책으로 사용하지 않는다.
- 중앙 관리자 예외와 서비스 운영자 권한의 관계, 운영자 지정과 서비스 회원 자격의 선후 조건.

현재 구현과 실제 업무를 조사한 뒤 사용자와 결정한다. UI에 버튼이 있다는 이유로 정책을 확정하지 않는다.

## 3. 목표와 완료 기준의 초안

1. 중앙에서 대상 서비스의 운영자를 지정·변경·해제할 수 있다.
2. 지정된 운영자가 담당 서비스 운영 화면과 허용된 API에 접근한다.
3. 회원 목록·상세·관리 동작이 정해진 해당 서비스 회원 범위를 따른다.
4. 서비스 A의 회원 상태 변경이 서비스 B의 회원 상태나 공통 계정을 의도치 않게 변경하지 않는다.
5. 운영자 권한과 일반 회원 자격을 별도로 관리한다.
6. 역할 변경·해제가 기존 로그인 상태에서도 적용된다.

서비스·상태·역할별 세부 기대 결과는 조사 후 수정 계획에서 확정한다.

충돌은 문서·코드·실측 근거와 함께 보고한다. 이번 지시서로 Frozen 계약이나 정본을 변경하지 않는다.

## 5. 1차 조사 실행 지시

각 서비스별로 **화면 → API → 서버 권한 판정 → 데이터 저장·조회 구조**를 연결한다.
공통 운영 화면 구현은 활용하되 서비스 wrapper·설정·실제 호출까지 확인한다.
공통 컴포넌트 하나를 확인한 것으로 모든 서비스 동작을 검증했다고 보고하지 않는다.

| 조사 영역 | 반드시 확인할 내용 |
|---|---|
| 서비스 목록 | 유지 대상, 서비스 키·역할 접두어·호스트 대응, 중앙 지정 가능 목록과 runtime catalog 차이 |
| 중앙 지정 | 화면·API·호출자 권한, 대상 서비스·사용자 검증, 중복 지정, 변경·해제 저장, 감사 기록 |
| 운영자 접근 | 메뉴 노출, 직접 URL, server API guard, admin/operator 계층, 서비스 scope와 tenant·분회 scope |
| 회원 구분 | 공통 계정·service membership·role assignment 연결, 일반 회원과 운영자 자격의 독립성 |
| 회원 목록 | service filter, 포함 상태, 운영자 포함 여부, 검색·상세·통계·pagination의 동일한 경계 |
| 회원 관리 | 실제 승인·반려·제한·해제·탈퇴 기능, 역할별 버튼과 server 허용 범위, 부수 역할 부여·회수 |
| 변경 영향 | 변경 테이블·필드·행 조건, 공통 계정 상태·다른 서비스·관련 cache·event 영향 |
| 권한 해제 | token/session의 역할 정보 출처, DB 재조회·cache·갱신 시점, 기존 세션으로 API 차단 여부 |
| 중복·잔재 | 옛 역할명·중복 API·별도 판정 코드, 실사용 소비처와 은퇴 잔재 구분 |

## 6. 조사 안전 경계와 증거

- 1차 조사는 읽기 전용이다. 소스·dependency·lockfile·설정·DB를 수정하지 않는다.
- production의 역할 부여·회수, 회원 상태 변경, migration·seed를 실행하지 않는다.
- 기존 테스트를 검토하고, 실행 전 외부 서비스·DB 연결과 쓰기 여부를 확인한다.
- 변경 동작 실측은 격리된 환경·승인된 검증 계정에서 수행한다. 별도 권한이 필요하면 구체적인 대상·동작을 보고한다.
- 실행 환경·계정이 없으면 코드 확인과 실제 동작 미검증을 분리한다. 미검증을 PASS로 표시하지 않는다.
- 비밀번호·token·개인정보·실제 계정 식별자를 보고서나 fixture에 복제하지 않는다.
- 테스트 데이터 보존만을 이유로 호환 구조를 유지하자는 결론을 내리지 않는다. 실제 사용과 운영 인프라 영향을 확인한다.

근거에는 commit, 파일·함수·route, 호출 흐름, query 조건, 테스트 명령·결과를 기록한다.
역할 해제는 새 로그인뿐 아니라 기존 세션의 동일 API 요청 결과를 확인한다.

## 7. 제출 산출물과 판정 기준

조사 결과는 `docs/investigations/`에 한 문서로 제출하고 본 지시서를 연결한다.
추가 확인 회차는 같은 조사 문서에 누적한다. 불필요한 CHECK나 canonical index 항목을 만들지 않는다.

필수 산출물:

1. 현재 유지 서비스·서비스 키·역할 접두어·호스트·중앙 지정 대상 대응표.
2. 중앙 지정·변경·해제의 화면/API/guard/저장 흐름.
3. 서비스별 회원 목록 포함 기준과 관리 작업별 데이터 변경·영향표.
4. admin/operator의 현재 구현 권한표와 실제 업무 근거, 사용자 결정이 필요한 차이.
5. 기존 로그인 상태의 역할 변경·해제 반영 경로와 검증 결과.
6. 중복·레거시 소비처, 수정 후보, 추가 조사 질문, 실행·미실행 검증 목록.

| 판정 | 처리 방향 |
|---|---|
| 정상 | 유지; 근거와 검증 범위 기록 |
| 구현 결함 | 확정 기준 위반 동작과 최소 수정 후보 기록 |
| 중복·레거시 | 소비처·사용 여부·제거 영향 확인 후 통합/제거 후보 기록 |
| 정책 미정 | 가능한 선택지·실제 업무·영향을 제시하고 사용자 결정 후 반영 |

정책이 미정인 동작을 구현 결함으로 확정하지 않는다. 코드·문서만 확인한 항목에는 실측 미검증 표시를 병기한다.

결과 표 양식:

| 서비스 | 기능 | 현재 동작 | 근거 | 판정 | 영향 범위 | 검증 상태 | 후속 조치 |
|---|---|---|---|---|---|---|---|
| 조사 후 작성 | 조사 후 작성 | 조사 후 작성 | 파일/API/query/실측 | 위 네 분류 | 해당 서비스/다른 서비스/공통 계정 | 실행 결과 또는 미검증 사유 | 수정/정책 결정/추가 확인 |

## 8. 조사 결과로 수정 계획 작성

각 수정 항목에 서비스별 문제, 변경 전·후 동작, 영향 범위, 작업 순서, 완료 기준을 작성한다.
admin/operator 회원 관리 권한과 미정 정책은 사용자 결정 내용을 기록한 후 구현 계획에 반영한다.
Frozen·Core·shared contract 변경이 필요하면 해당 승인 절차와 별도 작업 범위를 명시한다.

## 9. 추가 조사

수정 계획에 남은 질문만 조사한다. 각 질문에 대상 코드·소비처·확인 방법·답이 바꾸는 계획 항목을 적는다.

- 제거할 권한 판정이 범위 밖 기능에서도 사용되는가?
- 서비스 회원 상태를 공통 로그인·session 발급에서도 사용하는가?
- 지정 방식 변경이 기존 운영자·다중 서비스 접근·분회 범위에 영향을 주는가?
- 공통화할 부분과 서비스별로 유지해야 할 lifecycle·scope는 무엇인가?

## 10. 후속 구현·검증 순서

1. 중앙 운영자 지정·변경·해제.
2. 서비스별 운영 화면과 API 접근 권한.
3. 서비스별 회원 목록과 관리 범위.
4. 확정된 admin/operator 회원 관리 권한.
5. 소비처 영향이 확인된 중복·레거시 제거.
6. 실제 역할별 동작 검증.

| 검증 상황 | 기대 결과 |
|---|---|
| A 운영자 지정 | A 운영 화면·허용 회원 관리 가능 |
| A만 지정받고 B 접근 | B 운영 화면·API 접근 차단 |
| A admin → operator 변경 | 기존 세션에서도 확정된 operator 권한 적용 |
| A 운영자 권한 해제 | 기존 세션에서도 A 운영 기능 차단; 회원 자격은 확정 정책에 따라 독립 처리 |
| A 회원 이용 제한·해제 | A에 적용; B 회원 상태·공통 계정에 의도치 않은 변경 없음 |
| 회원 목록·상세 조회 | 확정된 서비스·상태 범위로 제한; 다른 서비스 ID 직접 조회도 검증 |
| 일반 회원만 보유 | 회원 자격만으로 운영 권한을 얻지 않음 |

화면 노출과 server API 차단은 각각 검증한다. 서비스별 일반 회원/admin/operator 및 다중 서비스 지정 조합을 포함한다.
