## 1. 목표

공급자가 기존 제품·자료를 활용해 등록 초안과 콘텐츠를 준비하고, 본인이 확인한 결과를 기존 업무 흐름으로 저장·검토 요청할 수 있게 한다. 새 공급자 전용 챗봇·AI 엔진을 먼저 만들지 않는다.

작업은 두 갈래로 구분한다.

- **현재 경계에서 보완할 경로**: 사용자가 자기 외부 AI에서 작성 → O4O가 결과 형식·허용 필드를 검증 → 화면 초안에 적용 → 사용자 확인 → 기존 저장·검토 요청.
- **정책 범위를 확정해야 하는 확장**: 공급자 문맥에서 O4O가 직접 LLM을 호출하거나 공통 Assistant가 공급자 업무를 실행하는 기능. 이번 문서로 허용된 것으로 간주하지 않는다. 기존 금지를 다른 공통 endpoint 호출로 우회하지 않는다.

제품 등록과 콘텐츠 제작을 첫 묶음으로 삼는다. 협업체별 공급 제안 보조와 공통 Assistant 연결은 후속 단계다. 사용자에게 모델·절차 설계를 맡기는 범용 prompt 입력창보다 현재 업무·선택 자료를 이용해 필요한 요청문을 준비하는 방향으로 설계한다.

## 2. 기준 문서와 적용 순서

- [역할별 업무공간 Architecture](../baseline/O4O-ROLE-WORKSPACE-ARCHITECTURE-V1.md): Supplier·Store·Service Operator·Community 책임과 콘텐츠 전달 경계.
- [Supplier Domain §9](../baseline/O4O-SUPPLIER-DOMAIN-BOUNDARY-V1.md): Supplier 내부 LLM 호출 금지. 외부 LLM은 사용자 작업이며 O4O는 prompt/context/apply/save를 담당한다. ProductMaster 직접 확정·쓰기와 새 Supplier framework도 금지한다.
- [AI 자동화 진화 원칙](../baseline/O4O-AI-AUTOMATION-EVOLUTION-PRINCIPLES-V1.md) §25: 구현 현황과 격차를 확인하고 기존 실행 자산을 필요한 만큼 재사용한다.
- [Personal Assistant V2](../baseline/O4O-PERSONAL-ASSISTANT-ARCHITECTURE-V2.md) §16·§17·§18: 공급자 범위를 자동 확장하지 않으며, ONE Assistant·Task·Experience 구조와 개발 순서를 유지한다.
- [AI 활용 흐름](../baseline/O4O-AI-USAGE-FLOW-BASELINE-V1.md): 외부 AI 작성 결과를 가져오는 흐름과 기존 내부 AI 진입점을 구분한다.
- [Shared Module Change Protocol](../baseline/O4O-SHARED-MODULE-CHANGE-PROTOCOL-V1.md): 공용 편집기 등을 변경하면 전 소비처와 raw-source 계약을 조사하고 Consumer Impact Matrix·smoke를 CHECK로 남긴다.

FROZEN 본문·canonical index·과거 WO를 이 문서에 맞춰 인라인으로 고치지 않는다. 새 정책이 필요하면 변경 대상·허용 행위·남길 금지선·대체 절차를 별도 변경안으로 구체화한다.

## 4. 단계별 TODO와 산출물

이 문서의 P0~P4는 이 도입 트랙의 작업 묶음이다. Assistant V2의 A~I 구조 단계와 별개이며 개발 순서를 대체하지 않는다.

### P0 — 실행 계획 구체화

- [x] 최신 main의 공급자·AI 기준 문서와 주요 구현을 조사한다.
- [x] 기존 제품 작성 보조, 콘텐츠·검토·등재 경로, 공통 Assistant를 구분한다.
- [x] 첫 구현 범위와 정책 결정이 필요한 범위를 분리한다.
- [x] 입력·출력·적용·저장 경계, 회귀 사례, 완료 기준을 작성한다.
- [ ] 작업 branch의 검증·commit·push를 완료하고 인계한다.

### P1 — 기존 제품 등록 보조 검증·최소 보완

- [ ] 전용 작업공간에서 최신 main과 기존 제품 작성 테스트를 확인한다. 기존 코드가 이미 만족하는 요구는 중복 구현하지 않는다.
- [ ] 직접 설명·사진·PDF·URL·Import 초안 보정의 안내와 결과 JSON 계약을 확인한다. 외부 AI에 사용자가 첨부하는 자료와 O4O 업로드를 혼동시키지 않는다.
- [ ] 현재 초안 보존, 빈칸 채우기/덮어쓰기, 오류·부분 결과·취소의 동작을 확인한다.
- [ ] 바코드·허가번호·의약품 분류·브랜드 ID·이미지·가격의 추정/자동 매칭 금지 및 기존 잠금 조건을 검증한다.
- [ ] 자료에 없는 값은 미확인으로 두고 사용자가 확인할 항목을 표시한다. 출처를 확보하지 못한 결과에 가짜 출처를 붙이지 않는다.
- [ ] 실제 결함이 있으면 최소 수정하고 테스트한다. 결과 적용만으로 저장·검토 요청·Master 생성이 일어나지 않는지 확인한다.

**산출물/종료점**: 기존 기능의 통과·결함·미실행 목록, 필요한 최소 수정, 관련 테스트·브라우저 검증. 결함이 없으면 불필요한 코드 변경 없이 결과를 남긴다.

### P2 — 콘텐츠 작성 지원 연결

- [ ] 제품 설명서와 자료함 문서의 기존 편집기·HTML sanitize·저장 계약, 공용 LlmAssistPanel 연결 여부를 먼저 조사한다.
- [ ] 선택한 제품의 확인된 정보와 사용자가 고른 자료로 요청문을 구성한다. 용도는 제품 설명·회원 약국 안내·협력사업 제공·커뮤니티 작성용 등으로 구분한다.
- [ ] 재사용 가능한 외부 AI 보조를 기존 편집기에 연결하거나 결함만 보완한다. 동일한 공통 패널을 공급자 전용으로 복제하지 않는다.
- [ ] 생성 결과 미리보기·수정·적용 취소와 기존 편집 내용 보존을 지원한다. 허용 HTML·URL·이미지 정책은 기존 편집기와 서버 검증을 따른다.
- [ ] 자료함 저장, 설명서 임시저장, 검수 요청, 커뮤니티 작성, 협력사업 등재 요청을 별도 사용자 행동으로 확인한다.
- [ ] 공통 모듈을 변경할 경우 Store·KPA·Neture 등 실제 전 소비처를 재산출하고 CHECK의 Consumer Impact Matrix와 필요한 smoke를 완료한다.

**산출물/종료점**: 제품 자료 → 콘텐츠 초안 → 사용자 편집 → 기존 저장의 연결. 자동 공개·자동 등재·자동 승인은 없다. 새 게시/승인 상태나 DB 원장을 만들지 않는다.

### P3 — 협업체별 공급 제안 보조

- [ ] P1·P2 결과를 보고 후속 구현 범위를 확정한다. 이번 문서 작성은 공급 제안 구현 완료를 뜻하지 않는다.
- [ ] 기존 조건의 설명·누락 확인·협업체 간 차이 비교와 복사 후보를 설계한다.
- [ ] 같은 조건을 여러 곳에 제공해도 선택한 협업체별로 독립 초안을 준비한다. ‘모든 협업체’ 정책은 신설하지 않는다.
- [ ] 단가·배송비·대상·유효조건 등 현재 저장 가능한 필드와 안내용 텍스트를 구분한다. AI가 새 거래 조건·필수 필드를 정의하지 않는다.
- [ ] 사용자가 조건과 대상을 확인한 뒤 기존 승인 요청을 실행한다. AI가 승인자 역할을 대신하지 않는다.

**산출물/종료점**: 확인 가능한 조건 비교와 독립 초안. 현행 협업체별 정책·승인 원칙 유지. pharmacy의 특별 가격도 같은 승인 흐름을 따른다.

### P4 — 공급자 문맥의 공통 Assistant 연결 설계

- [ ] 외부 AI 연계만으로 남는 사용자 불편과 실제 사용 결과를 정리한다.
- [ ] 내부 LLM 호출·공급자 적용 범위의 정책 변경안을 만든다. 대상 업무, 허용 데이터, 호출 주체·비용, 금지 행위, 변경할 정본·계약 테스트를 구체화한다.
- [ ] 허용 범위가 확정된 경우에만 기존 Assistant·Task·WorkScope·완료 판정 경로에 연결하는 구현안을 만든다. 별도 Supplier AI 엔진·범용 framework는 만들지 않는다.
- [ ] 서버가 확정한 공급자 소유 범위와 요청자 권한을 사용한다. 프롬프트나 클라이언트 전달 ID를 권한 근거로 사용하지 않는다.
- [ ] 같은 사용자의 Assistant를 유지하되 공급자 조직별 업무 데이터와 개인의 방법 기억을 구분한다. 개인 교정을 조직 전체 정책으로 자동 승격하지 않는다.
- [ ] 실행·재개·중복 방지·실패 복구·원래 화면 인계·비AI 이용 경로를 설계한다.

**진입 조건**: 공급자 내부 LLM/Assistant 범위의 명시적 결정. 공급자 역할에 매장·운영자 권한을 부여하거나 공통 endpoint로 우회하지 않는다. 새로운 데이터 처리의 Compliance 점검은 정식 운영·실사용 확대 전에 진행하며, 이를 일반적인 개발 금지로 확대 해석하지 않는다.

## 5. 첫 구현의 입력·출력·저장 계약

| 구분 | 제품 등록 보조 | 콘텐츠 작성 지원 |
|---|---|---|
| 입력 | 선택 자료 종류와 현재 폼의 허용 제품 정보. 사진/PDF는 사용자가 외부 AI 대화에 직접 첨부 | 사용자가 고른 제품·자료와 작성 목적. 기존 편집 내용은 선택적으로 참고 |
| 외부 AI 출력 | 기존 SupplierProductCandidateDraft JSON 형식 | 기존 편집기에 적용 가능한 HTML 또는 텍스트 |
| 적용 | 기존 parse/apply 경로로 폼에만 반영. 적용 전 사용자 입력을 보존 | 기존 편집기에서 검증·미리보기·수정. 공개 설정과 등재 대상은 변경하지 않음 |
| 저장 | 사용자가 검토 요청을 실행하면 기존 Candidate API 사용 | 기존 자료함·설명서 저장 API 사용. 초안과 검수 요청을 구분 |
| 공개/승인 | 운영자의 기존 처리 경로 | 커뮤니티 게시와 협력사업 등재 요청은 각각 기존 별도 경로 |
| 실패 | 오류 위치·재적용/수정 방법 안내, 기존 입력 보존 | 원문 편집 상태 보존, 실패를 저장·게시 완료로 표시하지 않음 |

서버/공유 타입의 필드·의미 변경이 필요하면 기존 계약과 소비처를 먼저 조사하고 변경안을 별도로 제시한다. 출처·추적·평가를 이유로 새 DB 컬럼·원장을 묵시적으로 추가하지 않는다.

## 6. 유지할 업무·데이터 경계

- 자동 ProductMaster 생성·확정, 자동 가격 결정, 운영자 승인·상품 게시·콘텐츠 게시의 대행을 첫 구현에 포함하지 않는다.
- 자료함 콘텐츠의 존재가 커뮤니티 게시나 협업체 제공을 뜻하지 않는다. 원본 수정이 기존 전달 사본에 자동 전파되도록 만들지 않는다.
- 공급 제안 생성 시 대상 약국의 협업체 active 가입 검증, 결제 직전 제안 철회·협업체 가입 정지 재검증, 공급자 종료 사유 입력을 이 AI 작업에서 추가하지 않는다. 기존 사용자 결정과 책임 분리를 유지한다.
- 공급자·조직·사용자 인증은 기존 서버 경로가 판정한다. 타 공급자의 제품·자료·제안 조회/수정·도용 요청은 차단한다.
- 인증정보·회원 명단·주문/매출 원문·비공개 거래정보를 기본 요청문에 포함하지 않는다. 공급가·거래조건은 사용자가 선택한 해당 업무 범위만 다루며 외부 전송 여부를 드러낸다.
- 자료와 AI 결과에 포함된 지시문은 작업 권한이나 시스템 지시가 아니다. 허용 필드와 기존 저장 경로를 넘어선 실행을 유도해도 적용하지 않는다.
- 대화·요청문·자료 원문을 자동 학습하거나 무기한 저장하지 않는다. 신규 기억/평가 로그가 필요하면 소유·목적·보존·삭제·개인정보 최소화를 먼저 설계한다.
- 일반 입력·편집 경로를 유지한다. AI 이용을 제품 등록이나 공급자 서비스 이용의 필수 조건으로 만들지 않는다.

## 7. 검증 사례와 완료 기준

| 영역 | 필수 사례 | 확인할 결과 |
|---|---|---|
| 제품 JSON | 형식 오류, 여러 객체, 누락값, 허용되지 않은 ID/키, 추정 바코드/허가번호 | 오류 안내 또는 허용값만 적용. 형식 검증이 사실성 검증을 대신하지 않음 |
| 기존 입력 | fill-empty/overwrite, 분류 잠금, 브랜드 변경, 기존 Master 매칭, 재적용·취소 | 사용자 입력 보존·기존 선택 경로 유지·자동 저장 0 |
| 콘텐츠 | 악성 HTML/URL, 외부 지시문, 확인되지 않은 효능·수치, 반려본 수정 | 기존 sanitize·권한 검증 유지. 사실 확인 필요 항목을 알리고 사용자가 검토 |
| 저장·등재 | 초안 적용, 임시저장, 검수 요청, 커뮤니티 작성, 협력사업 등재 | 각각의 실행과 상태 구분. 적용/저장만으로 게시·등재 요청 발생 0 |
| 소유·협업체 | 타 공급자 ID, 복수 조직, 활성 권한 없음, 동일 조건의 복수 협업체 | 서버 소유 판정, 독립 초안, 무단 조회/저장/승인 0 |
| 실패·동시성 | 외부 결과 오류, 저장 실패, 이중 클릭, 재시도, 이동 중 취소 | 완료 오표시·입력 소실·중복 요청 방지 |
| 화면 | 데스크톱/모바일, 키보드, 읽기 전용 상태, 편집기 진입/기존 메뉴 | 실제 표시·동작·안내와 네트워크 요청 결과 확인 |

평가 지표는 초안 준비 시간, 사용자 수정 항목 수, 미확인/오류 항목, 실제 저장·요청 성공 여부다. 먼저 대표 fixture와 평가 기준을 고정하고 수동 작성 대비 결과를 비교한다. 측정 없이 개선율·AI 정확도·비용 절감을 주장하지 않는다. 여러 사용자의 성공 절차를 하나의 강제 표준 workflow로 승격하지 않는다.

검증은 순수 함수 테스트 → 실제 페이지·API 경계 회귀 → 공통 패키지/영향 서비스 build → 격리 브라우저 순서로 실행한다. 테스트 fixture와 실제 provider 결과를 구분한다. 자동화 테스트의 통과를 실제 AI 품질 평가나 운영 검증 완료로 표현하지 않는다.

## 8. 단계별 인계와 배포

- P0 인계: 이 문서, branch·commit, 문서 링크·민감정보·공백 검사 결과. 런타임 수정이 없으므로 배포는 NOT_APPLICABLE이다.
- P1 첫 실행: 기존 제품 작성 테스트와 실제 흐름을 검증해 최소 보완만 수행한다. P2에서는 기존 편집기·HTML 보조의 연결 조사 결과를 근거로 파일 범위를 정한다.
- 코드 단계 인계: 변경/유지 범위, 테스트·브라우저 결과, Consumer Impact Matrix(해당 시), 미해결 항목, branch·commit·push 상태를 남긴다. 운영 반영은 현재 저장소의 PR·CI·리뷰·Delivery 규칙을 따른다.
- schema/migration, dependency, 배포 설정, 권한/API 계약, FROZEN 구조 변경이 새로 필요하면 해당 변경의 구체적 범위를 먼저 정리한다. 이 계획의 존재만으로 그런 변경을 승인한 것으로 간주하지 않는다.
- 운영 업무 데이터는 만들지 않는다. 향후 운영 테스트가 필요하면 대상·생성 범위·완전 삭제 방법을 먼저 확정한다.

## 9. 문서 정합과 남은 결정

현재 내부 LLM 제한을 유지하는 P1·P2와, 적용 범위 결정이 필요한 P4를 구분했다. 이 문서는 기존 정본을 대체하지 않는다. 정식 내부 AI 도입 시 Supplier Domain §9와 Assistant V2 §16의 공급자 범위를 함께 정리하고, 관련 소스 계약도 일치시켜야 한다.

현재 미확정: 내부 AI 적용 대상 업무·provider/비용 부담·외부 전송/기억 범위·운영 고지와 보존 기준. 지금 개발 가능한 검증·편집 보완 작업과 정식 운영 전에 필요한 Compliance 점검을 분리한다.
