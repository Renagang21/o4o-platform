### 단계 1 조사 핵심 사실 (설계 1-7 의 입력 — 상세 근거는 IR)
- **기본 가입이 없다**: `pharmacy.neture.co.kr` = serviceKey `kpa-society` · role `kpa:*`. 매장 기본 API 전부가 `isStoreOwner(...,'kpa')`(kpa-society active membership + `kpa:store_owner` + 조직 연결)를 요구 → §3-1 "미가입이어도 내 매장" 과 정면 충돌. 자격 확인은 사실상 없음(`license_verified` 쓰는 코드 0).
- **승인 우회**: `POST /api/v1/store/enrollment {serviceKey:'kpa'}` 가 로그인만으로 조직 · `kpa:store_owner` · active membership 생성.
- **약국 1 = 조직 1 미보장**: 프로비저너별 org code 규칙 상이(`kpa-pharm-{bizno}` · `store-{svc}-{uid}` · `ph-pharm-{uid}`), `organizations.business_number` UNIQUE 아님.
- **세미프랜차이즈 개념 없음**: serviceKey 가 그 역할 — 새 키 1개 = 약 15곳 수정. → **세미프랜차이즈는 데이터 행으로** (선례: 분회 `branch_memberships` · 커뮤니티 도메인).
- **단일 제안 강제**: SPO `UNIQUE(master_id, supplier_id)` · OSA/OSP `(offer, service_key)` unique · OPL unique v2 + ON CONFLICT 소비처 9곳. 제품 등록 승인과 공급 승인 미분리(SPO.approval_status 가 OSA 파생).
- **이벤트**: 가격 수정 경로 없음(OK) · **재신청 불가**(중복 검사가 status 무관 409 + DB 인덱스) · visibility 토글이 canceled→approved 되돌림(승인 우회) · 운영 조직 LIMIT 1 임의 선택. 수량 로직(`reserveEventOfferListing` · `incrementListingQuantity` · 취소 복원)은 보존 대상.
- **모집**: 참여 단위가 **사용자**(`allowed_seller_ids`) · 공급가 조건 없음 · 승인 참여자가 실제 주문 못 할 가능성(결함 후보).
- **재고**: B2B 경로는 검사만, 예약은 은퇴한 레거시 createOrder 에만. 배송완료 차감 · 취소 해제는 상태 변경 경로에서 동작(보존).
- **HUB**: web-store 가 약국 내 매장. `/hub/*` 진열 → apply → OPL → `/orderable` 이 주문 전 취급 등록을 강제(§3-9 충돌). `/hub` 전면 삭제 불가(KCos 링크 · spec 고정).
- **커뮤니티**: catalog policy + `community_memberships` 별도 가입 2단계 → §3-8 충돌. middleware 한 곳에서 세미프랜차이즈 가입 상태 직접 판정 가능.
- **공급자 주문 목록**: `COALESCE(o.service_key,'neture') = 'neture'` 필터 확정 — 약국(`kpa-society`) · 이벤트(`kpa-groupbuy`) 주문이 목록 · KPI · 정산에서 누락. 처리 경로는 필터 없어 목록과 불일치.
- **결제 결함 확정**: payment↔group/소유자 대응 미검증(소액 payment 로 고액 group 완료 가능) · 금액 일치 검증 없음 · 단건 경로 PG orderId 불일치 · PAID 재 confirm 409 · handler 중복 방지가 메모리 Set · 실패 후 재결제 영구 차단 · web-store 결제 버튼 미연결. 키 부재 → 가짜 성공은 **반박**(FAILED), 단 테스트 결제 모드 없음. 수취 주체 필드 없음(단일 env 키, 여러 공급자 주문을 group 하나로 결제).

## 1. 작업 목적

현재 개발 대상은 약국을 대상으로 하는 Neture(neture.co.kr) 서비스다. 이번 리팩토링은 다음 구조를 구현한다.

- 약국별 하나의 내 매장
- Neture 기본 가입 · 자격 확인 · 승인
- 세미프랜차이즈별 독립적인 가입 · 승인
- 공급자가 등록한 제품에 대한 복수 공급 제안
- 내 매장에서 승인된 상품 · 이벤트 · 모집 · 콘텐츠 직접 이용
- 세미프랜차이즈 가입 상태에 따른 커뮤니티 접근
- 선택한 공급 제안에 따른 주문 · 결제 · 공급자 주문 처리

비약국 서비스, 업종별 확장 구조, 공통 Core 추출은 범위가 아니다. 코드를 단순하게 만드는 것을 우선하고, 예상되는 미래 기능을 위한 조건문 · 추상화 계층을 추가하지 않는다.

## 2. 실행 방식

1. AGENTS.md 와 현재 정본을 읽고 최신 origin/main 기준으로 시작한다.
2. 기존 조사 결과는 참고하되 현재 코드와 달라진 부분은 다시 확인한다.
3. 아래 단계를 순서대로 진행한다. 단계는 작업 순서이며 단계마다의 승인 게이트가 아니다.
4. 조사만 하고 끝내지 않고 확정 범위의 설계 · 구현 · 검증까지 진행한다.
5. 미확정 사업 판단이 필요한 기능만 보류하고 나머지는 계속한다.
6. 코드 변경과 함께 관련 정본 문서를 구체적인 구현 기준으로 정비한다.
7. 저장소의 현재 통합 · CI/CD 절차를 따른다.
8. 완료하지 않은 항목 · 실제 검증하지 않은 항목을 PASS 로 표시하지 않는다.

## 3. 확정된 설계

### 3-1. 약국 기본 가입과 내 매장
- 약국의 내 매장은 하나다.
- Neture 기본 가입 · 자격 확인 · 운영자 승인 모델을 새로 만든다.
- 기존 kpa-society 가입을 Neture 기본 자격으로 재해석하지 않고, 기존 가입자를 자동 전환하지 않는다.
- 기본 가입과 세미프랜차이즈 가입은 서로 다른 승인이다. 세미프랜차이즈 운영자는 약국 자격을 독립적으로 확인할 수 있다. 기본 승인이 세미프랜차이즈 가입을 자동 승인하지 않는다.
- 내 매장은 세미프랜차이즈 미가입이어도 이용할 수 있다(매장 자체 콘텐츠 · 접근 가능한 커뮤니티 콘텐츠 · 디지털사이니지 · 태블릿 · QR 등).

### 3-2. 세미프랜차이즈
- 세미프랜차이즈마다 가입 신청과 운영자 승인이 필요하다. pharmacy.neture.co.kr 도 같은 절차다(전체 약국이 대상이라는 뜻이지 자동 가입이 아니다).
- 한 약국은 여러 세미프랜차이즈에 가입할 수 있고, 세미프랜차이즈별 가입 상태와 운영 권한을 구분한다.
- 운영자는 자신이 담당하는 세미프랜차이즈의 신청 · 제안만 처리한다.
- 세미프랜차이즈 추가 때마다 serviceKey 와 분기 코드를 여러 곳에 추가하는 방식을 피한다. 도메인 · 앱의 서비스 식별과 세미프랜차이즈 식별을 혼용하지 않는다.

### 3-3. 공급자와 제품 승인
- 공급자 가입 · 제품 등록에 운영자 승인이 필요하다. 공급자 검증은 서류 · 제품 · 공급 가격 중심이며 점수 · 위험 평가 · 거래 감시 시스템을 만들지 않는다.
- A. 공급처를 지정하지 않은 승인 제품 → pharmacy.neture.co.kr 공급 제품으로만 취급, 별도 세미프랜차이즈 공급 승인 없음, pharmacy 가입 승인 약국만 이용 · 주문.
- B. 공급처를 명시한 제안 → 해당 세미프랜차이즈 운영자 승인 필요(pharmacy 를 명시한 차등 가격 · 이벤트 제안도 같음), 승인된 해당 세미프랜차이즈 가입 약국에 제공.
- 기본 제품 등록 승인과 개별 공급 제안 승인을 혼동하지 않는다.

### 3-4. 제품과 공급 제안
- 동일 공급자의 동일 제품에 복수 공급 제안이 가능하다(여러 세미프랜차이즈 · 같은 세미프랜차이즈 복수 · 개별 약국 대상). 개별 약국 대상 제안도 해당 공급 경로의 승인 · 가입 조건을 따른다.
- 일반 조건과 세미프랜차이즈 조건이 동시에 보일 수 있고, 구매자가 선택한 제안으로 주문한다.
- 제품 정보와 공급 조건을 분리한다. 기존 제품 · 공급자 관계 아래에 복수 공급 제안을 둔다(실제 명칭은 현재 코드로 결정). 동일 제품의 설명 · 이미지 · 재고 정보를 반복 생성하지 않는다.
- 만들지 않는 것: 최저가 자동 선택 · 고가 선택 경고 · 제안 간 가격 분쟁 처리 · 구매자 선택 실수 보상/중재.

### 3-5. 이벤트
- 공급 대상: 전체 약국 = pharmacy.neture.co.kr / 특정 세미프랜차이즈 = 해당 세미프랜차이즈. 전체 약국 대상도 pharmacy 운영자 승인과 이용 약국의 pharmacy 가입 승인이 필요하다.
- 이벤트 가격은 수정하지 않는다 — 기존 이벤트를 삭제 · 종료하고 새로 신청한다. 주문이 참조한 이벤트는 주문 기록을 훼손하지 않게 삭제 · 종료한다.
- 동일 제품 · 동일 세미프랜차이즈라는 이유만으로 복수의 승인된 제안을 막지 않는다.

### 3-6. 취급매장 모집
- 운영자가 모집 조건을 승인하고, 공급자가 참여 신청 약국을 승인한다. 승인된 약국은 해당 조건으로 바로 주문할 수 있다.
- 이미 승인된 모집 조건에 운영자 재승인을 반복하지 않는다. 참여 대상은 사용자 개인이 아니라 약국 조직이다.

### 3-7. HUB 와 내 매장
- 별도의 매장 HUB 화면을 두지 않는다. HUB 에 먼저 진열하고 내 매장으로 가져오는 절차를 만들지 않는다. 내 매장에서 이용 권한이 있는 항목을 직접 보여준다.
- 출처별 탭 · 필터는 가능하나 접근 가능 항목을 먼저 판정한 뒤 나눈다. 미가입 · 미승인 · 정지 · 종료된 세미프랜차이즈 전용 항목은 전체 탭 · 검색 · 상세 · 주문 API 에도 노출하지 않는다.
- 공급자용 · 세미프랜차이즈 운영 화면은 유지한다. 없애는 것은 매장 이용자의 별도 HUB 단계다.

### 3-8. 콘텐츠와 커뮤니티
- 내 매장 활용 콘텐츠: 약국 자체 · 이용 권한이 있는 일반 커뮤니티 · 가입한 세미프랜차이즈 · 공급자 제공(이용 권한 있음). 출처와 기존 이용 방식을 유지하고, 상품 취급제품 등록 절차와 콘텐츠 활용 절차를 혼동하지 않는다.
- 세미프랜차이즈 커뮤니티는 기존 커뮤니티 기능에 연결한다 — 가입 승인 = 이용 가능, 정지 · 종료 = 접근 제한, 별도 커뮤니티 가입 신청 없음. 가입 상태를 직접 권한 판정에 쓰고, 커뮤니티 회원 데이터로 복제 · 동기화하지 않는다.
- 일반 커뮤니티의 독립 가입 정책은 유지한다. Neture 운영자 공통 자료를 위한 별도 제공자 유형을 만들지 않는다(운영자가 운영하는 세미프랜차이즈로 제공).

### 3-9. B2B 와 B2C
- 내 매장 운영자가 구매하는 제품 · 공급 조건 = B2B. 소비자에게 보여주는 제품 정보 · 매장 판매 가격 = B2C(가격은 약국이 결정). B2B 공급 가격을 소비자 판매 가격으로 자동 사용하지 않는다.
- 소비자용 제품 정보는 검색으로 이용한다(O4O 등록 제품 · 약국 자체 제품). B2B 주문 전에 내 매장 취급제품 등록을 강제하지 않는다.

## 4. 이전 조사 보고서 대비 수정 사항 (우선 적용)

- **그대로 유지**(삭제 · 휴면 금지, 새 제안 구조에 연결할 때 기존 동작 보존, 강화 · 재설계 없음): 내부 재고 검사 · 배송 완료 시 재고 차감 · 기존 예약/차감/복원 · 이벤트 수량 제한 · 기존 구매 한도 · 이벤트 수량 예약/차감/취소 복원 · 공급자 계좌 정보.

- **삭제 미확정**: 기존 `neture_settlements` 화면 · API, 결제 후 취소 · 환불 — 임의 삭제 · 확대하지 않고, 새 주문 구조와 연결되지 않는 부분의 실제 영향과 잔여 작업을 보고한다.

## 5. 단계별 구현 (요지 — 상세 완료 기준은 TODO 와 사용자 지시 원문 기준)

- **단계 1** 현재 코드 확인 · 구체 설계 정합. 범용 권한 엔진 · 업종 확장 프레임워크를 만들지 않는다. 정본 충돌 절은 데이터 관계 · 권한 조건 · 호출 흐름으로 구체화한다.
- **단계 2** 기본 가입 · 세미프랜차이즈 · 공급자 구조. 완료 기준: 한 약국 복수 세미프랜차이즈 가입 · 타 세미프랜차이즈 신청 처리 차단 · 기본 제품 승인과 개별 제안 승인 구분 · 동일 제품 복수 제안 · 이벤트 가격 수정 경로 없음 · 이벤트 삭제/종료 후 재신청 · 모집 참여 승인 후 주문.
- **단계 3** 내 매장 직접 이용 · 커뮤니티 연결. 메뉴만 숨기지 않고 API 에서 판정. 공급 제안별 공급자 · 공급 경로 · 조건 표시, 가격 비교 권유 · 자동 선택 변경 없음. 완료 기준: HUB 없이 이용 · 전체 탭/상세 API 차단 · 정지/종료 시 커뮤니티 제한 · 별도 커뮤니티 가입 없음 · 미가입도 기본 매장 기능.
- **단계 4** 공급 제안 기반 주문 · 공급자 처리. 완료 기준: 선택 제안 = 주문 가격 · 권한 없는 제안 주문 차단 · 공급자 목록에 약국 주문 표시 · 타 공급자 주문 차단 · 준비/배송/배송 완료 흐름 · 재고/이벤트 한도/취소 복원 보존.
- **단계 5** PG 독립 결제 과정(PG 미선정, 기존 Toss 설정을 최종 구조로 보지 않음). 범용 다중 PG 프레임워크 없음. 테스트 결제와 실제 PG 구분, 키 부재를 실결제 성공으로 처리하지 않음. 서비스 운영자 수취 구조 유지(공급자 즉시 지급 아님) · 수취 주체 식별 · 수취 주체 다른 주문을 한 실제 PG 결제로 합치지 않음. 결제 완료 ≠ 공급자 지급. 자동 정산 · 지급 · 클레임 엔진 없음.
- **단계 6** 통합 검증 · 잔재 정리 · 문서. 다른 서비스 사용 코드는 무조건 제거하지 않는다. 재고 · 이벤트 한도는 제거 대상 아님. 테스트 데이터 보존용 호환 구조를 만들지 않는다.

## 6. 데이터 처리 원칙

현재 제품 · 주문 · 가입자 데이터는 모두 테스트용이다 — 자격 자동 승계 · UUID 보존 · backfill · 옛 주문 읽기 호환 · 과거 제안 무손실 이관을 요구하지 않는다. 필요한 스키마 변경과 테스트 데이터 초기화 범위를 구체적으로 정한다. 다른 서비스 데이터 · 공통 운영 설정은 일괄 삭제하지 않는다. 데이터 보존 불필요와 기존 재고 · 이벤트 기능 유지를 혼동하지 않는다. (운영 DB 삭제 실행은 `CLAUDE.md` DB 경계에 따라 사용자 명시 승인 후.)

## 7. 필수 검증 시나리오

- **가입 · 권한**: 기본 승인 · 세미프랜차이즈 미가입 → 기본 기능 가능, 해당 상품 주문 · 전용 콘텐츠 불가 / pharmacy 가입 승인 → 기본 pharmacy 공급 제품 이용 · 주문 / 특정 세미프랜차이즈 승인 → 해당 제안 · 콘텐츠 · 커뮤니티 / 정지 · 종료 → 전용 조회 · 새 주문 · 커뮤니티 차단(이미 결제한 주문 이행은 별개 — 자동 취소 · 삭제 없음) / 비담당 운영자 → 타 세미프랜차이즈 승인 차단.
- **공급 제안**: 공급처 미지정 제품은 pharmacy 에만 · 명시적 제안은 대상 운영자 승인 전 불가 · 동일 제품 복수 승인 제안 공존 · 이벤트 가격 수정 불가 · 삭제/종료 후 재신청 · 모집 참여 승인 후 즉시 주문.
- **주문 · 결제**: 선택 제안 가격 = 서버 청구 가격 · 권한 없는 제안 주문 차단 · 타 주문 payment 로 확인 차단 · 금액 불일치 차단 · 중복 결제 확인/이벤트 전달 처리 · 결제 완료 주문의 공급자 목록 표시 · 공급자별 접근 제한 · 재고/이벤트 한도/예약/복원 회귀.
