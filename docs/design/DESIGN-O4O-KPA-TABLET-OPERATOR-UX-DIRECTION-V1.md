## 0. 전제 (사용자가 못박은 조건)

- **자동 전환·예약·스케줄 불필요.** 소규모 매장이다. **현장 근무자가 직접 바꾸는 것이 더 낫다.**
- 그래서 이 설계는 "유연한 자동화"가 아니라 **"근무자가 손으로 바꾸는 그 행동을 얼마나 쉽고 명확하게 만드느냐"** 만 다룬다.
- 코드 복잡·사용자 불편은 원치 않는다.

## 1. 진짜 문제 (지금 왜 어수선한가)

근무자가 화면만 보고 **① 우리 매장 코너들이 지금 각각 뭘 보여주는지 한눈에 인식이 안 되고, ② 코너 화면 교체가 바로 되지 않는다.** 조사로 확인한 구조적 원인:

| # | 원인 | 근거 |
|---|------|------|
| A | **코너 현황을 보려면 코너마다 들어가야 함.** 매장 전체를 한 화면에서 훑을 수 없다. | 코너 관리가 코너 선택 → 패널 진입 구조 |
| B | **교체가 2단계(연결 → '이 화면 사용').** "연결", "current" 같은 내부 개념이 근무자에게 노출됨. | `store_tablet_corner_contents`(연결) + `current_screen_set_id`(적용) 분리 |
| C | **"화면 보기"가 4종(고객 화면 열기 / 코너 미리보기 / 현재 화면 보기 / 리스트 미리보기).** 표면만 다른 중복이 섞여 어수선. | IR §3 — '고객 화면 열기 ≈ 코너 미리보기' 실질 중복 |
| D | **지금 뭐가 나오는지 글자로만 표시.** 썸네일(실제 화면 축소)이 없어 즉시 인식 불가. | 카드에 미니 렌더 없음 |
| E | **내부 용어 노출**(Screen Set / template_key / 연결 / current). 근무자 언어가 아님. | 코드 개념이 UI 라벨로 새어나옴 |

> 요약: 지금 UI는 **"콘텐츠(원본)를 만들고 코너에 연결하고 current를 지정한다"는 개발자 모델**을 근무자에게 그대로 보여준다. 근무자 모델은 훨씬 단순하다 — **"이 코너 태블릿, 지금 이거 나오네. 저걸로 바꿔야지."**

## 2. 설계 원칙 (6)

1. **한 화면에서 매장 전체가 보인다.** 코너에 들어가지 않고도 모든 코너의 "지금 화면"을 카드 그리드로 즉시 인식.
2. **교체는 한 동작.** '연결→적용' 2단계를 근무자에겐 **"이 화면으로 바꾸기" 1번**으로 합친다(연결은 시스템이 알아서).
3. **글자보다 그림.** 각 코너 카드에 **실제 화면의 미니 렌더(썸네일)**. 읽지 않아도 뭐가 나오는지 안다.
4. **미리보기는 1종.** 고객이 볼 화면을 그 자리에서 크게. 4종 → 1종.
5. **근무자 언어만.** 코너 / 화면 / 바꾸기 / 미리보기. Screen Set·template_key·연결·current 같은 말은 화면에서 사라진다.
6. **되돌리기 쉬움.** 방금 바꿨다 아니다 싶으면 이전 화면으로 한 번에.

## 3. 핵심 재구성 — 화면 2개면 충분하다

지금 여러 탭·패널·미리보기로 흩어진 것을 **사용 빈도로 딱 둘**로 가른다.

| 화면 | 언제 | 무엇 |
|------|------|------|
| **① 매장 코너 현황판** (매일) | 손님 응대 중 수시 | 모든 코너를 한눈에 + 화면 바꾸기 + 미리보기 |
| **② 화면 만들기** (가끔) | 콘텐츠 준비할 때만 | 새 화면 제작·편집(기존 콘텐츠 라이브러리) — 일상 조작과 분리해 어수선함 제거 |

일상은 **①에서 100% 끝난다.** ②는 셋업할 때만 들어가는 뒷방.

## 4. ① 매장 코너 현황판 (핵심)

```
┌─ 매장 코너 현황판 ─────────────────────────────  [화면 만들기] ─┐
│  우리 매장 태블릿 5개                                          │
│                                                                │
│ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐         │
│ │ ▏미니 실화면▕  │ │ ▏미니 실화면▕  │ │ ▏미니 실화면▕  │         │
│ │               │ │               │ │               │         │
│ │ 피부관리 코너  │ │ 구강관리 코너  │ │ 건기식 코너    │         │
│ │ 지금: 여름 안내│ │ 지금: 기본 안내│ │ 지금: 홍삼 소개│         │
│ │ [화면 바꾸기] │ │ [화면 바꾸기] │ │ [화면 바꾸기] │         │
│ │ [미리보기]    │ │ [미리보기]    │ │ [미리보기]    │         │
│ └───────────────┘ └───────────────┘ └───────────────┘         │
└────────────────────────────────────────────────────────────────┘
```

- **카드 = 코너 1개.** 미니 실화면(축소 렌더) + 코너 이름 + "지금: ○○" + 버튼 2개뿐.
- **미니 실화면**은 새 엔진이 아니라 **기존 미리보기 컴포넌트를 작게 축소**한 것(추가 개발 최소). 이게 "한눈에 인식"의 핵심.
- 코너가 많은 매장은 카드가 늘어날 뿐 구조 동일. 필요 시 이름/위치로 정렬(스키마 변경 없이 `location` 텍스트 활용).
- **드릴다운 없이** 여기서 다 보인다 → 원인 A 해소.

## 5. "화면 바꾸기" — 한 동작

카드의 [화면 바꾸기] → 그 코너에 준비된 화면들이 **썸네일 카드**로 뜨는 시트:

```
┌─ 피부관리 코너 · 화면 바꾸기 ───────────────────  ✕ ─┐
│ 지금 나오는 화면:  ▣ 여름 안내                        │
│ ─────────────────────────────────────────────────── │
│ ┌────────┐ ┌────────┐ ┌────────┐                     │
│ │ ▏썸네일▕│ │ ▏썸네일▕│ │ ▏썸네일▕│                    │
│ │ 여름 안내│ │ 기본 안내│ │ 감사 이벤트│                  │
│ │ ● 지금  │ │[이걸로] │ │[이걸로] │                     │
│ └────────┘ └────────┘ └────────┘                     │
│ [＋ 다른 화면 골라 넣기]                               │
└──────────────────────────────────────────────────────┘
```

- **[이걸로] 한 번 = 교체 완료.** 근무자에겐 1동작. (내부적으로 기존 API 2개 — 연결 보장 + current 전환 — 를 프론트가 순차 호출. 스키마 변경 0.)
- "다른 화면 골라 넣기"로 라이브러리의 화면을 이 코너에 추가 → 원인 B(2단계·용어) 해소.
- 교체 후 카드 미니 렌더 즉시 갱신 + "피부관리 코너 화면을 '기본 안내'로 바꿨어요" 토스트 + **[되돌리기]**(원칙 6).

## 6. 미리보기 1종 (4→1)

- 카드의 [미리보기] = **고객이 볼 실제 화면을 그 자리에서 크게**(인페이지 오버레이). 상품·이미지·QR까지 실제와 동일.
- "고객 화면 열기(새 탭)"는 **실제 매장 태블릿 URL로 열기** 용도로만 1개 남긴다(현장에서 진짜 태블릿에 띄울 때).
- "현재 화면 보기 / 리스트 미리보기"는 위 미리보기로 흡수 → 원인 C 해소.

## 7. 곁다리로 같이 정리되는 것 (IR 연계)

일상 조작을 위 구조로 바꾸면 IR에서 지적한 것들이 자연스럽게 정리된다:

- **이미지**: 미니 렌더/썸네일이 실제 이미지를 그대로 보여주므로, 상품 이미지가 placeholder면 근무자가 **보는 즉시 인지**한다. 실사진 교체는 상품 관리에서 `thumbnail_url` 한 필드(IR §9). (가글 이미지 `%0A` 깨짐은 별도 데이터 수정.)
- **QR 상품 불일치**(태블릿 vs QR 모바일 상품 수 다름, IR §7): 미리보기가 1종·실렌더면 근무자가 차이를 눈으로 발견 → 후속 정합 WO의 근거가 명확.

## 8. 하지 말 것 (anti-patterns)

- ❌ **자동 전환·예약·시간대·계절 스케줄러** — 사용자가 명시적으로 거부. 현장 수동이 기본.
- ❌ 코너에 들어가야만 현황이 보이는 drill-down.
- ❌ '연결 → 적용' 2단계, current/Screen Set 용어 노출.
- ❌ 미리보기 4종 병존.
- ❌ 빈 화면·데드 상태(항상 이전/기본 화면으로 fallback).

## 9. 복잡도·불편 최소화 (근무자 체크리스트)

| 기준 | 목표 |
|------|------|
| 코너 화면 교체까지 클릭 | **3번 이내** (현황판 → 화면 바꾸기 → 이걸로) |
| 전문용어 노출 | **0** |
| "지금 뭐 나오나" 인식 | 글 안 읽고 **썸네일로** |
| 실수 복구 | **되돌리기 1번** |
| 신규 테이블/스키마 변경 | **Phase 1은 0** (아래) |

## 10. 단계적 도입 (코드 복잡 회피)

- **Phase 1 — UI 재배치만, 스키마 0.** 현황판 카드 그리드 + 미니 렌더(기존 미리보기 축소) + '화면 바꾸기 1동작'(기존 API 2콜 순차) + 미리보기 1종 + 용어 순화. **신규 테이블 없음.** 대부분의 체감 개선이 여기서 나온다.
- **Phase 2 — 선택.** 미니 렌더 성능(썸네일 캐시), 코너 많을 때 위치별 정렬/그룹. 필요할 때만.

> 자동화가 빠졌으므로 백엔드 신규 개발이 거의 없다. 핵심은 **"이미 있는 데이터(코너·current·미리보기)를 근무자가 한눈에 보고 한 번에 바꾸도록 재배치"** 하는 프론트 작업이다.

## 11. 후속 WO 제안 (원인별)

1. **WO-…-TABLET-CORNER-BOARD-V1** — 매장 코너 현황판(카드+미니 렌더+2버튼), '화면 만들기'와 분리. (원인 A·D)
2. **WO-…-TABLET-ONE-TAP-SWAP-V1** — '화면 바꾸기' 1동작화(연결+적용 합침) + 되돌리기 + 용어 순화. (원인 B·E)
3. **WO-…-TABLET-PREVIEW-UNIFY-V1** — 미리보기 1종(인페이지) + '실제 태블릿에서 열기' 1개만 존치. (원인 C)

*설계 중심 = 자동화 아님, 현장 근무자의 수동 조작을 "한눈에 인식 + 한 번에 교체"로. 화면 2개(코너 현황판 / 화면 만들기)로 축소. 카드 미니 실화면으로 인식, [이걸로] 1동작 교체, 미리보기 1종, 근무자 언어만. Phase 1 스키마 변경 0. IR-...-AUDIT-V1의 이미지·QR·미리보기 지적과 연계.*
