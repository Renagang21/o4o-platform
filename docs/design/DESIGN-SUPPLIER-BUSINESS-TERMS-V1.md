## 승인된 사용자 결정과 적용 범위

협업체별 제안은 각각 독립한다. ‘모든 협업체’ 정책은 없다. 기존 조건을 복사해도 별개 요청·심사·변경·종료로 관리한다. pharmacy 기본 공급은 유지하고 특별가격은 기존 `supply_proposals` 승인 절차를 따른다.

이 문서는 [약국 commerce 설계](DESIGN-NETURE-PHARMACY-STORE-COMMERCE-V1.md) §3-4의 공급 제안에 대한 이번 작업 기준을 보완한다. [B2B 주문 정본](../baseline/O4O-B2B-SUPPLIER-TO-STORE-ORDER-CONTRACT-V1.md)의 payment-first·단일 주문 생성·수취 주체 경계는 유지한다.

## 조건과 변경

`terms_snapshot`은 `{version:1,baseShippingFee,freeShippingThreshold,minOrderAmount}`를 갖는다. 단위는 원이며 기본 배송비·최소 주문금액은 0 이상, 무료배송 기준은 양수 또는 null(기준 없음)이다. 최소 주문금액은 배송비를 제외한 동일 협업체·동일 조건 그룹의 상품 합계 기준이다. 미달 시 해당 그룹의 주문을 만들지 않는다.

새 화면은 배송비를 명시 입력하고 나머지 기준을 정한 뒤 요청한다. 기존 API 호출자가 조건을 생략하면 **요청 당시** 공급자의 배송비·무료배송 기준을 복사하고 최소금액 0으로 저장한다. 이후 공급자 공통 설정 변경은 새 제안의 조건에 전파되지 않는다. 요청한 조건은 제출·승인 후 수정하지 않고, 조건 변경은 기존 제안 종료 후 새 요청·승인으로 처리한다. 다른 협업체 조건은 바꾸지 않는다.

기존 제안은 snapshot NULL로 둔다. 과거 승인 당시 조건을 알 수 없으므로 현재값으로 backfill하지 않는다. 이 제안들은 종전 공통 배송정책을 유지하며, 고정 조건이 필요하면 종료 후 새 제안을 요청한다. 화면에서 기존 방식과 고정 조건을 구분한다.

## 승인과 종료 이력

운영자 승인 시 요청자 본인 또는 canonical Supplier resolver가 해당 공급자의 공급 업무 권한으로 판정한 사용자는 자기 제안을 승인할 수 없다. 현재 owner 관계를 우선하며, legacy pointer는 정본 resolver의 관측 가능한 fallback만 사용한다. 종료·반려 권한은 기존 담당 사업 경계를 유지한다.

`decided_by/decided_at/reason`은 승인·반려 결정만 기록한다. 종료는 `ended_by/ended_at/end_reason`에 별도로 기록한다. 기존 종료 기록을 추정 복원하거나 과거 운영 데이터를 수정하지 않는다. 이전에 승인·종료가 같은 필드에 기록돼 구분할 수 없는 행은 화면에서도 이전 처리 기록으로 표시한다. 공급자 종료도 actor를 기록한다.

## 주문 적용

새 snapshot 제안은 `(수취 주체,공급자,협업체,배송비/무료배송/최소금액 조건)`별로 묶어 각 승인 조건을 적용한다. 조건이 같은 동일 협업체 제안은 상품 합계를 공유할 수 있다. 기존 snapshot 없는 경로의 그룹 방식은 보존한다. paymentGroupId는 계속 수취 주체별이며 별도 결제 원장을 만들지 않는다.

주문 item metadata에 제안 조건을 보존하고 기존 배송비 snapshot 계산을 재사용한다. 결제는 이미 생성된 주문 금액을 이용한다. 결제 직전 제안·사업 가입 재검사를 신설하지 않는다.

## 협업체 책임

제안 생성 시 특정 약국의 협업체 active 가입 검사를 추가하지 않는다. 해당 약국이 대상에 맞는지는 협업체가 판단한다. 기존 약국 조직 존재 검사와 현재 노출·주문 접근 검사는 유지한다. 미결제 주문에 대한 제안 종료·가입 정지의 거래 처리는 협업체 책임이다.
