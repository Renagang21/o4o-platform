## 0. 이 문서가 답하는 질문

> 매장 경영자가 "태블릿 관리 / QR 관리 / POP 관리"를 각각 따로 볼 것인가,
> 아니면 **"혈당관리 코너에서 지금 무엇이 실행되고 있는가"** 를 중심으로 운영할 것인가?

**답: 둘 다 둔다.** 제작/자산 화면은 그대로 두고, 그 위에 **코너 축 운영 계층**을 새로 얹는다.

다만 조사 결과 한 가지를 먼저 정정해야 한다.

> **코너 축 화면을 막고 있는 것은 "코너 이름을 어디 저장하느냐"가 아니다.**
> 실행 표면 4개 중 **POP·Signage 에는 배치 축 자체가 없고**,
> 프로덕션 데이터도 각각 **0행 / 재생로그 0행**이다.
> 지금 Corner entity 를 만들면 **붙을 표면이 2개뿐인 빈 화면**이 된다.

그래서 이 설계는 **코너 축을 목표로 확정하되, 도달 순서를 바꾼다.**

## 1. 최상위 모델 (§1 확정)

```text
Product / Content          무엇을 알리는가        (기존 정본)
        ↓
Execution Asset            무엇으로 만들었는가     Tablet Screen Set · QR · POP · Signage
        ↓
Placement                  어디에서 사용 중인가    ← 표면마다 있어야 하는 축
        ↓
Corner / Surface           그 위치의 이름          물리 매대 · 디지털 표면
```

### 1-1. 계층별 현재 충족도 (실측)

| 계층 | Tablet | QR | POP | Signage | ESL |
|---|:---:|:---:|:---:|:---:|:---:|
| Execution Asset | ✅ | ✅ | ✅(0행) | ✅ | ❌ |
| **Placement** | △ 자유문자열·이력없음 | ✅ **원장** | ❌ | ❌ | ❌ |
| Corner | ≡ 태블릿 1대 | `corner_ref` 훅(미사용) | ❌ | ❌ | ❌ |
| 사용 측정 | ❌ 로그 없음 | ✅ 112행 | ❌ | △ 0행 | ❌ |

**QR 만 4계층을 전부 갖췄다.** 이 회차의 설계 기준은 QR 이다 — 새 모델을 발명하지 않는다.

### 1-2. 불변식

1. **"만들었다" ≠ "쓰고 있다".** 제작·게시 상태(`published`)를 배치 상태로 읽지 않는다.
2. **배치 종료가 자산을 죽이지 않는다.** (QR 회차 계약 계승 — 매대에서 떼도 인쇄물은 열린다)
3. **측정할 수 없는 것을 숫자로 만들지 않는다.** 로그 없는 표면에 노출 수치를 지어내지 않는다.
4. **코너는 관측 후 승격한다.** 자유 표기 → 분포 관측 → 정규화 (QR `placement` 에서 검증된 순서).

## 2. Corner / Location 모델 판정 (§2 확정)

### 2-1. 판정

| 질문 | 판정 |
|---|---|
| 독립 Store Corner entity 가 있는가 | **없다** |
| 문자열 `location` 으로 충분한가 | **불충분** — 한 컬럼에 관례 3종(`구강관리 코너` / `A-2` / `x`)이 섞여 join 이 **조용히** 실패 |
| 신규 entity 가 필요한가 | **결국 필요하다. 단, 지금은 아니다** |

### 2-2. 왜 지금이 아닌가

```text
지금 Corner entity 생성  →  참조 표면 2개(Tablet·QR) · POP/Signage 칸은 영구 "없음"
                        →  빈 코너 카드를 매장에 보여주게 된다
배치 축을 먼저 채움      →  코너 이름이 실제 데이터에서 드러난 뒤 승격
```

### 2-3. 승격 경로 (지금 만들지 않고 예약만 한다)

```text
1단계  Tablet.location · QR.placement 를 그대로 두고 운영 화면을 세운다
2단계  화면에서 매장이 실제로 쓰는 코너 표기를 관측한다
3단계  Store Corner entity 신설 → store_qr_placements.corner_ref (현재 0행 미사용) 가 참조
4단계  store_tablets.location 을 corner 참조로 승격 (자유문자열은 표시용으로 잔존)
```

`corner_ref` 는 QR 회차에서 **이 목적으로 비워 둔 훅**이다. 새 컬럼을 또 만들지 않는다.

**이번 회차 schema 변경: 0건.**

## 3. 제작 화면 vs 운영 화면 (§4 확정)

**둘을 합치지 않는다.** 질문이 다르기 때문이다.

| | 제작(A) | 운영(B) |
|---|---|---|
| 질문 | 무엇을 만들까 | 지금 어디서 무엇이 돌고 있나 |
| 단위 | 자산 종류 | **코너 / 위치** |
| 진입 | 태블릿·QR·POP·사이니지 각 화면 | 매장 실행 관리 홈 |
| 주 동작 | 만들기·편집·게시 | **배치·교체·종료·상태 확인** |
| 편집기 | **여기에만 있다** | 없음 (제작 화면으로 이동) |

운영 화면은 **편집기를 갖지 않는다.** 편집이 필요하면 제작 화면으로 보낸다.
이 경계가 무너지면 두 화면이 같은 것의 사본이 된다.

## 4. 기존 `StoreChannelsView` 와의 관계 (필수 — 미정의 시 중복 발생)

조사에서 **이미 운영 성격 화면이 존재**함을 확인했다(IR §4-1).

```text
StoreChannelsView   축 = 채널(매체 종류)  ·  상태 = 승인/활성/정지  ·  "태블릿 채널이 살아 있나"
실행 관리 홈(신규)   축 = 코너(물리 위치)  ·  상태 = 배치 여부      ·  "혈당관리 코너에 뭐가 있나"
```

**판정: 대체하지 않고 축을 분담한다.**

- `StoreChannelsView` = **채널 개설·승인 축**(매장 ↔ 플랫폼 계약 상태). 유지.
- 실행 관리 홈 = **매장 내부 배치 축**. 신설.
- 두 화면은 **서로 링크**한다. 실행 관리 홈의 표면 카드에서 채널 상태가 비정상이면
  채널 화면으로 보낸다.
- **채널 화면에 코너 개념을 넣지 않는다. 실행 홈에 승인 상태를 복제하지 않는다.**

마케팅 분석(`StoreMarketingAnalyticsView`)도 **매체 축을 이미 갖고 있으므로**,
코너 축 분석은 **같은 스캔 모집단을 다르게 자른 것**임을 화면에 명시한다(§8).

## 5. 매장 실행 관리 홈 IA (§3 확정)

### 5-1. v1 화면 (표면 2개만 — 정직한 범위)

```text
매장 실행 관리                                   [기간: 최근 7일 ▾]

┌ 혈당관리 코너 ────────────────────────────────┐
│ 태블릿   혈당관리 화면          정상          │
│ QR       2개 사용 중            스캔 143      │
│ POP      —  (배치 기록 없음)                  │
│ 사이니지 —  (설치 정보 없음)                  │
│                                      [관리]   │
└───────────────────────────────────────────────┘

┌ 상담 테이블 ──────────────────────────────────┐
│ QR       상담 안내              스캔 12       │
│ 태블릿   없음                                 │
│                                      [관리]   │
└───────────────────────────────────────────────┘

┌ 위치 미지정 ──────────────────────────────────┐   ← 숨기지 않는다
│ QR 89개 · 태블릿 1대                          │
│ 배치를 등록하면 코너별로 볼 수 있습니다 [등록] │
└───────────────────────────────────────────────┘
```

### 5-2. `위치 미지정` 카드는 필수다

QR 91개 중 배치가 등록된 것은 **4개뿐**이고 backfill 은 하지 않았다.
도입 직후 대부분이 여기 모이는 것이 **정상**이다.
이 카드를 숨기면 매장은 "코너가 2개뿐인 매장"으로 오해한다.

### 5-3. POP · Signage 행 처리

원장이 0행이고 배치 축이 없으므로 **행은 두되 값은 `—` 로 둔다.**

- 있는 척하지 않는다 (거짓 UI 금지)
- 없는 척도 하지 않는다 (나중에 붙을 자리를 미리 보여줘 IA 가 흔들리지 않게)

## 6. 표면별 연결 계약 (§5·§6·§7·§8·§9)

### 6-1. Tablet (§5)

기존 canonical 유지. 운영 화면은 **읽기 + 교체만**.

```text
표시   설치 코너(location) · 현재 화면 세트 · 실행 상태
동작   화면 열기 · 화면 바꾸기          ← TabletCornerBoard 가 이미 제공
금지   화면 세트 편집 (제작 화면으로)
```

`TabletCornerBoard` 는 **이미 코너 카드 UI 다**(카드 제목 = 설치 코너).
실행 관리 홈은 이것을 **재사용**한다. 새 태블릿 카드를 만들지 않는다.

### 6-2. QR (§6)

```text
표시   사용처(placement) · target · 활성 배치 수 · 스캔
동작   배치 추가/이동/종료 · 같은 콘텐츠로 QR 추가
```

`StoreQrPlacementPanel` · `StoreQrPlacementAnalyticsPanel` 을 **그대로 재사용**한다.
활성 배치 2개 이상이면 **"위치 구분 불가" 고지를 실행 홈에서도 유지**한다.

### 6-3. POP (§7)

**조사 결과 배치 축이 없다.** `status(draft|published|archived)` 는 게시 축이다.

> 판정: **"출력됨 ≠ 매장에서 사용 중" 원칙은 POP 에 적용 가능하다.
> 단 적용하려면 QR 과 동일한 배치 원장이 필요하다.**

이번 회차에서 만들지 않는다. 프로덕션 0행이라 **수요 근거가 없다**(IR §7 미결).

### 6-4. Signage (§8)

**기기·설치 위치 entity 가 아예 없다.** `signage_displays`/`players` 미존재.
`signage_playlists` 는 매장에만 묶이고 재생은 플레이어 URL 로 한다.

> 판정: **"대기공간 TV" 를 표현하려면 설치 표면 entity 가 필요하다.**
> Tablet 의 코너 모델과 **개념이 같다**(1 기기 = 1 설치 위치).
> 따라서 **Signage 전용 location 모델을 따로 만들지 않는다** — 승격 시 Corner 를 공유한다.

**중복 location 모델 생성 금지**(WO §8) 를 이렇게 지킨다.

### 6-5. ESL (§9)

코드·스키마에 **존재하지 않는다**(조사 대상 없음).

```text
향후:  ESL device → product/content → QR → placement
```

가 같은 화면에 들어올 수 있도록 **표면 카드 구조를 매체 중립으로만** 설계한다.
**제조사별 API/필드는 canonical 모델에 넣지 않는다.**

## 7. 상태 모델 (§10 확정)

**공통 enum 을 강제로 만들지 않는다.** 매체별 의미가 다르다.

### 7-1. 사용자에게 보이는 상위 상태 4개

| 표시 | 의미 | Tablet | QR | POP·Signage |
|---|---|---|---|---|
| **정상** | 배치돼 있고 동작 중 | 화면 세트 연결 + 활성 | 활성 배치 ≥1 + `is_active` | (해당 없음) |
| **미설정** | 만들었지만 배치 안 됨 | location 없음 | 활성 배치 0 | 원장만 존재 |
| **중지** | 의도적으로 내림 | 태블릿 비활성 | `is_active=false` | archived |
| **확인 필요** | 모순 상태 | 세트 없음/보관됨 | 활성 배치 ≥2(위치 구분 불가) | — |

### 7-2. 규칙

- **원장 상태를 그대로 노출하지 않는다.** 위 4개로 접어서 보여준다.
- **`확인 필요` 를 조용히 `정상` 으로 접지 않는다.** QR 다중 배치가 대표 사례다.
- 공통 enum(`CONFIGURED/ACTIVE/...`)은 **표면 3개 이상이 배치 축을 가진 뒤** 재검토한다.

## 8. Analytics (§11 확정)

### 8-1. v1 에서 보여줄 수 있는 것

| 지표 | 가능 여부 | 근거 |

> **v1 의 코너 지표는 QR 스캔 하나다.** 나머지는 `—` 로 둔다.
> 로그 없는 표면에 추정 노출수를 붙이면 매장은 그 숫자로 매대를 옮긴다.

### 8-2. 기존 마케팅 분석과의 정합

같은 스캔 모집단을 **매체 축 / 코너 축**으로 다르게 자른 것임을 화면에 명시한다.
두 화면의 총합은 같아야 하며, 다르면 그것이 결함이다.

### 8-3. 경계

**개인 소비자 추적은 하지 않는다.** 집계는 코너·표면 단위까지만 내려간다
(`O4O-STORE-COMMERCE-BOUNDARY-V1` — 태블릿·QR = 정보 제공).

## 9. KPA / PharmacyHub parity (§12 — 전제 정정)

### 9-1. 정정

WO §12 는 "KPA / PH 차이 = 없음"을 전제했으나 **메뉴 축에서는 이미 사실이 아니다**(IR §3-1).

| 표면 | KPA | PH | K-Cos |
|---|---|---|---|
| QR·POP | `[약국 경영지원]` | `[매장 실행]` | `[매장 활성화]` |
| Tablet | `[약국 경영지원]` | `[매장 실행]` | `[채널]` |
| Signage | 독립 그룹 | `[매장 실행]` | 독립 그룹 |

**서비스 3개 → 그룹핑 3종.** 이번 작업은 parity 유지가 아니라 **parity 회복**이다.

### 9-2. 계약

- 실행 관리 홈은 **공통 Core 1벌**로만 만든다. 서비스 조건문 0.
- KPA/PH 는 endpoint · accent · 라벨만 주입한다 (QR 회차에서 검증된 패턴).
- **둘 중 하나만 먼저 만들지 않는다.**
- K-Cosmetics 는 이번에도 **채택 대상이 아니다**(회귀 확인만).

## 10. 기존 메뉴 영향 (§13 판정 — 이번에 변경하지 않음)

### 10-1. 판정: 새 상위 메뉴가 맞다. 단 별도 회차에서.

근거:

1. 현재 4개 표면이 **3개 그룹에 흩어져** 있어 어느 기존 그룹에 넣어도 나머지가 남는다.
2. PH 가 이미 `[매장 실행]` 을 만들어 **어휘와 수요가 실증**됐다.
3. 셸·메뉴가 **`storeMenuConfig.ts` 한 곳**이라 3서비스 동시 정렬이 가능하다(IR §3-3).

### 10-2. 권장 형태 (구현 회차에서 적용)

```text
[매장 실행]              ← 신설(운영 축)
   매장 실행 관리        ← 신규 홈 (코너 축)
   태블릿 · QR · POP · 사이니지    ← 기존 제작 화면을 이 그룹으로 이동
```

- 기존 화면은 **이동만 하고 기능을 바꾸지 않는다.**
- 데드링크 0 / 실기능 은폐 0 (`O4O-STORE-MENU-CANONICAL-TREE-V1` 원칙).
- **이번 회차에서는 메뉴를 건드리지 않는다**(WO §16).
