## 1. 진입과 범위

관리자 → O4O 상품 DB → 데이터 정비 → 상품 보정 작업 공간의 **설명서 갱신 · 대량 점검 · 예약·알림** 영역이다. 조회와 쓰기는 모두 기존 `platform:super_admin`만 가능하다. 현황 열기는 실행·예약·상품 수정을 시작하지 않는다.

P2·우선순위 4~6번·일반 편집 연결은 PR #816으로 함께 main에 병합됐다. 배포 target a81448f0b1의 [Promote](https://github.com/Renagang21/o4o-platform/actions/runs/40192579965)가 API·관리자·관련 웹 5개 배포와 serving 검증을 완료했다. 과거 닫힌 PR #807과 구분한다.

## 2. 상품 보정 반영과 설명서 갱신 작업 연결

- P2의 선택 반영 transaction에서 해당 상품의 현재 canonical 유형·언어별 갱신 검토 작업을 만든다. 선택 반영한 유형·언어에 설명서가 없다면 그 조합도 작업으로 남긴다.
- 실제 반영한 필드, 원본 상품명, 원인 변경안·상품 작업, 대상 설명서 ID를 보존한다. 제안만 하고 반영하지 않은 상품명은 갱신 작업의 상품명으로 사용하지 않는다.
- 갱신 작업 저장에 실패하면 상품 반영도 함께 rollback한다. 같은 반영 재전송은 갱신 작업을 중복 생성하지 않는다.
- 각 작업의 전문인/AI 지원/소비자 QR 목적은 원인 작업의 제안값이다. 관리자가 실제 사용 목적을 선택하고 검토 메모를 남겨 대기/검토 중/검토 종료/대상 제외로 관리한다. 유형과 이용 목적은 별개다.
- 최신 상품·설명서를 확인한 fingerprint와 작업 revision을 저장 시 비교한다. 변경되면 입력을 보존하고 최신 자료를 다시 확인한다. 상품·설명서 편집 화면은 별도로 열린다.
- **검토 종료는 설명서 게시·수정·QR 갱신 완료가 아니다.** 변경이 필요하면 기존 편집 또는 P2 변경안 절차로 처리한다. 이전 검토 버전은 저장 이력에서 확인한다.
- 자동 연결은 P2 반영과 후속 구현의 일반 상품 수정·관리자 설명서 직접 저장을 지원한다. [기존 편집 연결 안내](O4O-PRODUCT-EDIT-RENEWAL-LINK-V1.md)의 명시한 경로를 따르며 공급자 제출·별도 검수·외부 수집·직접 SQL의 전체 변경 감지는 포함하지 않는다. 기존 상품의 과거 변경을 소급하여 일괄 보정하지 않는다.
- 기존 QR 설명서의 공식 지식 기반 채택 보류와 공용 자산/매장 제작물 분리를 유지한다. QR·매장 제작물은 자동 수정하지 않는다.

## 3. 관리 현황과 화면 내 알림

**정기 관리 현황 불러오기·새로고침**으로 갱신 대기, 근거 대기 작업기록, 변경안 검토 대기·검토 후 미반영·반영 오류 이력, 대량 점검 진행·중지·실패, 예약 도래·지연, 미확인 알림을 확인한다. 집계 단위는 작업·변경안·실행·예약 기록이며 상품 전체 품질 점수나 중복 제거 상품 수가 아니다. 조건은 겹칠 수 있다.

저장이 성공한 뒤 현황 조회만 실패하면 저장 완료와 조회 실패를 나누어 안내한다. 저장된 실행·예약 revision을 유지하며 같은 작업을 다시 생성하지 말고 현황을 새로고침한다.

최근 성공 조회 시각과 마지막 서버 tick을 표시한다. 조회 실패를 0건·완료로 바꾸지 않는다. 이전에 표시한 현황은 조회 시각과 함께 유지하며 다시 조회한다. 새로고침은 입력 중인 갱신 메모를 덮어쓰지 않는다. **최신 갱신 자료 다시 불러오기**는 명시적으로 원문·저장 기록을 다시 여는 동작이다.

알림은 점검 완료·실패·예약 지연/시작 실패·상품 반영 후 갱신 필요를 보관한다. 미처리 업무가 있으면 한국시간 하루 한 번 묶음 알림을 추가한다. 알림 확인은 알림의 확인 시각·관리자를 기록할 뿐 실제 작업을 완료하지 않는다. 이메일·Slack 등 외부 발송은 없다.

## 4. 고정 모집단과 대량 점검

1. 저장한 기준과 검색어로 **대량 후보 점검 만들기**를 실행한다. 생성 시 기준 snapshot과 후보 UUID 모집단을 고정한다.
2. 한 실행 최대 50,000개다. 초과하면 전체 생성을 거부한다. 상품군·검색 조건으로 나누며 몰래 자른 결과를 전수 점검으로 표시하지 않는다.
3. 서버 worker 또는 **다음 25개 점검**이 25개 단위로 처리한다. UUID cursor를 저장하므로 상품명 정렬 변화에 따른 페이지 누락·중복을 피한다. 최초 생성 후 추가된 상품은 다음 실행에서 점검한다.
4. 각 페이지는 처리 시점의 기준 조건·최신 원문으로 다시 확인한다. 조건을 벗어나거나 사라진 최초 후보는 조건 이탈 수로 기록한다. 후보 유지·이탈 합계는 처리한 최초 후보 수다.
5. 페이지별 기준·검색·후보 원문·실행 기록을 기존 runs 형식으로 보존한다. 결과 페이지에서 상품을 선택해 기존 작업 묶음 생성·재사용 흐름으로 연결한다. 화면의 선택은 현재 결과 페이지 단위다.
6. 기준이 변경돼도 과거 실행은 당시 기준을 유지한다. 최신 기준과 다름을 표시하고, 기존 작업 생성의 기준·원문 검사를 유지하므로 오래된 결과로 최신 기준 작업을 만들지 않는다.

**후보 점검 완료 ≠ 사람의 검토 완료 ≠ 상품 반영 완료**다. 자동 상품 수정·AI 판단을 실행하지 않는다. 전체 50,000개 처리의 운영 부하 검증까지 완료했다고 해석하지 않는다. 합성 검증은 상한 거부와 소규모 분할·동시 처리·복구 동작을 확인했다.

## 5. 중단·재개·실패

페이지별 transaction에서 실행 행 잠금/SKIP LOCKED로 다중 worker의 동일 cursor 처리를 방지한다. 페이지 선점 전 snapshot 충돌은 다음 tick으로 미루며 실제 처리 실패 횟수로 계산하지 않는다. 결과·cursor·완료 알림을 함께 저장하며 실패한 페이지는 전부 rollback한다. 중지·재개·취소는 revision을 검사하고 처리자·시각·cursor를 기록한다.

일시 중지한 실행은 자동 재개하지 않는다. 취소는 남은 점검만 중단하며 기존 결과를 보존한다. 완료·취소한 실행은 새 실행으로 다시 시작한다. 실행 도중의 제어는 처리 중 페이지가 끝난 뒤 적용될 수 있다.

실패 시 같은 cursor에서 최대 3회의 연속 시도(최초 실패 포함)를 허용한다. 첫 두 실패는 1분/2분 후 재시도 대기, 세 번째 실패는 자동 처리를 중단한다. 관리자는 원인을 확인하고 **실행 재개·재시도**로 시도 수를 초기화하거나 취소한다. 복구 중 늦은 실패가 다른 관리자의 제어를 덮어쓰지 않는다.

## 6. 한국시간 예약과 worker

기준별 예약은 기본 꺼짐이다. 관리자가 예약 사용, 간격(1~365일), 미래 최초·다음 예정 시각을 저장한다. 화면 입력·표시는 **Asia/Seoul**이며 API 저장은 UTC다. 기본 간격은 해당 기준 검토 주기를 제안하지만 실제 예약 간격은 별도 저장하고 기준 변경으로 몰래 바꾸지 않는다.

예약은 수동 대량 점검 검색어를 사용하지 않고 해당 기준 전체를 대상으로 한다. 50,000개 초과 시 예약 시작 오류로 남기므로 기준의 상품군을 좁혀야 한다. 기준을 사용 중지하면 다음 도래 확인에서 예약을 중지한다. 예약 사용 중지는 새 회차만 막으며 이미 시작한 실행의 중지·취소는 별도다.

기존 서버의 startup/shutdown에 연결한 in-process worker가 부팅과 약 1분 간격으로 확인한다. 한 tick에 예약 시작 최대 4개, 페이지 최대 4개를 처리한다. 여러 인스턴스는 DB 잠금과 예약 회차 고유 key로 중복을 방지한다. 이전 예약 실행이 대기·실행·중지·재시도·실패 상태면 다음 회차를 추가 생성하지 않는다.

**상시 실행 외부 cron이나 정시 실행 보장은 아니다.** Cloud Run 인스턴스가 쉬거나 재시작하면 마지막 tick과 도래·지연 상태를 확인한다. 다음 부팅/tick에서 누락 회차를 이번 점검 한 번으로 합치고 누락 수와 다음 예정 시각을 남긴다. 시작 실패는 회차 예약까지 rollback하고 약 5분 후 다시 시작을 시도하며 오류 알림을 보존한다. DB 자체 장애는 상태 기록도 지연될 수 있다.

## 7. 저장·보호 경계

기존 settings의 `product-correction:renewal:*`, `bulk:*`, `population:*`, `schedule:*`, `occurrence:*`, `notice:*`, worker key를 사용한다. schema migration·새 권한·외부 메시지·AI 호출·운영 데이터 보정은 없다. 설정 key의 100자 제한을 넘는 알림·갱신 버전 키는 결정적 해시로 저장하되 논리 ID와 기존 짧은 키는 유지한다. 인덱스·장기 전용 저장소와 이력 보관 용량은 후속 설계 대상이다. 현황·목록은 페이지당 10개, 결과는 25개, 갱신·제어 이력은 최근 20개 표시하며 기록을 자동 삭제하지 않는다.

서버가 처리 중인 원본은 조회 전용이다. 실제 원본 변경은 별도 P2 명시적 승인·선택 반영 또는 기존 편집 경로에서만 수행한다. 이번 개발 검증은 세션 전용 합성 DB·fixture이며 운영 계정·상품·예약을 만들지 않았다.
