# 관리자 상품 데이터 보정 작업 공간 V1

> **상태**: ACTIVE · **작성일**: 2026-10-24
> **근거**: 관리자에서 기준을 수정·보완하고 해당 상품을 선택하여 주기적으로 작업한다는 사용자 지시
> **구현 상태**: 개발 브랜치에서 수동 정기 운영 P1까지 구현. 운영 배포는 별도 확인.
> **상위 원칙**: [상품설명서 전문 판단·AI 활용 원칙](O4O-PRODUCT-DESCRIPTION-PROFESSIONAL-USE-POLICY-V1.md)

## 목적

이번 범위는 기존 상품 데이터를 직접 고치는 작업이 아니라, 반복적인 보정을 위한 관리자 작업 환경이다. 발견 사례를 고정된 오류 목록이나 일괄 수정 스크립트로 만들지 않는다. 관리자가 기준을 계속 수정하고, 그 기준으로 찾은 후보 중 실제 작업할 상품을 선택한다.

진입은 **관리자 → O4O 상품 DB → 데이터 정비** (`/admin/o4o-product-db/maintenance`)의 **상품 보정 작업 공간**이다. 공통 Product DB의 기존 권한인 `platform:super_admin`을 조회·저장 모두에 적용한다. 서비스 관리자 권한을 추가하지 않는다.

## 운영 순서

1. **기준 편집**: 이름, 검토·보완 지침, 설명서 이용 목적(전문인/AI 판단·상담지원/소비자 QR), 상품군, 설명서 유형, 언어, 점검 주기, 대상 찾기 방식을 저장한다. 기존 기준 수정은 새 버전이 된다. 이전 버전을 조회할 수 있다.
2. **대상 점검**: ACTIVE 상품을 조회한다. 제조사·규격·바코드 누락, 해당 유형·언어 설명서 부재, 설명서 경과일, 본문 확인 문구, STORE·B2B 동일 본문, 수동 검토 범위를 지원한다. 상품명·바코드 검색으로 좁힌다. 점검 실행은 검색 결과 한 페이지(최대 25개) 단위로 기준 버전·검색·페이지·후보 수·표시 원문·성공/실패를 보존한다. 후보 수는 검토 완료 수가 아니다. 문구 매칭은 후보 검색이며 오류 판정이나 단어 중심 반려가 아니다.
3. **상품 선택**: 결과는 25개씩 조회하고 여러 페이지에서 최대 50개를 선택하여 작업 묶음을 만든다. 점검 이후 기준 버전·선택 상품 원문이 바뀌면 다시 점검해야 한다. 같은 기준 버전·상품·원문에 열린 작업 또는 다음 점검 전 완료 기록이 있으면 기존 작업을 연결한다. 선택한 상품 중 새 작업과 재사용한 작업을 구분해 안내한다.
4. **보완안 준비**: 선택 당시 기준·원문을 참고하고 작업 안내를 복사하여 활용한다. 보완 초안, 검토 메모, 확인 근거·출처를 별도로 저장한다. 상품 사실 근거와 전문 참고정보 근거의 출처·확인일을 구분해 기록한다.
5. **작업 이력 재개**: 저장한 작업 묶음을 다시 열어 이어서 작업한다. 상태는 대기/작업 중/근거 확인 필요/검토 대기(미적용)/보류와 종료 결과인 수정 불필요/변경안 검토 완료(미적용)/대상 제외를 구분한다. 검토 대기·변경안 검토 완료는 초안·메모·근거가 필요하고 수정 불필요·대상 제외는 메모·근거가 필요하다. 근거 대기·보류에는 사유와 미래 재확인일을 입력한다. 동시 수정 충돌 시 입력 내용을 보존한 후 최신 작업과 비교한다. 이전 저장 기록도 조회할 수 있다.

점검 주기는 상품별 검토 종료 시 다음 점검일 계산에 사용한다. 검토 완료일·다음 점검일은 서버가 당시 기준으로 계산하며 설명서 변경 시점과 구분한다. 동일 내용 재저장만으로 완료일을 연장하지 않는다. 근거 대기·보류는 완료로 집계하지 않는다. 이번 버전은 관리자가 직접 점검을 실행한다. 예약 실행·자동 알림·외부 AI 호출·자동 수정 기능은 포함하지 않는다.

## 정기 관리 현황·실행 기록

현황 탭과 데이터 정비 화면에서 사용 중인 기준의 상품별 최신 작업 기록을 확인한다. 최신 기준 버전을 우선하고 같은 버전에서는 최근 생성된 작업을 기준으로 삼아, 과거 작업의 메모 수정이 새 작업을 가리지 않게 한다. 전체 기록·미완료·정기 점검 도래·재확인 도래·검토 완료·기준 변경 재점검 조건으로 조회하며, 상품 수와 상품·기준별 기록 수를 구분한다. 조건 간에는 중복이 있을 수 있다. 현황에서 해당 상품 작업을 바로 열 수 있고 입력 중인 초안을 유지한 채 현황을 새로고침할 수 있다.

새 기준 버전이 생기면 과거 작업의 기준·원문·예정일은 유지하고 기준 변경 재점검으로 표시한다. 현재 원문 변경 여부는 대상 점검에서 다시 확인한다. 사용 중지한 기준은 현황 집계에서 제외하되 기존 작업·실행 이력은 보존한다.

실패한 점검은 후보 0개나 정상 완료로 표시하지 않는다. 실패 범위를 같은 기준 버전으로 재실행하며 새로운 실행 이력을 남긴다. 기준이 바뀌면 최신 기준으로 새로 점검한다. DB 조회에는 30초 statement timeout을 두며, 5분 이상 실행 중인 기록은 관리자가 새로고침 후 중단 복구·재실행할 수 있다. 늦게 끝난 이전 요청은 복구된 실패 이력을 덮어쓰지 않는다.

화면 날짜는 브라우저 현지 시각으로 표시하며 API에는 UTC 시각을 저장한다. 점검은 전체 재고의 자동 순회가 아닌 페이지 단위 수동 조회다. 장기 대량 실행·진행 cursor·예약은 후속 범위다.

## 기준을 발전시키는 방법

수치와 1일량의 관계, 포장 수량과 총량의 불일치, 유형별 일반 사용 안내와 제품 고유 사용법의 혼동, 전문 참고정보 연결 부족 같은 발견은 **기준을 보완하는 사례**다. 특정 상품의 오류로 단정하거나 현재 데이터를 일괄 수정하는 근거로 삼지 않는다.

예를 들어 관리자가 “수치의 기준량 근거 확인” 기준을 만들고 `μg`, `mg` 등의 문구로 후보를 좁힐 수 있다. 계산·효능 판단은 문구 검색 결과만으로 확정하지 않는다. 확인할 자료와 보완 지침은 관리자 화면에서 바꾼다. 상품군별 다른 설명 목적과 근거 규칙은 상위 원칙을 따른다.

## 저장과 적용의 경계

- 기준 최신본, 변경 버전, 선택 작업 묶음, 페이지 점검 실행, 개별 작업 저장 이력은 기존 `settings`의 전용 `product-correction:*` namespace에만 저장한다. migration이나 기존 상품 데이터 보정은 수행하지 않는다.
- 작업 묶음은 당시 기준 전체와 선택 상품·설명서의 스냅샷을 보존한다. 기준을 나중에 수정해도 과거 작업 기준이 바뀌지 않는다. 원문이 긴 경우 처음 20,000자와 전체 확인 필요 표시를 제공한다.
- 초안·근거·메모의 저장은 `product_masters`, `shared_product_descriptions`, 식별자, 후보 상태, QR, 게시 데이터를 변경하지 않는다. 검토 대기 역시 승인·반영 완료가 아니다.
- 상품 원본·canonical 설명서의 적용/승인/게시 연결은 후속 작업이다. 기존 QR 설명서의 공식 지식 기반 채택 보류도 유지한다.
- 기존 고아 후보·취소 의약품 후보 정합화 작업은 별도 접기 영역에 유지된다. 새 보정 작업과 연결하지 않는다.

API는 `/api/v1/admin/o4o-product-db/correction` 아래의 기준/버전/preview/작업 묶음/개별 작업 기록과 `/rules/:id/runs`, `/runs`, `/runs/:id/retry`, `/operations`, `/batches/:id/items/:taskId/versions`로 구성한다. 기존 preview는 조회 전용으로 유지하며 화면의 대상 점검은 실행 기록을 남기는 runs API를 사용한다. SQL 조건은 서버의 고정 연산자와 바인딩 값만 사용한다. 기준 지침이나 검색어를 SQL·정규식·실행 코드로 평가하지 않는다. 기준과 작업에는 revision을 적용하여 다른 관리자의 저장을 덮어쓰지 않는다.

## 검증

합성 데이터 전용 PostgreSQL 통합 테스트, 관리자 API 권한 테스트, 화면 작업 흐름 테스트를 제공한다. 통합 테스트는 `CORRECTION_TEST_DATABASE_URL`로 지정한 로컬 `correction_review` DB에서만 실행한다. 상품·설명서 테이블에 쓰기 금지 trigger를 걸고, 작업 전후 전체 내용이 동일함을 확인한다. 운영 계정·실제 상품을 테스트 보정하지 않는다.
