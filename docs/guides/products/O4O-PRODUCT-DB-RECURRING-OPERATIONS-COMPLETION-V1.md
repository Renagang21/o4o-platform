## 관리자 운영 흐름

관리자 → O4O 상품 DB → 데이터 정비에서 기존 기준·선택 작업·변경안 승인·선택 반영·설명서 갱신을 그대로 이용한다. 조회와 쓰기는 기존 platform:super_admin 경계를 유지한다. 서비스 관리자에게 새로운 권한을 주지 않는다. AI 호출·QR 공식 DB 채택·일괄 상품 보정은 추가하지 않는다.

### 기준 초안

새 기준 작성 영역에서 함량/1일 기준량, 포장/총량, 화장품 고유 사용법, 전문 판단 참고정보의 초안을 선택한다. 선택은 작성 중인 이름·지침·상품군·후보 검색 조건만 바꾸고 목적·유형·언어·주기는 유지한다. 사용 여부는 꺼진다. 초안 사용 버튼 옆에 입력 교체를 안내하며 관리자가 내용을 편집하고 기준 저장을 실행해야 등록된다. 운영 seed나 자동 활성화·예약 생성은 없다.

수치·단어 매칭은 후보 검색이며 오류 확정이 아니다. 제품 사실과 전문 참고정보의 근거를 구분하고, 질병명이나 진단 과정이라는 이유만으로 전문 설명을 배제하지 않는다. 전문 참고정보를 해당 제품의 확정 효과로 바꾸지 않는다.

### 상품별 자료·관리 이력

상품 상세 또는 개별 검토의 **이 상품의 자료·정비·갱신 이력 열기**로 진입한다. 데이터 정비의 상품별 영역에 상품 ID를 직접 입력해도 된다. 조회 중인 상품 이름/상태/바코드/제조사/규격/상품군을 표시하고 다음 자료를 페이지당 10개씩 조회한다.

- 현행 정본 원문·요약·유형/언어·출처 유형/참조: 원문은 최대 20,000자와 잘림 표시, 전체는 상품 상세 연결.
- 검토와 다음 점검: 당시 기준 버전·상태·근거 메모·다음 점검/재확인일·기존 작업 직접 연결.
- 근거·변경안·반영: 상품 사실/전문 참고 출처·확인일·확인 상태·전후 값·검토/반영 상태·기존 변경안 연결.
- 설명서 갱신: 유형/언어·상태·메모와 갱신 직접 연결. 이동 후 **연결된 설명서 갱신 검토 열기**를 눌러 현재 원문을 확인한다.
- 일반 편집: 실제 변경 이벤트의 경로·시각·전후 값과 상품 상세 연결. 이것만으로 모든 raw SQL·공급자 수집 변경을 감지한다고 해석하지 않는다.

과거 작업 스냅샷과 현행 정본을 합치지 않는다. 원문 HTML은 실행하지 않고 텍스트로 표시한다. 다른 상품의 늦은 조회 응답이 현재 선택을 덮어쓰지 않는다. 조회 실패 시 마지막 성공 자료임을 표시한다. 조회 API는 READ ONLY + REPEATABLE READ transaction이며 상품 ID와 허용 section/page만 받아 고정 SQL로 조회한다. 목록·원문 조회가 승인·상품 반영·검토 종료를 수행하지 않는다.

## 정기 실행과 복구

기존 API 서버의 부팅/약 1분 tick은 유지한다. tick 전체에 PostgreSQL transaction advisory lock을 사용해 서버·독립 작업의 동시 tick을 조정한다. 페이지의 기존 행 잠금·cursor·예약 회차 고유 key·재시도 정책도 유지한다. 다른 tick이 실행 중이면 busy로 반환하며 중복 점검이나 실패 heartbeat를 만들지 않는다.

성공 heartbeat는 마지막 tick·성공·실행 경로(server/job)·소요 시간·처리 페이지/예약 수를 남기고 실패 시 마지막 실패 시각과 비밀 없는 오류 코드만 남긴다. 성공 후에도 과거 실패 시각을 보존하되 현재 오류 코드는 해제한다. DB 장애 시 heartbeat 자체도 지연될 수 있다.

독립 worker는 같은 정기 서비스를 호출하는 API 이미지의 별도 entry다. HTTP 서버·공개 작업 endpoint·migration runner·상품 적용 API를 시작하지 않는다. PostgreSQL만 사용하며 API의 기존 연결 검증/전송 설정을 재사용한다. entities/migrations/schema sync/extension 설치/cache는 끄고 작은 연결 풀을 사용한다.

```text
node dist/product-correction-worker.js --help
node dist/product-correction-worker.js --run --max-ticks 100 --max-seconds 240
```

help는 DB를 열지 않는다. --run 없는 요청, 미지정 DB 환경, 잘못된 옵션은 실패 종료한다. DB_HOST/DB_USERNAME/DB_NAME을 명시해야 하며 비밀은 기존 실행 환경에서 주입한다. 실행 성공은 counts/reason만 출력하고 SQL·상품 원문·자격정보를 출력하지 않는다.

기본 예산은 100 tick/240초이며 최대 1,000 tick/600초다. 예산·종료 신호는 tick 사이에서 확인한다. 진행 중인 페이지는 commit 또는 rollback하며 마지막 committed cursor에서 새 프로세스가 이어간다. 엄격한 wall-clock timeout이 아니므로 Job timeout은 예산과 최대 한 tick(페이지당 statement timeout)을 더해 설정해야 한다. 비정상 강제 종료도 이전 committed 페이지는 재처리하지 않는다. 중지·실패한 실행을 자동 재개하지 않는다.

## 운영 인계 — 아직 실행하지 않은 항목

이번 범위는 main 병합 전까지이며 Cloud Run Job/Scheduler/IAM/비밀/운영 예약은 생성·변경하지 않았다. **독립 entry가 있다는 사실만으로 Cloud Run 휴면 중 정시 실행이 보장되지는 않는다.**

향후 별도 통합·배포 단계에서 다음을 확인해 연결한다.

1. 이 entry가 포함된 검증 완료 API 이미지 digest와 기존 Cloud SQL 접속·최소 권한 실행 계정을 사용한다. Job command를 위 worker로 고정하고 중복 호출은 DB mutex로 조정한다. 기존 migration job을 재사용하지 않는다.
2. 기존 인프라 소유자가 Job timeout/재시도·리소스·DB 풀 예산을 확인하고 Cloud Scheduler 등의 인증된 Job 실행을 연결한다. 공개 HTTP 작업 경로나 브라우저 타이머로 대체하지 않는다.
3. 준비된 실제 이미지·서비스 계정·secret 참조·주기·비용·실행 scope를 검토한 뒤 운영 변경을 승인·적용한다. 최초 실행은 상품 보정 없이 후보/이력만 점검하고 heartbeat/job 로그와 지연 현황을 확인한다.
4. 독립 호출이 실제 활성화된 후 서버를 쉬게 한 상태에서도 예약 회차가 처리되는지 검증해야 운영의 휴면 한계 해소를 완료로 판정한다. 비활성화 시 API의 기존 best-effort tick으로 돌아가며 작업/이력은 삭제하지 않는다.

50,000개 로컬 합성 검증의 실행 시간은 CHECK의 측정값이며 운영 데이터·원문 크기·네트워크에서의 SLA나 처리량 보장은 아니다. 대량 한도·실제 상품 수정의 명시적 승인·QR 채택 보류는 그대로다.
