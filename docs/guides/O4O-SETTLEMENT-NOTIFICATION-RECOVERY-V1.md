# 정산 알림 확인·재처리 안내

> 상태: ACTIVE · 작성일: 2026-10-27 (KST)
> 범위: [개발 TODO](../work-orders/TODO-O4O-SETTLEMENT-NOTIFICATION-RECOVERY-V1.md)의 이용/통합 인계. 운영 적용 완료 선언은 아니다.

## 관리 화면

기존 Neture 정산 관리자 권한으로 **정산 관리 → 정산 알림 확인·재처리**에서 `저장 실패` 또는 `미처리·대기`를 조회한다. 정산 목록의 다른 상태 필터·빈 결과와 독립적으로 확인할 수 있다. 개별 정산의 상세를 펼쳐도 알림 상태가 표시되며 연결 주문이 없어도 확인할 수 있다.

| 상태 | 의미·행동 |
|---|---|
| 미처리·대기 | 처리 완료가 기록되지 않았다. 실행 중·처리 중단 이후 모두 포함한다. 현재 상태를 확인하고 알림 저장 재처리를 실행할 수 있다 |
| 알림함 저장 실패 | 현재 수신자 없음 또는 저장 실패다. 소유 관계/시스템 상태를 확인한 뒤 명시적으로 재처리한다 |
| 알림함 저장 완료 | 처리 시점의 수신자 알림이 DB에 저장됐다. 사용자가 읽거나 삭제해도 완료 상태를 유지하며 재생성하지 않는다 |
| 과거 발송 여부 확인 불가 | 새 처리 원장 없이 지급된 과거/구버전 건이다. 실패로 단정하거나 이 화면에서 재발송하지 않는다 |
| 지급 완료 전·대상 아님 | 알림 재처리 대상이 아니다. 이 기능으로 지급 상태를 바꾸지 않는다 |

조회 실패는 확인된 0건이 아니다. 재처리 응답이 유실되거나 오류면 **재지급하지 말고 알림 상태 다시 조회**로 결과를 확인한다. 같은 정산이 이미 완료됐다면 재요청은 새 알림을 만들지 않는다. 여러 관리자가 동시에 요청해도 행 잠금과 완료 상태로 중복 저장을 막는다. 시도 횟수는 DB에 결과가 확인된 처리 횟수이며 연결 중단까지 완전하게 세는 네트워크 시도 지표가 아니다.

저장 완료는 즉시 SSE/기기 수신·실제 열람·이메일 전달의 증거가 아니다. 화면 수신 힌트가 유실돼도 기존 알림함 조회에서 확인하며, 이미 저장된 알림을 다시 생성하지 않는다. 새 이메일/SMS/자동 스케줄러나 일괄 재발송은 추가하지 않았다.

## 지급과의 관계

기존 승인→지급 상태 변경과 알림 대기는 한 DB statement로 기록한다. 그 뒤 알림 저장과 완료 상태도 하나의 트랜잭션으로 기록한다. 수신자 중간 저장 실패는 알림 전체를 되돌리고 실패 상태를 남긴다. 알림 실패가 이미 기록된 지급을 되돌리거나 금액·메모·지급시각을 바꾸지 않는다. 알림 재처리는 정산 계산/승인/지급 또는 실제 은행 송금을 호출하지 않는다.

실행 시점의 기존 공급자 owner 판정과 legacy fallback을 그대로 사용한다. 새 수신자를 body로 지정하거나 모든 공급자/기존 소유자에게 다시 보내지 않는다. 실패 후 소유자가 바뀌면 재처리 시점의 현재 수신자를 확인한다. 완료 뒤 새 소유자에게 과거 이벤트를 다시 발송하지 않는다.

## 통합·운영 경계

forward migration `CreateSettlementNotificationJobs1793087685658`을 기존 정식 migration Job에서 먼저 적용해야 한다. 새 API를 schema 없이 먼저 올리면 지급+대기 SQL은 함께 실패하며 기존 approved 상태를 보존한다. 기존 API는 새 표와 공존할 수 있으나 구버전이 처리한 지급 건은 추적 불명 상태로 남을 수 있다. 운영 migration/배포/실계정 재처리는 이번 개발 단계에서 실행하지 않았다.

`neture_settlement_notification_jobs`는 정산 UUID·상태·확인된 시도/저장 건수·고정 오류 코드·시각만 저장한다. 금액·계좌·본문·수신자/관리자 ID는 복제하지 않는다. 정산 삭제에 종속되어 삭제하고 별도 개인정보 보존기간이나 금융 정책을 신설하지 않는다. 기존 계정 제거 writer fence를 연결하며 플랫폼 전체 파기 준비 완료를 뜻하지 않는다.

처리 증빙이 한 행이라도 있으면 migration down은 거부한다. 완료 상태를 지운 뒤 알림을 재생성하는 자동 rollback을 하지 않는다. 빈 전용 DB의 down/up는 검증했으며, 운영에서 상태를 폐기하거나 과거 발송 여부를 추정하는 작업은 별도 범위다.
