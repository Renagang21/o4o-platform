## 2. 실제 FK와 삭제 영향

| 삭제되는 부모 | 현재 FK | 이력 영향 |
| --- | --- | --- |
| communities | history.community_id → ON DELETE CASCADE | 해당 커뮤니티 이력도 삭제 |
| community_memberships | history.membership_id → ON DELETE CASCADE | 해당 가입 이력도 삭제 |
| 변경 대상 users | memberships.user_id → ON DELETE CASCADE → history.membership_id | 대상 계정의 가입과 이력이 연쇄 삭제 |
| 변경 수행자 users | history.actor_user_id → ON DELETE SET NULL | 수행자 연결만 제거. actor가 동일 row의 대상 회원이면 위 cascade도 별도로 적용됨 |

`actor_user_id`가 NULL이 되는 것만으로 익명화가 완료되는 것은 아니다. membership 연결과 자유 입력 reason이 남을 수 있다. 커뮤니티 비활성화·개별 탈퇴와 부모 row 물리 삭제는 구분한다. **일반 운영자 기록의 최소1년/해당 시2년 보존부터 부모 삭제의 cascade 보호가 즉시 선행되어야 한다.** 분쟁 예외가 있을 때만 필요한 보호나 향후 삭제 job의 부가 조건이 아니다. 현재 FK가 최소 보존이나 법률 보유 예외를 자동 보장한다고 판단하지 않는다.

### 2.1 현재 활성 계정 삭제의 선행 보호 — 미구현

현재 [AdminUserController.deleteUser](../../apps/api-server/src/controllers/admin/AdminUserController.ts)는 `/admin/users/:id`에서 Super Admin/Demo 보호 후 `userRepo.remove(user)`로 hard-delete를 시도한다. `23503` FK 거부일 때만 비활성화와 역할 제거로 fallback한다. CASCADE가 성공하면 이 fallback은 작동하지 않아 생성 후365일 미만의 해당 회원 이력도 삭제될 수 있다. 기간/예외 개정안을 확정하지 않아도 이미 존재하는 최소 보존 하한의 실제 결함이며, 자동 삭제를 비활성화해도 해결되지 않는다.

즉시 선행 조치는 해당 부모 hard-delete를 차단하거나 감사 이력을 독립 보존하는 것이다. **보호 구현 전에는 이 계정 삭제 경로가 보존 하한을 준수한다고 판정하지 않고, 관련 계정/가입/커뮤니티의 물리 삭제를 이번 작업에서 실행하지 않는다.** 예외 저장과 장기 보관 설계 완료만을 기다리며 현재 위험을 완료 처리하지 않는다.

새 schema 없이 우선 적용할 **최소 변경안**은 삭제 transaction에서 대상 users row를 잠그고, 해당 사용자의 community_memberships가 있으면 hard-delete 전에409 `COMMUNITY_RETENTION_REVIEW_REQUIRED`로 중단하는 임시 보호다. role/status/isActive·가입/이력 row를 그대로 유지하고 기존 Super Admin/Demo guard도 보존한다. 감사 이력 유무/나이만 먼저 읽고 삭제하는 방식은 동시 기록과 분류 미확정 문제를 놓칠 수 있으므로 사용하지 않는다. 부모 user 잠금과 새 membership FK의 동시 삽입까지 격리 DB에서 검증한다. 이 임시 보호는 최종 계정 파기/분리 보관 설계를 대체하지 않으며, 일반 사용자 데이터 처리 권리와 최종 보유 정책을 함께 정렬해야 한다.

이 변경은 통합 UI/조사에서 **전체관리자 계정 삭제 API의 동작/응답 계약**으로 범위가 넓어진다. AGENTS §5의 새로운 API contract 변경과 사용자의 ‘조사·개정안 준비 후 확정’ 경계에 따라, 이 문서로 구체안을 준비하고 해당 코드 변경 범위를 확정한 뒤 구현한다. 아직409 guard·FK 변경·감사 독립 보관은 구현/배포하지 않았다. 운영 계정을 실제로 삭제해서 검증하지 않는다.

## 3. 현행 최소 보존과 추가 확정할 집행안

현행 보유기간 정본 §6은 테이블 이름에 한정하지 않고 **그 밖에 개인정보 관리자·운영자의 처리행위 기록**을 포함하며 생성 후 최소1년 보존을 정한다. 커뮤니티 운영자의 승인·반려·역할 변경·정지·복구·관리자 탈퇴 처리와 개설 승인에서 생성한 초기 admin 기록도 이 기준을 보존한다. 자동 삭제 코드가 없다는 사실은 이 최소 보존 정책이 없다는 뜻이 아니다. 기존 정책을 단축하는6개월안은 철회한다.

이 테이블의 `action='create'`도 개설 승인자가 기록하는 현재 경로는 운영자 처리 기록이다. 본인 탈퇴와 `migration` 등은 호출 경로·수행자·목적에 따라 별도로 분류하되 action 이름이나 자유 입력 reason만으로 최소 보존을 우회하지 않는다. 분류 미확정 행은 자동 삭제 후보에서 제외한다. 단축안을 전체 테이블에 적용하거나 전자상거래 보유기간을 무조건 복사하지 않는다.

| 선택안 | 기준 | 장점 | 한계 |
| --- | --- | --- | --- |
| **기본365일 집행안** | 각 이력 created_at 이후365일 | 운영자 기록의 현행 최소1년 기준을 유지 | 분류·법정2년 대상·분쟁 예외·cascade 보호 검증 전에는 job 활성화 불가 |
| 730일 집행안 | 각 이력 created_at 이후730일 | 정본 §6의2년 대상이면 필수 상향 | 임의 선택이 아닌 해당 개인정보처리시스템의 요건 판정이 우선. 추가 장기 보유는 필요성·고지 검토 |

현행 기본을 유지하는 집행 권고는 **생성 후365일 이상**이며 기간을 이보다 짧게 확정하지 않는다. 다만 정본 §6의5만 명 이상 정보주체 처리·민감정보/고유식별정보 처리·그 밖의 법정2년 요건에 해당하는 시스템은730일 이상으로 상향해야 한다. 과거2026-09-17 조사 결과만으로 현재 시스템의2년 미해당을 단정하지 않는다. 운영 read-only 건수/취급 항목 조사와 법률 담당 판정으로 최신 요건을 확인하기 전 삭제 기준을 활성화하지 않는다.

회원의 탈퇴/복구/재가입이 이전 모든 이력의 시계를 다시 시작하지 않도록 각 row의 created_at을 사용한다. 회원 활동 중에도 분류/예외를 확인한 오래된 이력은 기간 경과 대상이다. 현재 가입 원장·계정 정보·게시글·거래 증빙은 별도 정책 대상이며 이 규칙으로 삭제하지 않는다. 시각이 누락/비정상인 row는 미확정으로 분류하고 자동 삭제하지 않는다. 달력상의1년과365일 차이는 최종 고지와 집행에서 같은 기준으로 표기한다.

분쟁·법정 보유 예외는 관련 row만 대상으로 목적·근거·승인자·보유 종료일/다음 검토일을 기록하고 접근을 제한하는 방식을 제안한다. 무조건 무기한 보존하거나 모든 커뮤니티 이력에 동일 예외를 적용하지 않는다. 예외 저장·cascade 보호 방식은 아직 구현되지 않았으므로 그 방식이 확정/검증되기 전 자동 삭제는 활성화하지 않는다. 새 schema가 필요한지까지 다음 구현 범위에서 따로 판단한다.

기간 만료의 기본 파기는 해당 **이력 row만 삭제**하는 안을 권고한다. reason 일부 마스킹과 actor NULL만으로 비식별화를 완료했다고 판단하지 않는다. 통계 목적의 비식별 집계를 별도로 남기려면 재식별 위험·필드·목적을 추가 확정해야 한다.

## 4. 개인정보 처리방침 개정 문구 제안 — 게시 전

아래 문구는 현행 최소 보존을 유지하면서 집행 범위·예외가 확정될 때의 후보이며 현행 처리방침을 대체하지 않는다.

> 커뮤니티 운영의 적정성 확인과 회원 문의 처리를 위해 가입 승인·반려, 역할 변경, 이용 제한·복구 및 탈퇴의 변경 이력을 처리합니다. 처리 항목은 커뮤니티·가입 식별정보, 변경 수행자 식별정보, 변경 전후 상태와 역할, 처리 사유 및 기록 시각입니다. 운영자의 개인정보 처리행위 기록은 생성 후365일 이상 보관하며 법령상2년 보존 대상 시스템의 기록은730일 이상 보관합니다. 분류된 기록의 확정 보유기간이 끝나면 파기합니다. 관계 법령에 따라 보존하거나 실제 분쟁 처리를 위해 별도 보관이 필요한 기록은 해당 목적과 기간을 정해 접근을 제한하고, 그 기간이 끝나면 파기합니다.

이 후보와 계정 자체 삭제·커뮤니티 폐쇄 시 처리, 예외의 실제 근거·기간 및 현행 v1 조항의 일치 여부를 함께 확정한다. 운영 안내에는 개별 탈퇴 후 게시글/기존 이력이 남는 현재 범위를 정확하게 표시한다. 자동 삭제를 지원하기 전 그 기능이 이미 운영 중이라고 공고하지 않는다.

## 5. 확정 후 구현·검증 순서

1. **현재 부모 hard-delete의 최소 보존 위반을 먼저 보호**한다(§2.1). 코드 변경 범위 확정 → 격리 transaction/동시성 및 현재 계정·권한 불변 검증 → 정상 CI/review/main/배포. 실제 계정 삭제는 검증에 사용하지 않음.
2. 운영자 기록 최소365일·2년 요건 해당 시730일의 현행 기준을 유지하고, 본인 탈퇴/자동 생성 행 분류·기산점·예외·최종 부모 삭제/독립 보존과 파기 방식 확정.
3. 보유기간 정본과 처리방침 개정안 정렬. 새 정책 version·본문·공고/시행일은 기존 인증/법률 담당 작업과 맞춤.
4. 현재 schema에서 가능한 범위와 예외/인덱스 등에 필요한 추가 변경을 명시해 별도 구현 범위 확정. 미승인 schema/migration은 추가하지 않음.
5. 합성 데이터로 기간 경계·active/withdrawn·재가입·정지/복구·예외·비정상 시각·마지막 admin·cascade를 검증. 현재 role/status와 회원 원장 불변 확인.
6. 운영 read-only dry-run으로 후보/예외/미확정 **건수만** 검증. actor/name/reason/원문·식별자는 보고하지 않음. 이번 조사에서는 운영 dry-run도 실행하지 않음.
7. 공고/시행 및 필요한 고지 후, 승인된 대상/배치/복구·실패 중단 기준으로 집행. 예외가 검증되지 않으면 fail closed. 작업 로그는 기준일·건수·성공/실패만 기록.
