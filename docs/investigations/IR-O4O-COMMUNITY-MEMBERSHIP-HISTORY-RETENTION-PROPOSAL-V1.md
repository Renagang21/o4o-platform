| 삭제되는 부모 | 현재 FK | 이력 영향 |

`actor_user_id`가 NULL이 되는 것만으로 익명화가 완료되는 것은 아니다. membership 연결과 자유 입력 reason이 남을 수 있다. 개별 커뮤니티 탈퇴와 전체 계정 제거는 별도 요청이다. 현재 FK는 법정 기록의 최소 보존과 일반 개인정보 파기를 함께 보장하지 않는다.

### 2.1 사용자 확정: 사용중지 후 Admin 완전 제거

2026-10-12 사용자는 **O4O의 개인정보 소유 최소화**를 우선하며, **각 서비스 Operator가 사용중지하고 Admin이 전체 계정을 완전 제거**하는 두 단계를 확정했다. 가입 데이터나 수행자 이력이 있다는 이유로 계정·프로필을 남기거나 계정 삭제를 막는 이전 제안과 `COMMUNITY_RETENTION_REVIEW_REQUIRED` guard는 철회한다. 이력 기본1년은 일반 회원정보의 삭제 유예기간이 아니다.

| 경로 | 조사한 실제 동작 | 구현 시 정렬할 차이 |
| --- | --- | --- |
| 서비스 사용중지 | [MembershipApprovalService.suspendMembershipCore](../../apps/api-server/src/services/approval/MembershipApprovalService.ts)는 서비스 운영 범위의 active 가입을 정지하고 해당 권한을 중지. 플랫폼 권한은 별도 범위 | 해당 서비스 사용중지가 공통 계정 또는 다른 서비스의 제거 권한으로 확대되지 않도록 유지 |
| 전체관리자 삭제 | [AdminUserController.deleteUser](../../apps/api-server/src/controllers/admin/AdminUserController.ts), `DELETE /api/v1/admin/users/:id`. 현재 `platform:super_admin`만 호출. Super Admin/Demo 보호 후 hard-delete | FK 오류23503이면 isActive=false·역할 제거 후 success=true를 반환하는 fallback은 완전 제거가 아님. 일반 개인정보가 남으며 제거 성공으로 판정하면 안 됨 |
| 다른 관리자 삭제 경로 | [UserManagementController.deleteUser](../../apps/api-server/src/controllers/UserManagementController.ts), `DELETE /api/v1/users/:id`; [UserRepository.softDeleteUser](../../apps/api-server/src/repositories/UserRepository.ts)를 호출. [Admin UserApi.deleteUser](../../apps/admin-dashboard/src/api/userApi.ts)도 이 경로를 참조 | soft-delete 시도와 완전 제거 계약은 다름. 두 API의 mount·인증·실제 UI 소비처를 함께 확정해야 함 |
| 개인 첨부파일 | 보유기간 정본 §9의 계정 제거→GCS 연동 미구현 | 계정 row 삭제만으로 개인 파일까지 제거했다고 보고할 수 없음 |

**완전 제거의 목표 범위**는 해당 사용자 계정·프로필·연락처·인증 연결/비밀번호/토큰·가입/개인 권한·개인 자격자료·개인 소유 콘텐츠 및 개인정보 첨부파일이다. 개인 내용이 공용 자료 안에 포함된 경우 그 개인정보를 찾아 제거한다. 사업체·매장 자체와 다른 사용자의 내용은 대상 사용자와 별도 주체이며 자동 연쇄 삭제하지 않는다. 사업 소유 자료의 관리책임 이전과 개인 정보 제거를 구분한다. 백업 사본은 정본 §11의7일 순환 보존 범위와 복원 시 재삭제 절차를 확인하며 즉시 모든 백업까지 지워졌다고 주장하지 않는다.

법령상 보존이 실제 필요한 처리 기록은 일반 계정·프로필과 분리하여 **필수 최소 항목만** 확정된 법정기간까지 보관하고 종료 시 파기한다. 법적 보존을 이유로 users/profile 전체를 유지하지 않는다. 법정 대상과 기간은 근거로 확인하며 모든 개인 활동·게시물·자유 입력 사유가 자동으로 법정 기록이 되는 것은 아니다. 현재 community history의 대상 membership CASCADE와 actor SET NULL은 이 분리·최소화 구현을 대체하지 않는다. 대상 회원 및 수행자 전용 계정 양쪽의 기록을 조사한다.

완전 제거 구현은 성공 응답 전에 DB의 일반 개인정보 제거와 인증/세션 무효화, 개인 파일 삭제 결과를 확인해야 한다. DB/파일 실패를 단순 비활성화 성공으로 감추지 않고 미완료 및 재시도 가능한 상태로 반환한다. 부분 실패·동시 가입/이력 기록·중복 요청·다른 사용자/사업 자료 보존을 합성 데이터로 검증한다. 실제 운영 계정 삭제는 테스트에 사용하지 않는다.

**CORE_CHANGE_REQUIRED — 구현 범위 준비:** 계정 제거 API는 [Core Freeze §2.3·§3.1](../architecture/O4O-CORE-FREEZE-V1.md)의 Approval Core다. 현재 사용자 답변은 위 개인정보 최소화·두 단계 정책을 확정했으며 이전 이력 기반 차단안의 구현 승인이 아니다. 이번 T08의 조사·개정안에서 두 삭제 경로·FK/비FK 개인정보·파일과 최소 법정기록의 처리 순서 및 결과 계약을 정리하고, 구체적인 Core 변경 WO·필요 DDL/운영 삭제 범위를 분리한다. 아직 어떤 삭제 API도 수정/배포하지 않았다. 자동 job을 꺼 두어도 현행 관리자 직접 삭제의 법정 기록 cascade 위험이나 soft-delete 잔여 문제는 해결되지 않는다.

## 3. 기본1년 확정과 추가 확정할 집행 범위

현행 보유기간 정본 §6은 테이블 이름에 한정하지 않고 **그 밖에 개인정보 관리자·운영자의 처리행위 기록**을 포함하며 생성 후 최소1년 보존을 정한다. 커뮤니티 운영자의 승인·반려·역할 변경·정지·복구·관리자 탈퇴 처리와 개설 승인에서 생성한 초기 admin 기록도 이 기준을 보존한다. 자동 삭제 코드가 없다는 사실은 이 최소 보존 정책이 없다는 뜻이 아니다. 기존 정책을 단축하는6개월안은 철회한다.

이 테이블의 `action='create'`도 개설 승인자가 기록하는 현재 경로는 운영자 처리 기록이다. 본인 탈퇴와 `migration` 등은 호출 경로·수행자·목적에 따라 별도로 분류하되 action 이름이나 자유 입력 reason만으로 최소 보존을 우회하지 않는다. 분류 미확정 행은 자동 삭제 후보에서 제외한다. 단축안을 전체 테이블에 적용하거나 전자상거래 보유기간을 무조건 복사하지 않는다.

| 집행 기준 | 기간 | 적용 | 미구현 범위 |
| --- | --- | --- | --- |
| **기본 달력 1년 — 사용자 확정** | 각 이력 created_at 이후 달력 1년 | 운영자 기록의 현행 최소1년 기준을 유지 | 분류·법정2년 대상·분쟁 예외·법정기록 분리·개인정보 파기 검증 전에는 job 활성화 불가 |
| 달력 2년 집행안 | 각 이력 created_at 이후 달력 2년 | 정본 §6의2년 대상이면 필수 상향 | 임의 선택이 아닌 해당 개인정보처리시스템의 요건 판정이 우선. 추가 장기 보유는 필요성·고지 검토 |

사용자가 확정한 기본 보유기간은 **생성 후 달력 1년**이며 기념일에 만료한다. 정본 §6의5만 명 이상 정보주체 처리·민감정보/고유식별정보 처리·그 밖의 법정2년 요건에 해당하면 **생성 후 달력 2년**으로 상향한다. 이는 필요한 기록의 보유기간이며 전체 계정/프로필 보유기간이 아니다. 과거2026-09-17 조사만으로 현재2년 미해당을 단정하지 않고 최신 취급 항목·규모와 법률 담당 판단을 확인한다. 근거 없는 기간 연장은 허용하지 않는다.

회원의 탈퇴/복구/재가입이 이전 모든 이력의 시계를 다시 시작하지 않도록 각 row의 created_at을 사용한다. 회원 활동 중에도 분류/예외를 확인한 오래된 이력은 기간 경과 대상이다. 현재 가입 원장·계정 정보·게시글·거래 증빙은 별도 정책 대상이며 이 규칙으로 삭제하지 않는다. 시각이 누락/비정상인 row는 미확정으로 분류하고 자동 삭제하지 않는다. 기간은 Asia/Seoul에서의 생성 시각을 기준으로 같은 월/일/시각의 달력 1년 또는2년 기념일로 정의한다. 해당 기념일이 없는2월29일 기록은 해당 만료 연도의3월1일 같은 시각으로 보수적으로 넘기고 그 이전에는 삭제하지 않는다. 만료 시각을 UTC로 변환해 비교하며 고정 일수나 now에서 단순히 일수를 빼는 방식으로 기념일을 앞당기지 않는다.

기간 경계 예: 생성2023-03-01 09:00(KST)의1년 기념일은2024-03-01 09:00(KST),2년 기념일은2025-03-01 09:00(KST)다. 생성2024-02-29 09:00(KST)의1년 기념일은 위 보수적 규칙으로2025-03-01 09:00(KST)다. 경계 직전/동일/직후 및 윤년·UTC 변환을 합성 데이터로 검증한다. 기존 generic retention의 policyDays=365 설정도 달력 1년과 동일하다고 주장하지 않는다. 이 테이블의 새 집행에 복사하지 않으며 기존 감사 job의 윤년 정합은 별도 담당 검토 항목으로 남긴다.

분쟁·법정 보유 예외는 관련 row만 대상으로 목적·근거·승인자·보유 종료일/다음 검토일을 기록하고 접근을 제한하는 방식을 제안한다. 무조건 무기한 보존하거나 모든 커뮤니티 이력에 동일 예외를 적용하지 않는다. 예외 저장·법정기록 분리 및 일반 개인정보 파기 방식은 아직 구현되지 않았으므로 그 방식이 확정/검증되기 전 자동 삭제는 활성화하지 않는다. 새 schema가 필요한지까지 다음 구현 범위에서 따로 판단한다.

기간 만료의 기본 파기는 해당 **이력 row만 삭제**하는 안을 권고한다. reason 일부 마스킹과 actor NULL만으로 비식별화를 완료했다고 판단하지 않는다. 통계 목적의 비식별 집계를 별도로 남기려면 재식별 위험·필드·목적을 추가 확정해야 한다.

## 4. 개인정보 처리방침 개정 문구 제안 — 게시 전

아래 문구는 현행 최소 보존을 유지하면서 집행 범위·예외가 확정될 때의 후보이며 현행 처리방침을 대체하지 않는다.

> 커뮤니티 회원 변경 이력은 생성 후 달력 1년간 보관하고 그 기념일에 보유기간이 만료되면 파기합니다. 법령상2년 보존 대상 시스템의 해당 기록은 생성 후 달력 2년간 보관하고 그 기념일에 만료되면 파기합니다. 계정 제거 시 일반 계정·프로필·개인 소유 정보는 지체 없이 파기하며, 법령상 보존이 필요한 최소 기록만 일반 회원정보와 분리하여 해당 기간까지 보관합니다. 실제 분쟁의 처리 증빙은 해당 분쟁 종결일까지 필요한 항목만 별도로 보관하고, 별도 법정기간이 적용되는 증빙은 그 기간 만료 시 파기합니다. 미확정 사유로 보유기간을 무기한 연장하지 않습니다.

이 후보와 계정 자체 삭제·커뮤니티 폐쇄 시 처리, 예외의 실제 근거·기간 및 현행 v1 조항의 일치 여부를 함께 확정한다. 운영 안내에는 개별 탈퇴 후 게시글/기존 이력이 남는 현재 범위를 정확하게 표시한다. 자동 삭제를 지원하기 전 그 기능이 이미 운영 중이라고 공고하지 않는다.
