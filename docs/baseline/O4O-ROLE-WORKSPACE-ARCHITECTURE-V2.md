# O4O-ROLE-WORKSPACE-ARCHITECTURE-V2

> **상태**: ACTIVE
> **작성일**: 2026-10-28 · **최종 갱신**: 2026-10-29 (Asia/Seoul)
> **근거 WO/IR**: [WO-O4O-UNIFIED-OPERATING-RESPONSIBILITY-V1](../work-orders/WO-O4O-UNIFIED-OPERATING-RESPONSIBILITY-V1.md) · 사용자 수용 완료 IR-1~IR-4 및 WO-1 추가 지침
> **적용**: 통합 회원·자격·관리자 리팩토링의 정책 기준. 런타임 구현·운영 반영 완료를 뜻하지 않는다.

## 1. 범위와 우선순위

기존 계정·인증·조직·역할·초대·승인 원장을 최대한 재사용한다. 이번 버전은 [V1](O4O-ROLE-WORKSPACE-ARCHITECTURE-V1.md)의 직영 운영 주체·운영자 지정·운영 화면 위치와 일반 회원 가입 조건을 해당 범위에서 대체한다. V1의 Store/Supplier 자기 업무, 콘텐츠 경로, Legacy Partner 은퇴, 서비스 identity와 관계 원장의 분리, §9 실행 규칙 및 그 밖의 유효한 계약은 유지한다. V1 전체를 폐기하거나 과거 실행 결과를 다시 판정하지 않는다.

코드·메뉴·도메인이 존재한다는 사실은 O4O가 그 사업의 운영 책임을 가진다는 근거가 아니다. 플랫폼 제공 책임과 사업자의 회원·사업 운영 책임을 구분한다. 이 문서는 새 역할·테이블·API를 도입하지 않는다.

## 2. 공통 회원과 자격

- 공통 계정 하나와 Google·카카오·이메일/비밀번호 로그인을 유지한다. 이메일 일치만으로 계정을 자동 병합하지 않는다.
- 최초 가입은 공통 회원 자격이다. 전문 자격·조직 소속·사업 참여 승인은 별도이며 대기·반려가 공통 계정을 없애지 않는다. 계정 자체의 보안 정지와 사업·자격 정지는 구분한다.
- 일반 소비자와 비약사도 공통 회원이 된다. 한 사용자의 복수 자격·복수 조직 소속을 허용한다.
- 약사 자격은 중앙의 위임받은 담당자가 면허 근거를 별도로 확인하고 확인 사유를 기록해 수동 승인한다(2026-10-28 사용자 확정). 과거 분회·약국 승인이나 자기 기입 면허번호를 자동 승격하지 않는다. 자격 반려·취소는 공통 계정을 변경하지 않는다.
- 약사 전용 기능은 확인된 개인 약사 자격이 필요하다. 약국 경영자는 그 자격과 해당 약국의 경영 권한이 필요하다.
- 약국 직원은 경영자의 초대·승인으로 일반 업무 권한을 얻는다. 약사 전용 업무에는 직원 본인의 확인된 약사 자격도 필요하다. 경영자의 확인 표시만으로 공통 자격 검증을 대신하지 않는다.
- 공급자·파트너는 비약사도 승인받아 활동할 수 있다. 현재 Partner 커뮤니티 가입은 승인된 파트너 사업 자격과 동일하지 않다.
- 불필요한 일반 서비스 가입은 줄이되 조직 승인·사업 참여·수강 등록·프로젝트 참여·독립 협업체 가입은 유지한다. `service_memberships` 전체 폐기나 일괄 active 전환을 뜻하지 않는다.

## 4. 관리자 권한 경계

### 4.1 중앙 Admin

전체 관리자 역할은 기존 `platform:super_admin`이다. O4O 직영 업무의 운영 책임, 운영자 지정·회수·업무 위임, 정책·설정 및 중요 데이터 관리·감독을 담당한다. 2026-10-31 사용자 지시에 따라 전체 관리자는 중앙 `/operators`에서 서비스 Admin 및 직영 업무 Operator의 초대·업무 위임·조회·회수를 수행한다. 직영 Operator의 신규 지정은 명시적인 중앙 위임(`o4o-direct`)과 초대 본인 수락을 요구한다. 기존 서비스 Admin의 자기 서비스 Operator 관리 권한은 유지하고, 일반 서비스 지정만으로 중앙 업무 위임을 만들지 않는다. 독립 사업·조직 Operator 지정은 기존 서비스·조직 Admin 경계를 유지한다. 기존 Operator 권한·위임과 독립 사업 범위는 유지한다. 전체 관리자 계정 관리와 서비스 운영 역할 관리는 구분한다. 본인·마지막 관리자·Demo 등 기존 보호 조건을 유지한다.

### 4.2 중앙 Operator

중앙 Operator는 새 기술 역할명이 아니라 **O4O 중앙 Admin에게 직영 업무를 위임받은 운영자**라는 책임 명칭이다.

- `supplier:operator` 등 기존 역할의 보유만으로 중앙 관리자에 자동 진입하지 않는다.
- 중앙 진입은 Google 인증, 정상 계정, 중앙 Admin의 유효한 직영 업무 위임을 확인해야 한다.
- 업무 API는 별도로 해당 서비스 역할·유효기간·필요 membership·조직 범위·승인 및 자격 조건을 검사한다. 중앙 진입이 전체 API 권한을 의미하지 않는다.
- 기존 초대·본인 수락·위임·감사 이력을 우선 재사용한다. 기존 역할 보유자의 일괄 중앙 운영자 전환, `platform:operator` 복구, 새 전역 Operator 역할 도입은 하지 않는다.
- 한 사람에게 여러 직영 서비스 업무를 위임할 수 있다. 각 위임의 부여·회수와 독립 사업 역할을 구분한다. 자기 권한 확대와 운영자 재위임은 별도 승인 없이 허용하지 않는다.
- 위임은 기존 역할 할당의 `scope_type=o4o-direct`로 구분한다. 중앙 Admin의 초대·본인 수락 후 정식 역할 write-path로 기록하며, 일반 서비스 역할 재부여는 이 표식을 이어받지 않는다. 초대·감사 이력의 보존기간이 지나도 현재 위임의 정본은 역할 할당이다. 새 전역 역할·독립 권한 원장은 만들지 않는다. 메뉴별 추가 제한 설정은 §10을 따른다.

일반 회원의 카카오·이메일 로그인은 그대로 유지한다. 중앙 Google 전용 정책을 이유로 서비스 Operator 보유자의 일반 회원 로그인까지 일괄 차단하지 않는다. 기존 전체 관리자 Google 전용 경계는 유지한다.

### 4.3 독립 사업자·자기 업무

협업체·분회·MegaPharm·CarePharm의 자체 운영 권한은 해당 사업·조직에 유지한다. O4O 중앙 위임은 그 사업의 역할·소속·가입·승인을 대신하지 않는다. 협업체별 비공개 자료는 서로 공유하지 않는다. 플랫폼 장애 대응·지원 목적도 무제한 사업 데이터 접근의 근거가 아니다.

매장 경영자·직원·공급자·강사 등의 자기 업무는 중앙 Operator 업무와 구별하며 기존 조직·소유·참여 범위로 검사한다.

각 WO는 최신 main의 변경 대상만 재확인한다. IR-1~IR-4 전체 재조사는 하지 않는다. 기존 인증 트랙의 실사용 OAuth·계정 연결 등 미완료 검증은 별도 추적하며 이번 정책 문서 완료로 대체하지 않는다.

## 7. Frozen/Core 영향과 변경 절차

- [F9](../rbac/RBAC-FREEZE-DECLARATION-V1.md): `role_assignments`와 정식 읽기·쓰기 경로 유지. `users.role/roles`, 폐기된 역할 및 fallback을 복원하지 않는다. 기존 협업체 역할의 조직별 경계도 유지한다.
- [F10](../architecture/O4O-CORE-FREEZE-V1.md): 운영 책임 WO-1은 문서만 변경했다. Auth/Membership/Approval/RBAC Core의 구조·미들웨어·API 계약 변경이 필요한 후속 WO는 `CORE_CHANGE_REQUIRED`, 변경 사유·대상·명시적 승인 범위 및 재검증 계획을 먼저 적는다. 이번 정책 채택은 포괄적 Freeze 해제가 아니다.
- [Role/Guard baseline](ROLE-POLICY-AND-GUARD-V1.md): 상위 역할의 하위 자동 포함 금지, 서비스·조직 격리, 명시적인 경로별 검사 유지. 중앙 메뉴 통합으로 전체 플랫폼 bypass를 켜지 않는다.
- 공통 상품 DB의 전체 관리자 보호는 별도 결정까지 유지한다. 위임 시 조회·등록·수정·삭제·복구 등 작업별 범위를 별도 WO로 확정한다.
- B2C AI 규격 설명서는 별도 후속 과제로만 기록하며 이번 리팩토링 구현 범위에 넣지 않는다.

## 8. 사용자 판단이 필요한 사항

1. `pharmacy` 사업의 실제 운영 주체와 기타 미확정 도구의 담당 범위. 결정 전 중앙 직영 목록 확대 금지.
2. 공통 약사 자격의 수동 승인 기준은 §2로 확정했다. 과거 자료의 일괄 인정·자동 승격은 하지 않는다. 추후 외부 면허 조회·자동 승인 방식 도입은 별도 정책 결정이다.
3. Partner 사업 활동·승인 대상. 커뮤니티 즉시 가입을 사업 승인으로 간주하지 않음.
4. 공통 상품 DB의 Operator 위임 작업·제한 범위. 별도 결정 전 현행 경계 유지.
5. 독립 사업의 비공개 자료를 중앙에서 조회해야 할 경우 목적·항목·담당자 범위. 필요 발생 시에만 확인.

사업 책임·회원/자격 정책·독립 조직 권한·Admin/Operator 경계의 새 변경은 사용자 판단 대상이다. 기존 코드 재사용, UI 연결, 내부 배치, 테스트 등 승인된 범위의 기술 선택은 개발 담당이 결정한다.

## 9. 구현·운영 상태 구분

[통합 구현 WO](../work-orders/WO-O4O-UNIFIED-MEMBERSHIP-ADMIN-REFACTOR-V1.md)는 일반 커뮤니티·수강자 접근, 약사 자격 신청·검토, 중앙 위임 진입과 직영 운영 UI 연결을 하나의 개발 브랜치에서 진행한다. 이 문서의 정책 채택이나 로컬 검증은 main 병합·운영 적용을 뜻하지 않는다. 운영 DB 변경·기존 사용자 자격 자동 승인·배포는 이번 개발 작업에서 하지 않는다.

- 중앙 `/operations`는 Google 세션과 현재 위임을 확인한다. 기존 `/admin`·중요 상품 DB·운영자 재위임은 전체 관리자 경계를 유지한다.
- 공통 자격은 기존 개인 프로필에 상태·사유를 추가하고 승인자·승인시각과 감사기록을 재사용한다. 약국 경영은 공통 자격과 약국 원장·소속 권한을 함께 검사한다. 직원의 일반 업무는 개인 약사 자격과 구별한다.
- 일반 기능의 과거 pending/rejected 가입 이력은 공통 계정을 차단하지 않는다. 명시적 서비스 정지·탈퇴, 전문·조직·사업·실제 수강 조건은 유지한다.
- 독립 사업의 운영 주체나 비공개 데이터 범위는 중앙 화면 연결을 근거로 확대하지 않는다. 전문 세부 화면은 재사용·소비처 검증 없이 삭제하지 않으며, 남아 있는 특화 업무는 기존 호스트로 연결한다.

## 10. 메뉴 단위 위임 구체화 — 구현 브랜치, 운영 반영 전

`WO-O4O-UNIFIED-OPERATIONS-WORKSPACE-V1`은 위 운영 책임을 변경하지 않고 실제 업무 메뉴 단위로 위임을 좁힌다. 강사/강의/포럼/펀딩 신청은 예시이며, 현재 유지되는 직영 운영 화면의 상세·탭·명령·실패 복구까지 대조한다. 서비스·화면·API의 대응 정본은 해당 WO와 기능 대조 IR에 기록한다. 코드 존재나 메뉴 metadata 등록을 기능 완료 근거로 삼지 않는다.

- 기존 `users`, `service_memberships`, `role_assignments`와 초대·본인 수락·감사 write-path를 유지한다. 새로운 전역 Operator 역할은 만들지 않는다.
- `central_operation_menu_grants`는 기존 역할 할당 또는 수락 전 초대 한 건에 종속된 **추가 제한 설정**이다. 이 레코드만으로 사용자·역할·membership·조직 권한을 얻지 못한다. 기존 F11의 독립 권한 원장을 만드는 구조와 구분한다. Core entity와 Core membership guard는 변경하지 않고 application 경계에서 추가 검사한다.
- 업무 설정은 중앙 Admin만 조회·변경한다. 실제 선택 값은 해당 서비스/역할의 메뉴 allowlist와 교차 검증하며 사유와 동시 수정 버전을 확인한다. 다른 서비스·전체 관리자 전용 업무를 위임할 수 없다. 복수 서비스는 기존 복수 역할 할당으로 처리한다.
- 초대의 업무 범위는 수락 전에 확인할 수 있어야 하며 수락 transaction에서 역할 할당의 제한으로 이전한다. 기존 명시적 중앙 위임에 제한 설정이 없으면 종전 서비스 업무를 유지한다. 명시적인 빈 목록은 중앙 업무 없음이다. 기존 서비스 역할만으로 중앙 위임을 만들지 않는다.
- 메뉴 표시뿐 아니라 중앙 직접 URL과 원래 업무 API에서도 제한을 검사한다. 중앙 위임을 사용하는 운영 요청은 Google proof를 요구하며 일반 회원의 이메일/카카오·자기 업무 로그인은 유지한다. 독립 조직 API의 기존 소속·사업 범위를 대체하지 않는다.
- 전체 Admin의 직영 Community·Partner·연합회 운영은 실제 직영 책임에 맞춘다. 가입/membership을 자동 생성하거나 MegaPharm/CarePharm/개별 조합/분회의 내부 운영권을 얻는 예외로 확대하지 않는다.
- 공통 회원 directory에는 자격 프로필이 없는 계정도 포함한다. 회원 조회와 약사 자격 심사를 분리하며 회원 조회만 위임받은 담당자에게 면허번호·검토 사유를 전달하지 않는다. 기존 서비스 가입 처리와 약국·매장 신청 심사는 별도 업무다.
- 메뉴 제한의 소유는 기존 할당/초대의 FK로 정하고 부모 삭제와 함께 제거한다. 별도의 사용자 식별·승인 사유를 설정 테이블에 복제하지 않는다. 감사는 기존 action log에 기록한다. 새 테이블에도 현행 erasure writer fence를 적용한다.

본 절은 2026-10-27의 **직영 Operator를 중앙에서 지정하지 않는 범위**와 이전 제한적 중앙 업무 화면을 이 WO 범위에서 구체화한다. 독립 사업자의 자체 지정/사업 운영, 공통 상품 DB 중요 관리 권한, 기존 퇴역·인증 제공자·자격·조직 계약을 대체하지 않는다. 실제 migration·CI·브라우저·배포 상태는 WO/CHECK의 검증 결과로 확인한다. 이번 구현 브랜치의 운영 적용은 아직 수행하지 않았다.

### 10.1 삭제 원장 연동의 구현 보완 (2026-10-29, 배포 전)

메뉴 제한의 소유는 부모 역할 할당/초대의 수신·수락 계정으로 판별한다. 초대한 계정은 설정의 소유자가 아니다. 계정 제거 과정에서 설정 ID도 reference key로 포착하고 본인 설정만 제거하며, 다른 사람에게 복사된 ID는 기존 수동 검토 경계를 유지한다. 형식이 확인된 위임/메뉴 변경 감사 이벤트의 삭제 대상 식별정보는 최소화하되 기존 생성 시각·감사기록 보유기간을 유지한다. 알 수 없는 감사 payload를 통째로 삭제하거나 검토에서 제외하지 않는다. 기존 서비스 중지 선행 조건·법정 기록 검토·writer fence를 완화하지 않는다.
