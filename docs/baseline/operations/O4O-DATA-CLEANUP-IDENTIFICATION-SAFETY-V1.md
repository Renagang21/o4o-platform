# O4O 데이터 정비 대상 식별 안전 규칙 V1

> **운영 데이터를 지우기 전에 "무엇을 지우는지" 를 증명하는 규칙이다.**
> 대상 식별이 틀리면 되돌릴 수 없다. 이 문서는 삭제 방법이 아니라 **대상 판정 방법**을 정한다.

## 1. 원칙 (필수)

> **UUID prefix 만으로 운영 데이터를 일괄 삭제하지 않는다.**
> 정확한 대상 UUID, 생성 이력, 의미 있는 두 번째 세그먼트, 자연키, FK 역방향 참조를
> 함께 확인한 뒤 판정한다.

`e0000000%`, `f0000000%` 처럼 "고정 UUID = fixture" 로 보이는 prefix 는 **fixture 전용이 아니다.**
같은 prefix 아래에 정상 운영 콘텐츠와 live 코드 상수가 함께 존재한다는 것이 실측으로 확인됐다.

| prefix | 실제로 들어 있던 것 |
|---|---|
| `e0000000%` | KPA 게시 콘텐츠 (`cms_contents`) — 상당수가 **활성 slot 에서 소비 중** |
| `f0000000%` | **live 코드 상수** — 소스에 하드코딩된 식별자 |

prefix 로 일괄 삭제했다면 운영 콘텐츠와 코드가 참조하는 식별자를 함께 지웠을 것이다.

## 2. 판정에 반드시 포함할 근거

대상 하나를 "지워도 되는 것" 으로 판정하려면 아래를 **모두** 확인한다. 하나라도 비면 판정하지 않는다.

| 근거 | 확인 방법 |
|---|---|
| **정확한 UUID 집합** | 열거된 개별 UUID. `LIKE 'prefix%'` 는 조사 보조 수단일 뿐 판정 근거가 아니다 |
| **두 번째 세그먼트** | `e0000000-ee01`, `f0000000-aa01` 처럼 계열을 구분하는 자리까지 본다 |
| **생성 이력** | migration / seed 스크립트 / `typeorm_migrations` 실행 기록에서 출처를 특정한다 |
| **자연키** | fixture 이메일·코드명 등 UUID 밖의 식별자로 교차 확인한다 |
| **FK 역방향 참조** | 부모 ID 를 기준으로 이 행을 가리키는 모든 자식 테이블을 역추적한다 |
| **코드 참조** | 소스에 상수로 박혀 있는지 검색한다. 참조 행이 없어도 코드가 그 값을 쓰면 삭제 대상이 아니다 |

## 3. `gen_random_uuid()` 하위 행 — prefix 검색으로는 못 찾는다

부모를 고정 UUID 로 심었더라도, **자식 행은 `gen_random_uuid()` 로 생성되어 prefix 가 다르다.**
따라서 prefix 검색만으로는 고아 여부를 판단할 수 없다.

```
잘못된 방법   SELECT * FROM child WHERE id LIKE 'e0000000%';        -- 항상 0건. 아무것도 증명하지 못한다
올바른 방법   SELECT * FROM child WHERE parent_id IN (<부모 UUID 집합>);  -- 부모 기준 FK 역추적
```

부모가 `ABSENT` 임을 확인했다면, **같은 부모 집합으로 자식 테이블을 전부 역추적해 0 임을 함께 증명**한다
(부모 0 + 자식 0 → 고아 0).

## 4. 조사는 read-only 로 하고, 차단을 실증한다

- 세션에 `SET default_transaction_read_only = on` 을 걸고 `SHOW transaction_read_only` 로 확인한다.
- **차단이 실제로 걸렸는지 증명**한다 — `CREATE TEMP TABLE` / `UPDATE` / `DELETE` 를 시도해 거부되는 것을 기록한다.
- 조사 SQL 은 저장소에 남겨 **재현 가능**하게 한다 (`scripts/audits/`).
- 스크립트에 자격증명 literal 을 넣지 않는다.

## 5. "대상이 없음" 도 정상 완료다

정비 작업의 결과가 반드시 삭제일 필요는 없다.
**삭제 대상이 존재하지 않음을 증명한 것** 역시 완결된 결과이며, 이때는 후속 데이터 정리 WO 를 만들지 않는다.

`b501e007c` 가 그 사례다 — SET A/B 가 `ABSENT` 로 확정되어 운영 DB write 0 으로 트랙이 마감됐고,
선행 CHECK 들의 "seed 잔존" 보류 항목이 함께 종결됐다.

## 6. 판정이 갈리는 것은 섞지 말고 분리한다

한 조사에서 성격이 다른 것이 같이 나오면 **같은 WO 로 처리하지 않는다.**

| 사례 | 올바른 처리 |
|---|---|
| slot 미연결 게시 콘텐츠 | fixture 가 아니다. 콘텐츠 큐레이션·보관 정책 트랙에서 판단한다. 미연결 = 삭제 후보가 아니다 |
| 참조 행이 없는 live 코드 상수 | 기능 생명주기 조사 대상이다(초기화 기준값 / 예약 식별자 / 잔재 / 휴면 기능 중 무엇인지) |

미연결·미참조는 그 자체로 삭제 근거가 아니다. **무엇인지 판정되기 전까지는 손대지 않는다.**

## 7. 적용 범위

운영 DB 를 대상으로 하는 모든 정비 작업 — legacy fixture 제거, 고아 행 정리, backfill 대상 선정,
비활성화·격리 판단 — 에 적용한다.

데이터 변경(UPDATE/DELETE/DROP/ALTER)은 [`CLAUDE.md`](../../../CLAUDE.md) §0 에 따라 **사용자 승인이 필요**하며,
이 문서의 판정 근거를 갖추지 못한 삭제는 승인 요청 자체를 하지 않는다.
