# O4O Work Order

사용자의 요청을 실제 작업으로 연결하는 절차 선택기다. 새로운 개발 정책이나 아키텍처를 정의하지 않는다.

## 1. 현행 규칙을 먼저 읽기

작업 저장소의 루트를 확인하고 [AGENTS.md](../../../AGENTS.md)를 읽는다. 이 Skill은 최상위 실행 규칙인 AGENTS.md를 대체하지 않는다. 사용자 지시와 문서 간 우선순위도 그 문서의 Source of Truth 규칙을 적용한다. 경로 링크는 이 Skill 파일 기준이다.

[Canonical Index](../../../docs/CANONICAL-INDEX.md)에서 해당 업무의 현행 정본을 찾고 본문과 상태를 확인한다. 작업 경로에 적용되는 추가 AGENTS.md가 있으면 함께 읽는다. 필요한 문서가 없거나 서로 충돌하면 그 영향을 받는 작업을 보류하고 근거를 보고한다. 독립적으로 가능한 조사는 계속한다.

기존 WO·CHECK·IR은 요청의 배경, 실행 이력과 검증 증거로 재사용한다. 기록의 완료 표시나 과거 정책을 현행 정본으로 취급하지 않는다. 새 작업 ID나 문서를 만들기 위해 사용자의 요청을 다시 작성하게 하지 않는다. 문서 생성이 필요한지는 AGENTS.md의 문서 규칙으로 판단한다.

## 2. 요청 분류

| 분류 | 요청의 목적 | 실행 방식 |
| --- | --- | --- |
| INVESTIGATION | 원인·현황·영향 조사 | 읽기 전용 조사 후 근거 보고 |
| IMPLEMENTATION | 기능 구현 또는 오류·UI 수정 | 조사로 범위를 확정한 뒤 승인된 변경과 검증 |
| VALIDATION | 기존 코드·PR·검증 기록 확인 | 변경 범위와 실제 검증 증거를 대조 |
| INTEGRATION | 명시적으로 요청된 PR 통합과 후속 확인 | 기존 통합 규칙과 현재 사용자 승인 범위 적용 |

“조사하고 필요한 부분을 수정”은 IMPLEMENTATION으로 분류하되 조사부터 시작한다. “통합 가능한지 확인”은 VALIDATION이며 그 문구만으로 통합을 실행하지 않는다. 혼합 요청은 단계를 나누고 각 단계의 변경 허용 범위를 유지한다.

계획·시뮬레이션 요청은 해당 분류에 `SIMULATION`을 표시한다. 계획과 예상 검증만 작성하고 코드 수정, commit·push·PR 생성, 통합, 배포를 실행하지 않는다. 실행 예정인 검사를 PASS로 보고하지 않는다.

요청이 명확하면 바로 진행한다. 결과나 승인 범위를 결정하는 필수 정보가 실제로 부족한 경우에만 짧게 질문하고, 답변과 무관한 작업은 계속한다. 이미 주어진 승인을 다시 요구하지 않는다.

## 3. 실행 범위 정하기

코드와 현행 정본을 확인하여 다음을 간단히 정리한다. 확인 전 추측은 사실과 구분한다.

- 요청 분류, 기대 결과, 포함·제외 범위, 기존 WO가 있으면 해당 ID
- 대상 서비스와 실제 파일·컴포넌트·호출 경로
- 공통 모듈·Core·Extension 및 다른 서비스 소비자에 미칠 영향
- 작업 격리 필요 여부와 현재 작업공간 상태
- 변경 범위에 맞는 검증과 성공을 판단할 증거
- 현재 승인으로 가능한 작업과 추가 승인이 필요한 구체적인 작업

격리, 공통 모듈 영향 확인, 위험 작업 승인, Git 작업, 통합과 배포의 판단 및 명령은 AGENTS.md와 관련 현행 정본을 따른다. 여기서 별도의 안전 규칙이나 예외를 만들지 않는다. 관련 문서만 읽고 같은 정책을 이 Skill에 복제하지 않는다.

## 4. 선택한 절차 실행하기

### INVESTIGATION

정본과 구현을 대조하고 요청한 사실·원인·영향을 조사한다. 사용자 파일, 코드, Figma, DB, 운영 설정을 변경하지 않는다. 조사 결과를 남기기 위한 저장소 문서나 branch도 자동으로 만들지 않는다. 관측한 결과와 추정을 구분한다.

### IMPLEMENTATION

AGENTS.md의 작업 격리 절차를 적용한 뒤 승인된 범위만 변경한다. 공통 변경은 해당 영향 확인 절차를 먼저 수행한다. 범위 밖 문제가 보이면 별도 발견 사항으로 보고한다.

요청과 실제 변경에 맞는 검증을 실행한다. UI 변경은 현행 UI 검증 규칙을 적용하고 실제 브라우저 증거를 확보한다. 테스트 실패나 도구 제약을 해결할 때도 요청 범위를 지킨다. commit·push·PR 및 CI 확인은 기존 Git 절차와 승인 범위에 따라 수행한다.

### VALIDATION

작업 당시 기록과 현재 상태를 분리한다. PR이면 파일 변경 범위, head commit, 현재 상태, 해당 revision의 CI, 리뷰와 미해결 스레드, 통합 준비 여부를 각각 확인한다. 과거 revision의 성공을 현재 CI 성공으로 대체하지 않는다.

이미 통합된 PR은 통합 완료 상태로 보고한다. 검증 기록 조회만 요청된 경우 수정·재실행·통합을 임의로 수행하지 않는다. 실행하지 못한 검사와 접근할 수 없는 증거는 미확인으로 남긴다.

### INTEGRATION

통합 대상과 사용자 승인이 명시되어 있는지 확인하고 AGENTS.md의 통합 조건을 점검한다. 승인이나 필수 증거가 부족하면 준비 상태와 차단 사유만 보고한다. 통합 준비 완료와 실제 통합 완료를 구분한다. 통합 승인을 배포 승인으로 확대하지 않는다.

## 5. 증거와 완료 보고

요청한 결과를 검증 증거와 대조한다. 실제 실행한 검사만 결과로 기록하고, 계획·정적 확인·실행 검증을 구분한다. 새로운 세션의 Skill 발견처럼 현재 세션에서 확인할 수 없는 사항은 미확인으로 보고한다.

다음 항목을 한국어로 간결하게 보고한다. 해당하지 않는 항목은 생략하거나 N/A로 표시한다.

1. 수행한 작업과 요청 분류
2. 변경 파일과 핵심 내용 또는 읽기 전용 여부
3. 실행한 검증, 대상 revision·환경, 결과와 증거
4. 미해결 사항과 실제 차단 사유
5. PR·CI 및 리뷰 상태
6. main 통합 필요 여부와 실제 통합 여부
7. 배포 필요 여부와 실제 수행 여부
8. 다음 작업의 필요성

AGENTS.md가 요구하는 문서 정합 및 작업공간 처리 보고도 포함한다. 완료 판정이 부족한 항목을 성공으로 채우지 않는다. 사용자에게 새로운 WO 작성을 요구하는 대신 현재 요청에서 가능한 작업과 남은 필수 조건을 분명히 한다.
